# 기술 선택과 구현 방향

이 문서는 현재 상태와 다음 구현 순서를 정리합니다. 아래 선택은 조사 결과를 바탕으로 한 추천입니다. 아직 코드에 넣지 않은 기능은 구현된 것처럼 설명하지 않습니다.

## 지금 프로그램이 하는 일

- 네이티브 그래픽 앱은 Flecs Entity에 붙은 Jolt Body로 위치·속도·Quaternion 자세·각속도를 계산합니다. 운동학 기준선은 비교 시험과 WebAssembly 실행에서 사용합니다.
- 그래픽 앱이 화면 표시와 함께 게임패드, UDP 명령, 기록·재생, 시나리오 시연, 성능 측정을 맡고 있습니다. UDP 상태 응답은 위치·속도와 함께 자세 Quaternion 및 각속도도 전달합니다. 지상통제의 연속 속도·회전 명령은 기본 60 Tick 동안 갱신되지 않으면 정지시키며, 기록 중에는 자동 정지도 기록합니다.
- 화면이 없는 시나리오 실행 경로와 OpenGL을 쓰는 화면 실행 경로가 따로 있습니다.
- Flecs 4.1.6은 연결했습니다. 드론과 EO 카메라를 각각 Entity로 만들고, 상태 데이터를 Component로 보관해 고정 Tick마다 System이 갱신합니다.
- 강체 모드는 고정 Tick, PD 비행 제어, 모터·로터 힘·항력, 바람, 평평한 바닥 또는 높이 지형의 접촉을 연결했습니다. 화면에는 PX4가 공개한 X500 메시를 불러와 물리 상태의 위치와 자세로 그립니다.

다음 작업은 현재 화면과 명령 흐름을 한 번에 다시 만드는 일이 아닙니다. 모의 상태를 관리하는 작은 중심부를 만들고 기존 기능을 한 단계씩 연결합니다.

## 우선 선택

### Flecs는 객체 관리에만 사용

Flecs는 화면 객체와 시뮬레이션 객체를 식별하고 필요한 상태를 묶는 데 사용합니다. 드론 Entity에는 위치·속도·비행 상태와 제어 목표를, 카메라 Entity에는 센서 상태를 데이터 Component로 보관합니다. Flecs System이 이 데이터를 읽고 갱신합니다. 입력 처리, UDP 소켓, OpenGL 자원은 기존 C++ 객체로 뒀습니다.

Entity는 장면 속 대상의 번호입니다. Component는 그 대상에 붙이는 위치·속도 같은 데이터이고, System은 그 데이터를 읽거나 갱신하는 계산입니다.

현재는 상태와 제어 목표를 필요한 만큼만 나눴습니다. Flecs 기반 객체 관리의 첫 단계는 끝났지만, 여러 기체나 물리엔진을 연결하는 상태 구조까지 완성된 것은 아닙니다. 다음 단계에서 물리 Body와 모터 상태를 더할 때 같은 값을 두 곳에서 관리하지 않도록 주의합니다. Flecs 고급 파이프라인이나 병렬 실행은 넣지 않았습니다.

### 물리엔진은 Jolt로 시작

현재 프로그램은 자체 OpenGL 창과 화면 없는 실행 경로를 이미 갖고 있습니다. Jolt를 기존 구조에 연결하면 별도 시뮬레이터 없이 강체와 충돌을 계산할 수 있습니다. 강체 실행 모드에서는 Flecs Entity가 Jolt Body 핸들을 보유하고, Flecs System이 1/60초씩 Jolt를 진행한 뒤 계산된 위치·속도·자세·각속도를 Entity 상태에 복사합니다. 이 경로에서는 운동학 적분을 실행하지 않습니다. Gazebo는 쿼드콥터 모터 예제가 있다는 장점이 있지만 별도의 시뮬레이터 환경까지 함께 관리해야 하므로 우선순위에서 제외합니다.

Jolt가 드론을 대신 날려 주지는 않습니다. 작은 C++ 비행 모델에서 모터 회전속도에 따른 추력·토크를 계산하고, 그 힘을 Jolt의 강체(물리 계산 대상)에 적용합니다. Jolt가 계산한 위치·자세·속도를 물리 상태의 기준으로 삼습니다. ECS나 화면 코드가 같은 값을 다시 적분하지 않습니다.

Jolt 강체를 만들 때 질량과 함께 기체 축 기준의 주관성 모멘트를 직접 넣을 수 있게 했습니다. 값은 `kg·m²` 단위이며, 생략하면 기존처럼 상자 크기와 질량으로 계산합니다. X500 호버링 시험에는 공개 시뮬레이터 설정의 관성을 전달하고, 같은 회전력을 받았을 때 관성이 작은 물체가 더 빠르게 도는지도 확인합니다. 0 이하이거나 유한하지 않은 관성값은 거부합니다.

강체 모드에서는 TakeOff·속도·경유점·Yaw 회전·Land 명령을 PD 제어로 모터 속도에 연결합니다. 위치·속도 오차에서 필요한 가속도를 구하고, `F = m(a + g)`로 필요한 힘을 계산합니다. 힘 방향으로 목표 자세를 만들고, 자세·각속도 오차를 토크로 바꿉니다. 로터별 힘은 로터 위치와 회전 방향으로 구성한 4×4 식을 풀어 나눕니다. 현재 제어 이득은 위치 3.0, 속도 2.5, 자세 20.0, 각속도 7.0이며 가속도는 4m/s², 토크는 0.5N·m로 제한합니다. 이 값은 초기 설정이며 실기체 자료에 맞춰 조정하거나 검증하지 않았습니다.

X500 충돌 형상은 PX4 공개 Gazebo 모델을 참고해 아홉 개 상자로 단순화했습니다. 중심 프레임 하나, 착륙 다리 둘, 스키드 둘, 프로펠러 면 넷으로 구성합니다. 각 상자는 기체 중심 기준 위치와 방향을 갖고 하나의 강체로 함께 움직입니다. 화면에는 이 상자 대신 PX4가 공개한 본체·모터·프로펠러 메시를 표시합니다. 착륙 다리 아래쪽이 지면에 닿도록 모델 기준점은 지면에서 0.24m 높이에 둡니다. 네이티브 그래픽 앱은 강체 모드로 실행합니다. 헤드리스 시나리오는 기본적으로 운동학 기준선을 사용하고, 시나리오 설정에서 같은 강체 경로를 선택할 수 있습니다. 한 Entity의 위치를 두 방식이 동시에 계산하지 않도록 경로를 분리했습니다. WebAssembly 빌드는 아직 Jolt 대신 운동학 경로를 사용하며, 이 환경의 전체 빌드는 별도로 확인하지 않았습니다.

이륙 목표는 시작 지점의 지면보다 1.5m 높고, 착륙 목표는 지면보다 0.24m 높습니다. 산악 지형의 격자 높이는 기준점보다 높거나 낮을 수 있으므로 월드 높이를 고정값으로 쓰지 않습니다. 화면 시연은 지도 원점의 급한 경사 대신 주변에서 찾은 완만한 지점(동쪽 171.35m, 북쪽 -92.77m)에서 시작합니다. 시작 위치를 바꾼 뒤 Reset을 해도 같은 지면 높이와 위치를 복원합니다. 이 설정은 해당 시연 지점의 이착륙을 확인한 결과이며, 지형 전체에서 안전한 착륙 지점을 자동으로 찾는 기능은 아닙니다.

### 로터가 만드는 힘과 토크

각 로터의 추력은 `T = k_f ω²`로 계산합니다. `ω`는 모터 회전 속도이고, `k_f`는 속도가 추력으로 바뀌는 비율입니다. 기체에 걸리는 회전력은 로터 위치에서 생기는 `r × F`와 프로펠러 반작용 토크를 더합니다. 회전 방향 값은 반시계 방향일 때 `s=+1`, 시계 방향일 때 `s=-1`입니다. 반작용 토크 비율은 `모터 토크/추력`으로 구하므로 단위는 미터입니다. PX4 기준 모델의 값은 `0.016 m`이고, 공개 모터 표에 맞춘 현재 프로필은 `0.0142786 m`입니다. 두 회전 방향의 로터가 같은 속도로 돌면 Yaw 토크가 서로 상쇄됩니다. 입력값이 하나씩 유한해도 큰 계수를 곱하면 힘이나 토크가 무한대가 될 수 있습니다. 모든 입력에 임의의 상한을 붙이는 대신, 계산을 마친 힘과 토크가 유한한지 검사해 잘못된 결과를 거부합니다. 이 사례를 재현하는 회귀 시험에서 수정 전에는 예외가 없었고 수정 뒤에는 잘못된 결과가 거부됐습니다.

모터 속도는 목표값에 즉시 도달하지 않습니다. `ω_next = e^(-Δt/τ) × ω_now + (1 - e^(-Δt/τ)) × ω_target` 식으로 한 단계씩 움직입니다. 속도가 올라갈 때와 내려갈 때 서로 다른 `τ`를 사용합니다. PX4 Gazebo 기준값은 추력 계수 `8.54858×10⁻⁶`, 반작용 토크 비율 `0.016 m`, 상승 시간 `0.0125초`, 하강 시간 `0.025초`, 최대 속도 `1000 rad/s`입니다. 네이티브 강체 실행에는 아래 공개 모터 표에서 맞춘 추력 계수·토크 비율과 표에 실린 최대 회전속도를 사용합니다. 모터 응답과 로터 항력은 계속 PX4 설정을 따릅니다.

현재 항력은 기체 몸체 전체가 아니라 회전 중인 로터에 옆으로 흐르는 공기에서 생기는 힘입니다. 월드 속도와 바람의 차이를 기체 좌표로 바꾸고, 각 로터 축과 나란한 성분을 뺀 뒤 `F_drag = -|ω| k_d v_perp`로 계산합니다. 네 로터의 힘을 더하고, 각 로터 위치 `r`에서 생기는 `r × F_drag`와 구름 모멘트 `τ_roll = -|ω| k_r v_perp`도 반영합니다. 바람이 기체 좌표로 변환되어 Jolt에 전달되는 흐름은 Yaw가 90°인 드론에 월드 +X 바람을 주는 자동 시험으로 확인했습니다. PX4 X500 공개 모델과 Gazebo 모터 계산 코드에는 로터 항력 계수는 있지만 별도 동체 항력 계수는 없어, 확인되지 않은 값을 임의로 보태지 않았습니다. 따라서 이 모델은 실제 기체의 전체 공기 저항을 재현하지 않습니다.

이 숫자는 실측값이 아니라 PX4 Gazebo 시뮬레이터 설정값입니다. 중심 기체 2kg에 로터 링크 네 개의 질량을 더해 총 2.0643kg으로 계산합니다. 이 값은 실제 X500의 전체 비행 중량이 아닙니다. 관성도 각 로터의 관성과 중심까지의 거리를 평행축 정리로 더했습니다. 로터 높이 0.06m도 항력이 만드는 회전력 계산에 반영했습니다. 다만 로터를 각각 회전하는 강체로 계산하지 않고, 질량과 관성을 한 강체에 합친 근사입니다. 회귀 시험은 PX4 모델의 질량·관성·모터 설정과 네 로터의 위치·회전 방향을 직접 비교합니다. 이는 코드가 참고 모델을 빠뜨리지 않고 읽었는지 확인하는 시험이며, 실제 기체의 물리 특성을 검증하지는 않습니다. [PX4 X500 설정](https://github.com/PX4/PX4-gazebo-models/blob/e5997f455e33ec071c7c677fc59a65781de496a4/models/x500/model.sdf)과 [중심 기체 자료](https://github.com/PX4/PX4-gazebo-models/blob/e5997f455e33ec071c7c677fc59a65781de496a4/models/x500_base/model.sdf)를 기준으로 합니다. 기체 몸체 전체의 공기 저항과 실제 기체 제어도 아직 모델에 넣지 않았습니다.

### 공개 모터 시험값과 추력 계수 비교

Holybro 제품 안내는 X500에 2216 KV920 모터와 1045 프로펠러가 포함된다고 밝히고, 연결된 모터 사양 그림을 제공합니다. 그림의 세 시험 지점은 약 16V에서 4,269·6,252·10,703rpm, 추력 214.74·470.2·1,367.04g입니다. 각 점에 `k_f = 추력(N) / 회전속도(rad/s)²`를 적용하면 약 `1.054·10⁻⁵`, `1.075·10⁻⁵`, `1.068·10⁻⁵`가 나옵니다. 세 점이 서로 가까워 `추력 = k_fω²`라는 간단한 근사와 대략 맞습니다. 이 점들은 정적 시험표의 자료이며, 전체 기체의 비행 성능이나 반복 오차를 알려 주지는 않습니다. [Holybro X500 제품 안내](https://holybro.com/collections/multicopter-kit/products/x500-v2-kits), [연결된 모터 사양 그림](https://cdn.shopify.com/s/files/1/0604/5905/7341/files/X500MotorSpec.png?v=1678791632).

세 점 전체의 제곱 오차가 가장 작아지도록 맞춘 추력 계수는 `1.0677459×10⁻⁵`입니다. 이때 표의 추력과 계산 결과 차이는 세 점에서 각각 약 1.33%, 0.74%, 0.05%입니다. 토크와 추력의 비율도 표의 세 점에 맞춰 `0.0142786 m`로 추정했습니다. 표의 토크는 `0.01 N·m` 단위로 반올림되어 있어, 계산 결과와 표의 차이는 각 지점에서 `0.005 N·m`보다 작습니다. 가장 높은 표의 운전점은 `1120.82 rad/s`이므로, 모터 속도 상한도 이 값으로 제한합니다. 이는 표에서 확인한 시험 범위의 끝이지 모터의 안전 최대 속도라는 뜻은 아닙니다. 추력 계수는 PX4 기준값보다 약 25% 크고, 토크 비율은 약 10.8% 작습니다.

따라서 네이티브 강체 실행은 모터의 추력·반작용 토크 계수와 확인된 속도 범위에 한해 공개 표에 맞춘 추정값을 사용합니다. 이 설정을 실제 기체 전체의 검증으로 보지는 않습니다. 공개 표에는 시험 장치·반복 횟수·오차 범위가 충분히 설명되어 있지 않고, 질량·관성·모터 응답·항력은 여전히 PX4 시뮬레이터 설정에 의존합니다. `X500Gazebo` 값은 비교 기준으로 보존합니다. 더 신뢰할 수 있는 값에는 동일한 모터·프로펠러·전압에서의 원자료나 자체 추력 시험이 필요합니다.

참고 자료: [Holybro X500 구성과 모터·프로펠러 안내](https://holybro.com/collections/multicopter-kit/products/px4-development-kit-x500-v2), [Holybro 연결 모터 사양 표](https://cdn.shopify.com/s/files/1/0604/5905/7341/files/X500MotorSpec.png?v=1678791632), [표의 시험값을 인용한 공개 학위논문](https://munin.uit.no/bitstream/handle/10037/25775/thesis.pdf?isAllowed=y&sequence=2).

헤드리스 강체 시나리오는 `wind_velocity_meters_per_second`로 일정한 월드 바람을 설정할 수 있습니다. 2m/s 바람을 X축으로 둔 10초 이륙·착륙 시험에서 공개 모터 표 기반 설정은 시작점에서 약 1.55m 떨어진 곳에 착륙했습니다. 설정을 바꾸기 전에는 약 1.71m였습니다. 새 추력 계수와 속도 상한으로 다시 실행한 결과이며, 현재 제어기는 공중에서 속도를 줄이지만 위치를 고정하지 않습니다. 또 로터가 중심 기체보다 0.06m 높은 곳에서 항력을 받아 자세에 회전력이 생깁니다. 이 값은 현재 모델에서 재현한 결과이지 실제 X500의 바람 대응 성능을 뜻하지 않습니다.

공식 배포 목록에서 확인한 Flecs 4.1.6과 Jolt 5.6.0을 기준으로 합니다. Flecs 4.1.6은 Release 빌드와 화면 없는 실행, Viewer 스모크 시험에서 확인했습니다. 강체 단위 시험에는 자유낙하, 힘·토크, 평평한 바닥·실제 높이 지형 접촉, 로터 추력으로 만든 호버링, 입력한 관성에 따른 회전 차이, 여러 상자로 된 강체의 접촉이 포함됩니다. 강체 경로에서는 상승·속도 이동·경유점·Yaw 회전·착륙 명령과 같은 입력의 반복 결과도 확인합니다. 명령 기록을 재생했을 때 운동학과 Jolt 강체 모드에서 Tick 수와 위치·속도·자세·각속도가 기록 결과와 일치하는지도 시험합니다. 이륙 뒤 10분 동안 호버링하는 시험에서는 매초 상태값의 유한성, 고도와 자세 유지 여부를 확인합니다. 헤드리스 실행에서는 바람을 포함한 강체 모드 이륙·착륙 시나리오도 확인합니다. 지형 격자 읽기, 좌표 변환, 최고점 충돌과 Viewer 시작도 확인합니다. 최신 전체 빌드와 시험 결과는 아래 기록에서 갱신합니다. 이 장시간 시험은 실기체 내구성이나 실제 비행 안정성을 증명하지 않습니다. 제어 이득과 공력 값의 실기체 적합성도 검증하지 않았습니다.

다중 드론 시험에서는 X500 두 대를 서로 접근시킵니다. 120 Tick 동안 두 기체 중심 사이의 3차원 거리 최솟값이 0.30m를 넘고 0.55m보다 작은지 확인합니다. 현재 충돌 형상에서 서로 겹쳐 지나가지 않는지 보는 시험입니다. 시나리오는 설정한 최소 중심 간격보다 가까워지면 실패 처리할 수 있습니다. 실제 접촉 시각이나 충격량을 이용한 판정은 아직 지원하지 않습니다.

위치 공유 시나리오에서는 한 드론이 다른 드론의 위치를 받아 지정된 간격을 유지합니다. 설정한 Tick 구간에 연결을 끊으면 추종 드론은 마지막 목표를 향해 움직이고, 복구 뒤에는 새 위치를 다시 따라갑니다. 이 흐름은 한 방향 위치 공유만 흉내 냅니다. 패킷 지연·손실률·대역폭·신호 세기는 모델에 포함하지 않습니다.

### 첫 기체는 PX4 X500으로 검증

첫 실기체 기준 모델은 PX4 X500으로 진행합니다. 제조사 제원과 시각 자료가 있고, PX4 공개 시뮬레이션 모델에는 관성·로터 위치·모터 응답·추력 계수의 출발점이 있습니다. 모델에 들어 있는 숫자는 제조사 실측값이 아니라 시뮬레이터 설정값으로 표시합니다.

제조사 자료의 610g은 X500 V2 프레임 키트 무게이고, 500mm는 휠베이스입니다. PX4 Gazebo는 중심 기체를 2kg, 로터 링크 네 개를 합쳐 2.0643kg으로 설정합니다. 프레임 키트 무게와 시뮬레이터 기체 질량은 포함 부품과 기준이 다르므로 직접 비교하지 않습니다. 배터리와 탑재 장비를 포함한 비행 상태의 질량·무게중심·관성 자료를 확보하기 전에는 X500 실기체와 물리적으로 일치한다고 주장하지 않습니다.

화면에는 PX4가 공개한 X500 본체, 모터와 프로펠러 메시를 불러옵니다. 원본의 미터·Z축 위 좌표를 화면의 Y축 위 좌표로 바꾸고, SDF에 적힌 부품 위치를 적용해 하나의 메시로 묶었습니다. 약 25만 개 삼각형으로 된 형상이며, 표면 무늬와 개별 재질은 가져오지 않아 현재 화면에서는 한 가지 색으로 보입니다. PX4 모델 저장소는 BSD 3-Clause 조건을 표시하고 있어 그 안내를 모델 자산과 함께 보관합니다. 이 시각 메시를 X500 전체의 정확한 CAD나 실측 형상으로 간주하지 않습니다.

### 실제 지형 높이를 화면과 충돌에 연결

북한산 남쪽 구역의 NASA SRTM 자료를 65×65 격자로 잘라 화면 지형과 Jolt 높이 충돌체에 함께 사용합니다. 자료 중심의 위도·경도를 시뮬레이션 원점 `(0, 0)`에 두고, 지역 범위가 작아 위도·경도 차이를 동쪽·북쪽 평면 거리로 근사합니다. 기준 높이는 중심점의 EGM96 고도이며, 지형 높이는 이 값에서 얼마나 위·아래인지 나타냅니다.

격자는 동서 약 24.5m, 남북 약 30.9m 간격입니다. 자동 시험은 실제 격자의 최고점에서 강체가 멈추는지 확인합니다. Viewer 시작 시험은 지형 자료를 읽어 화면 장면을 그리는 경로를 실행합니다. 지형 높이 정확도나 실제 지도 화면의 시각 품질을 별도 측량 자료와 비교하지는 않았습니다.

국립공원공단의 북한산 시설물 49개는 EPSG:5186 위치와 정표고를 기준으로 화면 GLB와 Jolt 충돌 상자에 연결했습니다. 충돌은 원본 메시가 아니라 각 모델의 경계 상자를 사용합니다. 변환한 3DS 형상의 바닥과 원본 목록 높이를 비교했을 때 차이는 -0.34~0m였고 평균은 -0.018m였습니다. 형상 바닥과 SRTM 보간 높이의 차이는 -25.25~+29.77m, 평균 -7.79m였습니다. 시설물 정표고는 인천항 평균해수면 기준이고 SRTM은 EGM96 기준입니다. 현지 법령도 우리나라 중력기준면을 인천만 평균해수면의 지오포텐셜값으로 정의합니다. 두 기준을 잇는 보정은 적용하지 않았습니다. 49개 중 8개만 주변 SRTM 네 격자 높이의 최솟값과 최댓값 사이에 들었고, 이는 격자 지형이 시설물 아래 지면을 정확히 나타낸다는 증거가 아닙니다. 높이 기준 변환, 지형 격자 간격, 실제 지면 형상의 영향을 각각 측량 자료와 비교해야 합니다. [높이 기준 규정](https://www.law.go.kr/LSW/admRulLsInfoP.do?admRulSeq=2100000278218), [SRTM 높이 기준과 해상도](https://www.usgs.gov/centers/eros/science/usgs-eros-archive-digital-elevation-shuttle-radar-topography-mission-srtm). 이 시설물은 주변 건물 자료를 대신하지 않습니다.

건물 외곽선은 계속 OpenStreetMap 17개를 씁니다. 높이와 층수가 없어 화면·Jolt 상자에는 3m 시연용 가정을 사용하며, 실측 높이가 아닙니다. 같은 구역의 Overture 자료 18개도 높이와 층수가 비어 있습니다. 국토교통부 GIS건물통합정보 SHP는 건축물대장 속성을 합친 자료지만, 공식 안내만으로는 북한산 건물의 높이 필드와 대응 관계를 확인할 수 없습니다. 따라서 실제 건물 높이 반영은 남아 있습니다.

## 앞으로 연결할 상태 흐름

```text
명령·시나리오 입력
  → 비행 제어와 모터 목표 계산
  → 로터 힘·토크와 항력 적용
  → Jolt 고정 시간 계산
  → Flecs 상태 갱신
  → 센서와 결과 판정
  → 화면용 자세 전달
```

모의 코어는 드론마다 Flecs Entity와 상태·제어·모터 정보를 보관합니다. 드론에 ID를 붙여 따로 명령하고 상태를 읽을 수 있으며, 제거할 때 연결된 Jolt 강체도 함께 없앱니다. 모든 드론의 힘을 적용한 뒤 공통 Jolt 세계를 Tick당 한 번 계산하고 상태를 다시 Entity에 복사합니다. 한 세계를 공유하므로 드론끼리 부딪힐 수 있고, 드론 수만큼 물리 시간이 더 흐르지 않습니다. 마지막 드론은 지울 수 없어 기존 단일 드론 호출도 계속 동작합니다. 화면과 지상통제 프로그램은 기본 드론 한 대를 다룹니다. JSON 시나리오는 이름으로 드론을 여러 대 지정해 각각 명령하고 마지막 상태를 확인할 수 있습니다. 시나리오에서는 한 방향 위치 공유와 연결 단절·복구, 드론별 역할·목표·완료 기한이 있는 기본 공동 임무를 시험할 수 있습니다. 실제 네트워크나 임무 간 선후 관계·경로 재계획은 아직 구현하지 않았습니다.

EO 센서는 Flecs Component에 상태, 프레임 정보와 월드 기준 위치·자세를 보관합니다. 카메라 중심은 동체 기준 앞쪽 0.35m, 위쪽 0.12m에 고정하고 자세는 동체를 따릅니다. 고정 Tick의 물리 계산과 상태 복사가 끝난 뒤 센서 위치·자세를 갱신하므로 렌더러는 그 Tick의 최종 드론 상태를 읽습니다. 렌더링은 Z축 위 좌표를 화면의 Y축 위 좌표로 바꾸며, 화면 구도용 아래쪽 시선 기울기는 별도로 적용합니다. 기본 드론이 바뀌면 센서 자세도 즉시 새 드론에 맞춥니다. 이 장착 위치와 시선 기울기는 현재 시연용 설정이며 실기체 카메라 장착값은 아닙니다.

EO 프레임 번호는 활성 상태에서 고정 Tick마다 늘고, 화면은 그 시각에 그린 픽셀에 같은 Tick 번호를 붙입니다. 녹화나 재생을 시작하면 시뮬레이션 시간이 0으로 돌아가므로 저장된 영상도 함께 비웁니다. Tick 시각에 별도 세대 번호를 두는 방안도 검토했지만, 초기화 순간 영상만 무효화하면 되어 더 단순한 쪽을 선택했습니다. 자동 시험은 자세가 바뀐 경우와 기본 드론 교체·초기화 뒤에도 센서 위치·자세가 일치하는지, Viewer 실행 종료 때 영상 Tick이 활성 센서 Tick과 같은지 확인합니다.

## 성능 측정

일반 실행에서는 물리 계산 시간을 재지 않습니다. 벤치마크를 켰을 때만 Jolt가 한 물리 단계를 계산하는 데 걸린 시간을 기록합니다. 이 값은 제어 입력, 모터 계산, 상태 복사에 걸린 시간을 포함하지 않습니다. 전체 Tick 시간은 이 작업들을 포함해 따로 잽니다.

2026년 10월 22일, 같은 Windows Release 실행 파일로 숨김 화면을 5초씩 세 번 측정했습니다. 화면 크기는 1280×720이고, X500 메시와 강체 물리를 사용했습니다. Jolt 계산 p95는 38.8~42.2µs, 전체 Tick p95는 52.3~57.2µs였습니다. 한 번에 처리한 Tick은 실행마다 298개였고, 초당 화면 출력은 약 397~400회였습니다. 이 결과는 이 컴퓨터에서의 기준 측정이며, 다른 기기나 실제 비행의 성능을 뜻하지 않습니다. 측정 원본에는 p50·p95·p99와 메모리·CPU 값도 남겼습니다.

드론 수별 물리 비용은 화면을 그리지 않는 경로에서 따로 측정합니다. 화면 출력과 물리 계산의 시간이 섞이지 않게 하며, 결과에는 1·2·4·8대의 반복 측정과 CPU·작업 집합 표본을 함께 기록합니다.

처음 계측했을 때 물리 시간이 모두 0으로 나왔습니다. 실패한 시험을 따라가 보니, 계측을 끈 경우에만 실행해야 할 `return`이 조건문 밖에서 항상 실행되고 있었습니다. 조건문 범위를 고친 뒤 물리 세계와 시뮬레이션 코어의 회귀 시험을 통과시켰고, 그 다음에 세 번 다시 측정했습니다. 자세한 표본은 [성능 측정 원본](../../benchmarks/results/aerosimlab-mvp-release.json)에 있습니다.

국립공원 시설물 49개를 화면과 Jolt 충돌에 연결한 뒤에도 같은 장비와 5초 측정으로 세 번 확인했습니다. 화면 출력은 398.4~406.5FPS, 전체 Tick p95는 54.6~55.1µs, Jolt 단계 p95는 39.7~40.8µs였습니다. 시설물 연결 전 결과는 한 번만 측정했으므로 두 조건의 차이로 성능이 개선되거나 나빠졌다고 결론내리지 않습니다. 새 측정은 위 원자료에 이어 기록했습니다.

드론 수에 따른 비용도 같은 Release 빌드에서 다시 쟀습니다. 화면을 그리지 않는 강체 모의에서 1·2·4·8대를 각각 세 번 실행했고, 매 실행은 120 Tick을 준비 단계로 진행한 뒤 30,000 Tick을 측정했습니다. 전체 Tick p95는 차례로 3.7µs, 4.2~4.3µs, 5.4µs, 7.6~9.9µs였습니다. Jolt 단계 p95는 2.6µs, 2.7µs, 3.0~3.1µs, 3.8~4.5µs였습니다. 각 실행에서 프로세스 CPU 사용률은 약 100%였습니다. 이는 이 시험에서 프로세스가 CPU 한 코어를 거의 계속 썼다는 뜻입니다.

작업 집합은 실행마다 약 103.5~105MiB였지만 드론 수가 늘어도 일정하게 증가하지 않았습니다. 이 값에는 시뮬레이터 전체와 렌더러의 메모리가 포함되고, 운영체제가 회수한 메모리도 반영될 수 있어 드론 한 대당 메모리로 볼 수 없습니다. 측정은 Windows 11 x64, MSVC Release, i5-13600KF, RTX 3060 Ti 환경에서 이뤄졌으며 그래픽·통신·센서 부하는 드론 수 비교에 포함하지 않았습니다. [드론 수별 원자료](../../benchmarks/results/drone-scaling-release-2026-10-22.json)에는 실행별 Tick·Jolt 시간, CPU, 작업 집합과 측정 커밋을 기록했습니다. 이 결과는 현재 구현의 기준값이며, 다른 컴퓨터나 8대 초과 성능을 예측하거나 성능 개선을 입증하지 않습니다.

## 남은 확인 사항과 다음 작업

네이티브 그래픽 앱은 강체 모드로 실행하며 드론 Entity가 Jolt Body와 모터 상태를 보유합니다. 고정 Tick마다 비행 제어, 모터 응답, 로터 힘·토크·항력, Jolt 적분, 상태 복사를 순서대로 실행합니다. 헤드리스 실행은 기본적으로 운동학 기준선을 사용하지만, 시나리오 설정으로 강체 모드와 월드 바람을 선택할 수 있습니다. 바람을 포함한 Release 이륙·착륙 시나리오, 회전한 드론의 바람 방향 통합 시험, 실제 지형 충돌 시험, Viewer 스모크가 통과했습니다. X500 충돌 상자, OSM 건물 상자, 국립공원 시설물에서 가져온 충돌 상자의 접촉 경로를 확인했습니다. OSM 건물 높이는 3m 가정이고 시설물 바닥과 SRTM 격자 사이의 정합은 미검증입니다. WebAssembly는 운동학 경로로 지형과 시설물 화면을 그리지만 Jolt 충돌을 계산하지 않습니다. PX4 공개 메시와 제조사 CAD·실물의 치수 및 외관 비교, 제어 이득과 공력 값의 실기체 적합성, 건물의 실측 높이는 아직 확인하지 않았습니다. 현재 공력 모델은 PX4 설정에 있는 로터 횡방향 항력만 반영하며 기체 동체 항력은 계수 근거가 없어 포함하지 않았습니다. 질량·관성·모터 응답·로터 항력의 PX4 값은 기준 설정이고, 추력·반작용 토크 값은 공개 모터 표에서 계산한 추정치입니다. 어떤 값도 기체 전체의 실측 검증을 뜻하지 않습니다.

자유낙하 시험은 처음에 1초 뒤 위치를 약 5.1m로 예상했지만, Jolt는 각 단계에서 속도를 먼저 갱신한 뒤 위치를 움직입니다. 이 계산을 60단계에 적용하면 위치는 약 5.013m가 됩니다. 시험 기대값을 이 단계별 계산에 맞춰 고쳤습니다. 이 값은 Jolt의 적분 방식을 확인한 것이며 실제 기체의 낙하 결과를 뜻하지 않습니다. 첫 빌드 시도에서 `cassert`를 찾지 못한 문제는 C++ 개발 환경을 불러오지 않은 데서 생겼습니다. Visual Studio 개발 환경을 설정한 뒤 빌드에 성공했습니다.

다음 지도 작업은 시설물과 SRTM 높이 격자의 수직 정합을 측량 자료와 비교하고, 북한산 건물의 실제 높이를 확인하는 것입니다. 현재 높이 차이는 최대 약 30m지만, 격자 해상도와 높이 기준 중 어느 쪽이 얼마나 영향을 줬는지 알 수 없습니다. 국토정보플랫폼은 KNGeoid26도 목록에 올려 두었지만, 파일을 받으려면 로그인해야 합니다. 파일 형식과 이용 조건을 확인하기 전에는 모델을 저장소에 넣거나 변환에 사용하지 않습니다. 건물 높이 자료를 확인하기 전에는 3m 시연용 상자를 유지합니다. 별도로 공개 드론 메시의 크기와 배치를 제조사 CAD·실물 자료와 대조하고, 물리 상태의 자세가 센서·화면·기록 경로에서 같은 기준으로 쓰이는지 확인합니다. PX4 시뮬레이션 파라미터와 제조사 제원 사이의 차이도 유지하며, 실측 자료를 확보하기 전까지 물리 일치성을 주장하지 않습니다. 운동학 기준선은 비교 시험에 남겨 둡니다.
