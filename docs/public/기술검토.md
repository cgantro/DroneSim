# 기술 선택과 구현 방향

이 문서는 현재 상태와 다음 구현 순서를 정리합니다. 아래 선택은 조사 결과를 바탕으로 한 추천입니다. 아직 코드에 넣지 않은 기능은 구현된 것처럼 설명하지 않습니다.

## 지금 프로그램이 하는 일

- 드론 위치와 속도, 수평면에서 도는 방향각(Yaw)을 1/60초 간격으로 갱신합니다. 중력, 기울기, 모터, 추력, 공기 저항은 계산하지 않습니다.
- 그래픽 앱이 화면 표시와 함께 게임패드, UDP 명령, 기록·재생, 시나리오 시연, 성능 측정을 맡고 있습니다.
- 화면이 없는 시나리오 실행 경로와 OpenGL을 쓰는 화면 실행 경로가 따로 있습니다.
- Flecs 4.1.6은 연결했습니다. 드론과 EO 카메라를 각각 Entity로 만들고, 상태 데이터를 Component로 보관해 고정 Tick마다 System이 갱신합니다.
- Jolt 물리 월드는 별도로 있지만 기존 비행 시뮬레이션과 연결하지 않았습니다. 모터·추력 계산, 실제 기체 형상과 지형도 아직 없습니다.

다음 작업은 현재 화면과 명령 흐름을 한 번에 다시 만드는 일이 아닙니다. 모의 상태를 관리하는 작은 중심부를 만들고 기존 기능을 한 단계씩 연결합니다.

## 우선 선택

### Flecs는 객체 관리에만 사용

Flecs는 화면 객체와 시뮬레이션 객체를 식별하고 필요한 상태를 묶는 데 사용합니다. 드론 Entity에는 위치·속도·비행 상태와 제어 목표를, 카메라 Entity에는 센서 상태를 데이터 Component로 보관합니다. Flecs System이 이 데이터를 읽고 갱신합니다. 입력 처리, UDP 소켓, OpenGL 자원은 기존 C++ 객체로 뒀습니다.

Entity는 장면 속 대상의 번호입니다. Component는 그 대상에 붙이는 위치·속도 같은 데이터이고, System은 그 데이터를 읽거나 갱신하는 계산입니다.

현재는 상태와 제어 목표를 필요한 만큼만 나눴습니다. Flecs 기반 객체 관리의 첫 단계는 끝났지만, 여러 기체나 물리엔진을 연결하는 상태 구조까지 완성된 것은 아닙니다. 다음 단계에서 물리 Body와 모터 상태를 더할 때 같은 값을 두 곳에서 관리하지 않도록 주의합니다. Flecs 고급 파이프라인이나 병렬 실행은 넣지 않았습니다.

### 물리엔진은 Jolt로 시작

현재 프로그램은 자체 OpenGL 창과 화면 없는 실행 경로를 이미 갖고 있습니다. Jolt를 기존 구조에 연결하면 별도 시뮬레이터 없이 강체와 충돌을 계산할 수 있습니다. 작은 Jolt 물리 월드는 추가했지만 기존 비행 시뮬레이션에는 아직 연결하지 않았습니다. Gazebo는 쿼드콥터 모터 예제가 있다는 장점이 있지만 별도의 시뮬레이터 환경까지 함께 관리해야 하므로 우선순위에서 제외합니다.

Jolt가 드론을 대신 날려 주지는 않습니다. 작은 C++ 비행 모델에서 모터 회전속도에 따른 추력·토크를 계산하고, 그 힘을 Jolt의 강체(물리 계산 대상)에 적용합니다. Jolt가 계산한 위치·자세·속도를 물리 상태의 기준으로 삼습니다. ECS나 화면 코드가 같은 값을 다시 적분하지 않습니다.

공식 배포 목록에서 확인한 Flecs 4.1.6과 Jolt 5.6.0을 기준으로 합니다. Flecs 4.1.6은 Release 빌드와 화면 없는 실행, Viewer 스모크 시험에서 확인했습니다. Jolt 5.6.0으로 만든 물리 월드에서는 자유낙하, 힘과 토크, 바닥 충돌, 잘못된 크기 입력을 시험했습니다. Release 전체 빌드와 27개 CTest도 통과했습니다. 다만 이 물리 월드는 아직 드론 제어와 Flecs에 연결되지 않았습니다. 로터 추력, 모터 지연, 항력과 호버링은 아직 구현·검증하지 않았습니다.

### 첫 기체는 PX4 X500으로 검증

첫 실기체 기준 모델은 PX4 X500으로 진행합니다. 제조사 제원과 시각 자료가 있고, PX4 공개 시뮬레이션 모델에는 관성·로터 위치·모터 응답·추력 계수의 출발점이 있습니다. 모델에 들어 있는 숫자는 제조사 실측값이 아니라 시뮬레이터 설정값으로 표시합니다.

제조사 페이지는 무게 610g과 500mm 휠베이스를 안내하지만, PX4 모델의 기준 링크 질량은 2kg입니다. 두 숫자의 측정 범위가 같은지는 확인되지 않았으므로 서로 바꿔 쓰지 않습니다. 완성 기체의 질량·무게중심·관성 자료를 확보하기 전에는 X500과 물리적으로 일치한다고 주장하지 않습니다.

화면 모델은 공개된 PX4 자료를 우선 검토합니다. 저장소의 BSD 3-Clause 표시는 확인했지만, 개별 메시와 텍스처의 권리까지 자동으로 해결되는 것은 아닙니다. 제조사 CAD를 프로젝트에 복사하거나 배포하기 전에도 해당 파일의 이용·재배포 조건을 확인합니다.

### 첫 지형은 SRTM으로 만들고 건물은 별도 처리

시험 지역은 서울 북한산 남쪽의 작은 구역을 우선 후보로 둡니다. SRTM의 실제 고도 자료로 지형을 만들고, 같은 높이 자료에서 화면 형상과 충돌 지형을 함께 생성합니다. 격자 간격이 약 30m라 바위·도로 턱·건물 외벽은 재현하지 못합니다.

건물이 필요해지면 OpenStreetMap을 보조 자료로 검토합니다. 출처 표시와 ODbL 조건을 지키는 배포 방법을 먼저 정합니다. 그 전까지는 임의의 건물 높이를 실측 데이터처럼 넣지 않습니다.

## 앞으로 연결할 상태 흐름

```text
명령·시나리오 입력
  → 비행 제어와 모터 목표 계산
  → 로터 힘·토크 적용
  → Jolt 고정 시간 계산
  → Flecs 상태 갱신
  → 센서와 결과 판정
  → 화면용 자세 전달
```

최종 구조에서는 한 객체의 수명을 모의 중심부가 관리합니다. 드론을 만들거나 지울 때 Flecs Entity와 Jolt Body도 같은 경로에서 함께 만들고 정리해야 합니다. 현재는 이 연결이 아직 없습니다. Jolt 물리 월드는 한 스레드에서 계산하며, 다음 단계에서 드론 Entity와 물리 Body의 생성·삭제 경로를 묶습니다.

## 남은 확인 사항과 다음 작업

Flecs로 기존 비행 상태를 관리하고 있습니다. Jolt 물리 월드에서는 상자 모양 강체의 중력·힘·토크·바닥 접촉을 확인했습니다. Release 전체 빌드와 27개 CTest, Viewer 스모크도 통과했습니다. 두 모듈은 아직 드론 시뮬레이션에서 서로 연결되지 않았습니다. 드론 제어, 호버링, 차등 추력과 실제 비행은 검증하지 않았습니다. 실제 기체 형상과 지형도 아직 추가하지 않았습니다. PX4 시뮬레이션의 질량·관성·모터 계수는 실측값과 구분해 보관합니다.

자유낙하 시험은 처음에 1초 뒤 위치를 약 5.1m로 예상했지만, Jolt는 각 단계에서 속도를 먼저 갱신한 뒤 위치를 움직입니다. 이 계산을 60단계에 적용하면 위치는 약 5.013m가 됩니다. 시험 기대값을 이 단계별 계산에 맞춰 고쳤습니다. 이 값은 Jolt의 적분 방식을 확인한 것이며 실제 기체의 낙하 결과를 뜻하지 않습니다. 첫 빌드 시도에서 `cassert`를 찾지 못한 문제는 C++ 개발 환경을 불러오지 않은 데서 생겼고, 환경을 설정한 뒤에는 코드 변경 없이 빌드됐습니다.

X500 화면 자산의 이용 조건, 서울 시험 구역의 SRTM 높이 기준, OSM 자료의 배포 조건은 데이터를 추가하기 전에 확인합니다. 다음 구현에서는 모터 회전속도에 따른 로터 힘과 토크를 계산해 물리 월드에 적용하고, 호버링과 차등 추력 시험을 추가합니다. 그 뒤 기존 명령·시나리오 경로를 새 물리 상태에 연결합니다.
