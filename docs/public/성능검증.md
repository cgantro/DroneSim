# 성능 검증과 측정 결과

## 이 측정은 무엇을 알아보려는 건가요?

성능 측정은 실제 드론보다 빠르거나 물리적으로 정확하다는 것을 증명하기 위한 시험이 아닙니다. 현재 코드가 어떤 작업에서 시간을 쓰는지 살펴보고, 제한된 조건에서 변경 전후나 드론 수에 따른 차이를 확인하려고 진행했습니다.

| 알고 싶은 것 | 어떤 시험을 했나 | 결과를 어디까지 읽을 수 있나 |
| --- | --- | --- |
| 장면과 EO 카메라를 함께 켰을 때 화면이 멈추는가? | 보이는 창에서 앱 프레임 시간을 여러 번 기록했습니다. 별도로 EO 픽셀을 GPU에서 가져오는 호출도 조사했습니다. | 보이는 창 시험은 앱이 화면을 처리한 시간입니다. 픽셀 읽기 조사는 원인 후보를 좁히는 진단이며 원인을 확정하지 않습니다. |
| 드론이 늘거나 서로 가까워지면 계산이 얼마나 무거워지는가? | 화면을 끈 채 운동학·AirSim 강체 모의와 분리·밀집 배치를 시험했습니다. | 비행·충돌 계산의 비용을 비교합니다. 장면 그리기나 실제 지도 전체의 충돌 비용은 포함하지 않습니다. |
| 통신 장애 뒤 과제를 다시 배정하는 시나리오의 실행 시간은 편대 크기에 따라 어떻게 달라지는가? | 운동학 시나리오에서 4·16·64·256대 중 25%의 보고를 끊고 임무 재배정과 전체 실행 시간을 기록했습니다. | 통신·임무 갱신과 운동학 계산을 포함한 시나리오 전체 시간입니다. 조정기만 따로 재지 않았으며, AirSim 강체·충돌 회피·화면 그리기는 포함하지 않습니다. |
| 충돌 계산 변경이 시간을 줄였는가? | 같은 PC와 비슷한 입력으로 코드 변경 전후를 측정했습니다. | 해당 배치의 측정 구간에서 달라진 점을 봅니다. 모든 장면에서의 개선을 보장하지 않습니다. |
| 큰 편대에서 임무가 끝나고 메모리는 얼마나 늘어나는가? | 가상 임무 완료 여부와 프로세스 메모리를 기록했습니다. | 시나리오가 목표까지 진행되는지와 전체 프로세스의 대략적인 메모리 증가를 봅니다. 실제 임무 성공률이나 객체 하나의 크기는 알 수 없습니다. |

화면 시험은 앱의 프레임 처리를, 화면 없는 시험은 렌더링을 뺀 비행·충돌·임무 계산을 봅니다. 서로 다른 질문에 답하는 결과이므로 한쪽 수치로 다른 쪽 성능을 판단하지 않습니다.

## 측정 환경과 결과를 읽는 방법

2026년 10월 24일 Release 빌드에서 화면 시험과 화면 없는 전체 시험을 진행했습니다. 화면 시험은 리비전 `edd2a04d`에서 1280×720, VSync 끔, X500 한 대로 장면과 EO 카메라를 켜고 5초씩 세 번 측정했습니다. 전체 시험은 숨김 OpenGL 창에서 5초 동안 프레임을 기록한 뒤, 화면 렌더링을 제외한 드론 확장성과 협동 임무를 측정했습니다. 첫 전체 시험은 `c55c76de`, 임무 진행 시간을 기록한 시험은 `efa1ea8f`, 재할당 규모를 추가한 최신 시험은 `1c0c60dd-dirty`에서 실행했습니다. 최신 기록에는 실행 당시 작업 폴더에 Git이 관리하지 않는 자료가 남아 있어 `dirty` 표식이 붙었습니다. 세 시험 모두 NVIDIA GeForce RTX 3060 Ti와 OpenGL 3.3.0 NVIDIA 581.42를 사용했습니다. 원자료에는 CPU·메모리 용량과 운영체제 세부 정보가 없어 여기에도 적지 않았습니다.

실제 창의 프레임 결과는 사용자에게 보이는 화면 처리 지연을 살펴보고, 숨김 창의 기록은 렌더링 영향을 줄인 시뮬레이션 계산을 봅니다. 측정 대상과 코드 리비전이 다르므로 두 결과를 합치거나 직접 비교하지 않습니다. 숨김 창의 5초 프레임 기록 역시 실제 모니터에 표시된 시간이나 사용자 입력 지연을 뜻하지 않습니다.

- **앱 프레임 시간**은 앱이 한 화면 프레임을 처리하는 데 걸린 시간입니다. 16.67ms는 60Hz 화면의 한 프레임 예산을 가늠할 때 쓰는 기준입니다. VSync를 끈 이번 시험에서 모니터가 그 시간 안에 화면을 보여 줬다는 뜻은 아닙니다.
- **패널 구성 시간**은 ImGui 프레임을 시작한 뒤 장면·카메라·상태 패널을 구성하는 구간입니다. 앱 프레임 안의 하위 구간이며, 장면과 카메라를 실제로 그리는 호출도 포함될 수 있어 다른 구간과 시간을 더하면 안 됩니다.
- **Tick 시간**은 비행 상태를 1/60초 진행하는 계산 한 번에 걸린 시간입니다. 화면 프레임 시간과 별도로 봅니다.
- **p95**는 측정 표본의 95%가 그 시간 안에 처리됐다는 뜻입니다. 드문 긴 지연을 놓치지 않도록 p99와 최댓값도 함께 봅니다.
- **실시간 배수(RTF)**는 실제 경과 시간에 비해 모의 시간이 얼마나 진행됐는지를 나타냅니다. 1배면 실제 시간과 같은 속도입니다.
- 서로 다른 코드 리비전, 실행 시점, 장면과 부하의 숫자는 직접 비교하지 않습니다. 원자료는 [측정 결과 찾아보기](../../benchmarks/results/README.md)에서 찾을 수 있습니다.

## 실제 창에서 화면이 멈추는지 확인

**이 시험을 한 이유:** 평균 FPS 하나로는 대부분 빠른 화면 속에 섞인 드문 멈춤을 찾기 어렵습니다. 그래서 장면과 EO 카메라를 함께 켜고, 보통 프레임과 유난히 오래 걸린 프레임을 따로 확인했습니다. 여기서 잰 값은 앱 내부 처리 시간이며, 모니터에 실제로 표시된 시각이나 조종 입력부터 화면까지 걸린 시간은 아닙니다.

| 실행 | 프레임 수 | FPS | 앱 프레임 p50 | p95 | p99 | 최댓값 | 16.67ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,359 | 271.69 | 2.411ms | 7.434ms | 11.868ms | 201.880ms | 7 |
| 2 | 1,644 | 328.52 | 2.404ms | 5.715ms | 7.669ms | 39.101ms | 3 |
| 3 | 1,579 | 315.80 | 2.411ms | 6.719ms | 8.215ms | 13.348ms | 0 |

세 번의 p95 중앙값은 6.719ms, p99 중앙값은 8.215ms였습니다. 16.67ms를 넘은 프레임은 각 실행에서 7개, 3개, 0개였습니다. 첫 실행의 최댓값은 201.880ms였고, 같은 프레임의 패널 구성 구간은 200.620ms였습니다. 이 구간에서는 장면·카메라 렌더링 호출이 기록되지 않았습니다. 다만 계측은 패널 안의 개별 ImGui 작업을 더 나누지 않으므로, 지연이 난 세부 동작이나 근본 원인은 아직 확인되지 않았습니다. p95·p99가 60Hz 한 프레임 기준보다 낮더라도 이런 긴 프레임이 있었으므로, 짧은 시험의 평균적인 처리 속도만으로 화면이 늘 매끄럽다고 말할 수 없습니다. 측정은 앱 내부 처리 시간이며 모니터 표시 완료 시각이나 조종 입력부터 화면까지의 지연은 포함하지 않습니다.

각 실행은 1초 준비 뒤 5초 기록했습니다. 지형은 약 18.8×23.7km이며, 장면에는 건물 상자 17개와 공원 시설물 49개가 있었습니다. EO 픽셀은 3칸 비동기 PBO 버퍼로 읽었습니다. 실행별 원자료는 [세 번의 화면 측정과 설정](../../benchmarks/results/archive/aerosimlab-visible-benchmark-release-2026-10-24-edd2a04d.json)에 있습니다.

FPS는 화면에 표시된 주사율이나 사용자가 느끼는 입력 지연을 뜻하지 않습니다. 이번 측정은 창을 보이게 하고 자동 시연을 실행했지만, 사용자 입력 지연이나 장시간 사용 중의 끊김은 따로 검증하지 않았습니다.

## 드론 수와 배치가 계산 비용에 미치는 영향

**이 시험을 한 이유:** 렌더링 비용을 빼고도 운동학과 AirSim 강체 모의를 유지했을 때 드론 수와 배치가 계산 시간에 어떤 영향을 주는지 보기 위해서입니다. 멀리 떨어진 편대와 가까이 모인 편대, 협동 임무를 따로 실행했습니다. 실행이 끝났는지와 Tick 시간을 함께 기록했지만, 이 결과만으로 화면이 있는 시뮬레이터의 성능이나 실제 지도 환경의 처리 가능 규모를 판단할 수는 없습니다.

독립 비행과 밀집 배치 시험은 각 조건에서 준비 Tick 120회 뒤 최대 30,000 Tick을 실행하고, 세 번 반복했습니다. 표의 Tick p95와 실시간 배수는 세 실행 결과의 중앙값입니다. 강체 1,024대는 30초 실행 제한에 걸려 24,000 Tick까지 한 번만 실행됐습니다. 아래 p95는 각 Tick의 계산 시간을 뜻하며 전체 30,000회 실행 시간과는 다른 값입니다.

| 모의 방식과 부하 | 드론 수 | 반복과 작업량 | Tick p95 중앙값 | RTF 중앙값 | 결과 |
| --- | ---: | --- | ---: | ---: | --- |
| 운동학, 서로 떨어진 배치 | 1,024 | 30,000 Tick씩 3회 | 11.8µs | 약 1,934배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 512 | 30,000 Tick씩 3회 | 787.9µs | 약 28.5배 | 세 번 모두 완료 |
| AirSim 강체, 0.55m 간격 배치 | 256 | 30,000 Tick씩 3회 | 899.3µs | 약 24.1배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 1,024 | 24,000 Tick까지 1회 | 1,676.6µs | 약 13.2배 | 30초 제한에 걸린 부분 실행 |

운동학 1,024대와 강체 512대까지는 각 조건에서 세 번 모두 목표 Tick을 마쳤습니다. 강체 1,024대는 한 번뿐인 부분 실행이므로 완료 가능한 규모로 해석하면 안 됩니다. 0.55m 간격의 강체 256대 시험도 세 번 모두 완료했습니다. 각 실행에서 16.67ms를 넘은 Tick은 없었습니다. 다만 이 드론 확장성 시험은 실제 지도 지형과 건물·시설물 충돌을 포함하지 않아, 시뮬레이터 전체 장면에서의 처리 규모를 뜻하지 않습니다.

대규모 임무 시험은 시작 전에 각 드론에 조사 목표 하나를 지정합니다. 따라서 편대가 커질 때 드론별 비행, 목표 도달, 완료 판정에 드는 비용을 봅니다. 조정기가 통신 장애 뒤 과제를 다시 나누는 비용은 아래의 4대 협동 시험과 재할당 규모 시험에서 따로 확인합니다.

운동학 1,024대는 300 Tick, AirSim 강체 128대는 480 Tick을 수행해 각 크기별 세 번의 실행에서 모두 임무를 마쳤습니다. 컴퓨터가 시나리오를 계산한 벽시계 시간 중앙값은 각각 29.54ms와 73.22ms였습니다. 이와 별도로 최신 JSON은 `mission_completion_time_seconds`에 **첫 임무가 실제로 시작된 때부터 마지막 임무가 끝날 때까지 시뮬레이션 안에서 흐른 시간**을 기록합니다. 이 값의 중앙값은 운동학에서 0.083초, AirSim 강체에서 1.10초였습니다. 이 시험의 각 목표는 출발점에서 0.5m 떨어져 있으므로, 이 시간은 긴 실제 비행 임무의 소요 시간을 뜻하지 않습니다. 두 시간 값은 서로 다른 것을 잽니다. 전자는 이 PC가 시나리오를 계산하는 데 걸린 시간이고, 후자는 시뮬레이션 속 임무가 진행된 시간입니다. 이 결과는 미리 할당한 목표의 비행과 완료 판정만 확인하며, 실제 UDP 통신 장애나 편대 충돌 회피 성능은 검증하지 않습니다.

### 통신 단절과 임무 재배정을 함께 실행하면

**이 시험을 한 이유:** 드론 수만 늘리는 확장성 시험은 통신 장애 뒤 임무를 다시 나누는 비용과 실제 최소 간격을 보여 주지 못합니다. 그래서 네 대가 조사 임무를 수행하다 한 대의 상태 보고가 끊기는 대표 시나리오를 운동학과 AirSim 강체 모드에서 각각 반복했습니다. 매번 준비 실행 1회 뒤 같은 입력으로 3회 측정했고, 네 구역의 완료 여부, 통신 상태를 확인할 수 없는 기체 수, 실제 최소 중심 간 거리를 함께 기록했습니다.

| 모의 방식 | Tick 수 | 반복 결과 | 재배정된 구역 수 | 미확정 드론 | 네 구역 완료 | 최소 중심 간 거리 | PC 실행 시간 중앙값 | 모의 임무 시간 중앙값 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 운동학 | 320 | 3회 모두 통과 | 2 | 1 | 100% | 3.417m | 2.14ms | 3.017초 |
| AirSim 강체 | 1,800 | 3회 모두 통과 | 1 | 1 | 100% | 2.221m | 13.97ms | 9.767초 |

두 방식 모두 세 번의 실행에서 네 구역을 모두 완료했고, 최소 간격도 통과 기준인 1m를 넘었습니다. 통신이 끊긴 드론은 한 대로 남았으며, 확인할 수 없는 임무 상태를 성공이나 실패로 확정하지 않았습니다. 재배정 구역 수와 모의 임무 시간은 모의 방식마다 달랐습니다. 표의 PC 실행 시간은 시나리오 계산에 걸린 벽시계 시간이고, 모의 임무 시간은 첫 임무 시작부터 마지막 임무 완료까지 시뮬레이션 안에서 흐른 시간입니다. 특히 강체 시험은 운동학보다 Tick 수가 많으므로 PC 실행 시간을 두 물리 방식의 처리 속도 비교로 읽으면 안 됩니다. 이 측정은 시나리오 계산이며 실제 UDP 장애, 실제 비행제어기의 통신 상실 동작, 기체 크기를 반영한 충돌 보증을 확인하지 않습니다. 반복별 설정과 수치는 [전체 측정 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에 있습니다.

### 배터리 부족과 통신 단절이 함께 생기면

**이 시험을 한 이유:** 통신 복구 시험만으로는 배터리가 부족한 기체의 귀환 판단이 임무 재배정과 함께 동작하는지 알 수 없습니다. 이미 준비된 통합 시나리오를 운동학과 AirSim 강체 방식으로 각각 실행해, 임무 완료와 저전력 귀환, 에너지 사용량을 확인했습니다. 각 방식은 준비 실행 1회 뒤 같은 입력으로 3회 측정했습니다.

| 모의 방식 | Tick 수 | 반복 결과 | 완료 과제 | 저전력 귀환 | 모의 임무 시간 중앙값 | 계산 시간 중앙값 | 총 에너지 사용량 중앙값 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 운동학 | 720 | 3회 모두 통과 | 3/3 | 1대 | 3.867초 | 2.169ms | 0.779Wh |
| AirSim 강체 | 1,800 | 3회 모두 통과 | 3/3 | 1대 | 3.600초 | 11.164ms | 1.996Wh |

두 방식 모두 세 번의 측정에서 세 과제를 완료했고, 저전력 귀환은 한 대에서 발생했습니다. 계산 시간은 이 PC에서 시나리오 전체를 실행한 시간이고, 모의 임무 시간은 시뮬레이션에서 과제가 진행된 시간입니다. Tick 수와 물리 계산이 다르므로 두 행의 계산 시간을 물리 엔진끼리의 속도 비교로 해석하면 안 됩니다. 에너지 값은 이 시나리오의 배터리 모델이 계산한 소모량이며 실제 기체의 전력 계측값이 아닙니다. 이 입력은 충돌 예측·회피를 활성화하지 않아 충돌 이벤트가 0이고 최소 거리 값도 기록되지 않았습니다. 따라서 이 결과는 충돌 안전성이나 실제 통신 장애 대응을 검증하지 않습니다. 실행별 기록과 설정은 [배터리·통신 장애 통합 측정 자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-483b3c49-dirty.json)에 있습니다. 벤치마크는 실행 당시 리비전을 `483b3c49-dirty`로 표시했습니다. 현재 Git 작업 폴더는 깨끗하지만, 이 결과에는 실행 시점에 작업 폴더가 깨끗하지 않았다는 표식이 남아 있어 그 상태를 그대로 공개합니다.

### 편대가 커질 때 임무 재할당 계산은 얼마나 늘어나나?

**이 시험을 한 이유:** 네 대 대표 시나리오는 통신 단절 뒤 임무가 복구되는지와 안전거리를 확인하지만, 더 많은 드론을 관리할 때 조정기의 계산량이 어떻게 달라지는지는 보여 주지 않습니다. 이를 확인하려고 운동학 시나리오의 드론 수를 늘리고, 전체의 4분의 1에서 임무 시작 직전부터 상태 보고가 끊기게 했습니다. 장애 대상은 편대 전체에 고르게 배치했습니다. 각 드론에는 시작 전에 조사 과제 하나를 미리 배정했습니다.

한 Tick은 1/60초입니다. 보고 단절은 임무 시작 5 Tick 전에 발생하고, 3 Tick 동안 Heartbeat가 돌아오지 않으면 해당 드론의 상태를 미확정으로 처리합니다. 과제는 임무 시작 Tick 90에 시작하며, 모두 끝내야 하는 기한은 Tick 690입니다. 각 과제의 목표는 출발점에서 0.5m 떨어져 있습니다. 드론 수별로 준비 1회와 측정 3회를 실행했습니다.

| 드론 수 | 상태 보고 단절 | 재할당 횟수 중앙값 | 임무 완료율 | 모의 임무 시간 | 계산 시간 범위 | 계산 시간 중앙값 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 1대 | 1회 | 100% | 1.083초 | 2.055–2.172ms | 2.172ms |
| 16 | 4대 | 4회 | 100% | 1.083초 | 2.773–2.874ms | 2.783ms |
| 64 | 16대 | 16회 | 100% | 1.083초 | 7.815–8.005ms | 7.970ms |
| 256 | 64대 | 64회 | 100% | 1.083초 | 65.540–67.518ms | 65.554ms |

네 규모 모두 세 번씩 임무를 완료했습니다. 미확정 상태로 남은 드론 수와 과제 재배정 횟수는 각각 장애 수와 같았습니다. 계산 시간은 PC에서 시나리오를 실행하는 데 걸린 전체 시간이며, 통신 상태 갱신·임무 처리·운동학 Tick을 포함합니다. 조정기만 따로 잰 시간이 아니고, 모의 임무 시간과도 다릅니다. 드론이 늘수록 계산 시간도 증가했지만, 이 네 점만으로 알고리즘의 복잡도나 다른 PC에서의 처리 한계를 단정할 수는 없습니다. 이 시험은 운동학과 단순한 0.5m 목표 이동을 사용하므로 AirSim 강체 계산, 충돌 회피, 렌더링, 실제 통신 장애의 비용은 포함하지 않습니다. 실행 설정과 반복별 원자료는 [재할당 규모가 포함된 Release 측정](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에서 확인할 수 있습니다.

화면 없는 전체 시험의 배터리·통신 통합 시나리오 결과는 [최신 통합 측정 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-483b3c49-dirty.json)에 있습니다. 재할당 규모와 네 대 통신 장애의 이전 기준은 [전체 시험 자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에서 확인할 수 있습니다. 그보다 앞선 기록은 [이전 전체 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-efa1ea8f.json), [첫 전체 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-c55c76de.json), [화면 표시 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-edd2a04d.json)에 보관했습니다. 전체 드론 수별 반복 기록과 개별 계산 구간은 JSON에 보존했습니다.

### 드론 수가 늘 때 프로세스 메모리는 얼마나 바뀌나?

**이 시험을 한 이유:** 드론 수가 늘 때 프로세스 전체가 추가로 사용하는 메모리의 대략적인 규모를 비교하기 위해서입니다. 이 값은 ECS Entity나 강체 객체 하나의 정확한 크기를 구하는 측정은 아닙니다.

이번 실행의 메모리 증가량은 모델을 추가하는 과정의 별도 표본에서 확인했습니다. 1대와 1,024대일 때 프로세스 `Private Bytes` 차이를 비교하고, 새로 추가한 1,023대로 나눴습니다. 아래 값은 프로세스 전체의 차이를 단순히 나눈 값입니다.

| 모의 방식 | 1대에서 1,024대까지 늘어난 프로세스 메모리 | 추가 드론 1대당 단순 나눗값 |
| --- | ---: | ---: |
| 운동학 | 724,992B | 약 709B |
| AirSim 강체 | 8,192,000B | 약 7.8KiB |

각 방식은 한 번만 측정했습니다. 프로세스 메모리에는 드론 상태뿐 아니라 컨테이너 용량 증가, 메모리 할당기, 물리 엔진의 공유·내부 자료가 함께 들어갑니다. 따라서 이 값으로 객체 하나의 메모리 크기나 반복 실행의 평균을 말할 수는 없습니다. 표본과 실행 설정은 [전체 Release 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-edd2a04d.json)에 있습니다.

## 충돌 후보 정렬을 바꾼 효과

**목적:** 드론이 서로 앞지르지 않았는데도 매 Tick 전체 정렬을 다시 하는 비용을 줄이면, 넓은 배치와 밀집 배치의 물리 계산이 실제로 빨라지는지 확인했습니다.

변경 전 `94c39b94`와 변경 후 `69ecab93`를 같은 Windows Release 환경에서 측정했습니다. 각 조건은 준비 Tick 120회 뒤 30,000 Tick씩 세 번 실행했습니다. 분리 배치는 드론 간격 2.5m, 밀집 배치는 정사각 격자 간격 0.55m였습니다. 아래 값은 각 반복에서 구한 p95의 중앙값입니다.

| 배치와 드론 수 | 물리 단계 p95 전 → 후 | 접촉 후보 생성 p95 전 → 후 | 결과 해석 |
| --- | ---: | ---: | --- |
| 분리, 128대 | 190.5 → 189.7µs | 125.0 → 129.3µs | 차이가 작아 개선을 확인했다고 보기 어려움 |
| 분리, 256대 | 381.0 → 348.0µs | 247.6 → 232.8µs | 각각 8.7%, 6.0% 감소 |
| 분리, 512대 | 745.3 → 677.7µs | 470.5 → 445.6µs | 각각 9.1%, 5.3% 감소 |
| 밀집, 128대 | 474.0 → 411.9µs | 403.0 → 350.7µs | 각각 13.1%, 13.0% 감소 |
| 밀집, 256대 | 833.0 → 796.9µs | 705.1 → 676.4µs | 각각 4.3%, 4.1% 감소 |

접촉 후보 생성 구간에는 정렬뿐 아니라 충돌 상자 좌표 갱신과 후보 쌍 검사가 포함됩니다. 따라서 표의 전체 시간 감소를 정렬 비용 하나의 절감으로 볼 수는 없습니다. 이 드론 전용 시험에는 지형 격자와 정적 장애물이 없으므로, 실제 지도 장면에서의 충돌 비용은 별개입니다. 전체 실행 기록은 [변경 전](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-94c39b94-before-sort-reuse.json)과 [변경 후](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-69ecab93-after-sort-reuse.json)에 있습니다.

## 긴 프레임 원인 조사 기록

EO 픽셀 읽기, OpenGL 호출과 CPU 표본을 나눠 살펴본 조사는 별도 문제 해결 기록에 모았습니다. 그 조사는 **긴 프레임의 원인 후보를 좁히는 과정**이지, 최신 Release의 대표 성능 기준선이 아닙니다. [EO 카메라를 켜면 화면이 가끔 멈춘 문제](문제해결/화면-프레임-지연.md)에서 확인된 사실과 미확정 원인을 읽을 수 있습니다. 화면 없는 다중 드론 충돌 시험의 이전 단계는 [충돌 계산 성능 기록](문제해결/다중드론-충돌-성능.md)에 있습니다.
