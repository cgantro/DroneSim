# 성능 검증과 측정 결과

## 이 측정은 무엇을 알아보려는 건가요?

성능 측정은 실제 드론보다 빠르거나 물리적으로 정확하다는 것을 증명하기 위한 시험이 아닙니다. 현재 코드가 어떤 작업에서 시간을 쓰는지 살펴보고, 제한된 조건에서 변경 전후나 드론 수에 따른 차이를 확인하려고 진행했습니다.

| 알고 싶은 것 | 어떤 시험을 했나 | 결과를 어디까지 읽을 수 있나 |
| --- | --- | --- |
| 장면과 EO 카메라를 함께 켰을 때 화면이 멈추는가? | 보이는 창에서 앱 프레임 시간을 여러 번 기록했습니다. 별도로 EO 픽셀을 GPU에서 가져오는 호출도 조사했습니다. | 보이는 창 시험은 앱이 화면을 처리한 시간입니다. 픽셀 읽기 조사는 원인 후보를 좁히는 진단이며 원인을 확정하지 않습니다. |
| 드론이 늘거나 서로 가까워지면 계산이 얼마나 무거워지는가? | 화면을 끈 채 운동학·AirSim 강체 모의와 분리·밀집 배치를 시험했습니다. | 비행·충돌 계산의 비용을 비교합니다. 장면 그리기나 실제 지도 전체의 충돌 비용은 포함하지 않습니다. |
| 충돌 계산 변경이 시간을 줄였는가? | 같은 PC와 비슷한 입력으로 코드 변경 전후를 측정했습니다. | 해당 배치의 측정 구간에서 달라진 점을 봅니다. 모든 장면에서의 개선을 보장하지 않습니다. |
| 큰 편대에서 임무가 끝나고 메모리는 얼마나 늘어나는가? | 가상 임무 완료 여부와 프로세스 메모리를 기록했습니다. | 시나리오가 목표까지 진행되는지와 전체 프로세스의 대략적인 메모리 증가를 봅니다. 실제 임무 성공률이나 객체 하나의 크기는 알 수 없습니다. |

화면 시험은 앱의 프레임 처리를, 화면 없는 시험은 렌더링을 뺀 비행·충돌·임무 계산을 봅니다. 서로 다른 질문에 답하는 결과이므로 한쪽 수치로 다른 쪽 성능을 판단하지 않습니다.

## 측정 환경과 결과를 읽는 방법

2026년 10월 23일 Release 측정은 Windows 11 Pro, Intel Core i5-13600KF, 메모리 31.8GiB, NVIDIA GeForce RTX 3060 Ti에서 수행했습니다. 최신 기준선의 소스 리비전은 `69ecab93`입니다. 보이는 창은 1280×720, VSync 끔, X500 한 대, 지형·건물·시설물과 EO 카메라를 켠 상태였습니다. 화면 없는 시험은 그래픽 렌더링을 실행하지 않았습니다.

- **앱 프레임 시간**은 앱이 한 화면 프레임을 처리하는 데 걸린 시간입니다. 16.67ms는 60Hz 화면의 한 프레임 예산을 가늠할 때 쓰는 기준입니다. VSync를 끈 이번 시험에서 모니터가 그 시간 안에 화면을 보여 줬다는 뜻은 아닙니다.
- **Tick 시간**은 비행 상태를 1/60초 진행하는 계산 한 번에 걸린 시간입니다. 화면 프레임 시간과 별도로 봅니다.
- **p95**는 측정 표본의 95%가 그 시간 안에 처리됐다는 뜻입니다. 드문 긴 지연을 놓치지 않도록 p99와 최댓값도 함께 봅니다.
- **실시간 배수(RTF)**는 실제 경과 시간에 비해 모의 시간이 얼마나 진행됐는지를 나타냅니다. 1배면 실제 시간과 같은 속도입니다.
- 서로 다른 코드 리비전, 실행 시점, 장면과 부하의 숫자는 직접 비교하지 않습니다. 원자료는 [측정 결과 찾아보기](../../benchmarks/results/README.md)에서 찾을 수 있습니다.

## 실제 창에서 화면이 멈추는지 확인

**이 시험을 한 이유:** 평균 FPS 하나로는 대부분 빠른 화면 속에 섞인 드문 멈춤을 찾기 어렵습니다. 그래서 장면과 EO 카메라를 함께 켜고, 보통 프레임과 유난히 오래 걸린 프레임을 따로 확인했습니다. 여기서 잰 값은 앱 내부 처리 시간이며, 모니터에 실제로 표시된 시각이나 조종 입력부터 화면까지 걸린 시간은 아닙니다.

| 실행 | 프레임 수 | FPS | 앱 프레임 p50 | p95 | p99 | 최댓값 | 16.67ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,767 | 353.28 | 2.403ms | 5.041ms | 5.513ms | 14.639ms | 0 |
| 2 | 1,750 | 349.92 | 2.403ms | 5.175ms | 6.139ms | 17.353ms | 1 |
| 3 | 1,815 | 362.77 | 2.402ms | 4.577ms | 5.225ms | 12.254ms | 0 |

세 번의 p95 중앙값은 5.041ms, p99 중앙값은 5.513ms였습니다. 16.67ms를 넘은 프레임은 세 번 중 한 번에 1개 있었습니다. 짧은 시험의 대부분 프레임은 예산 안에 있었지만, 이 결과만으로 장시간 화면이 매끄럽다고 보장할 수는 없습니다. 측정은 앱 처리 시간이며 모니터 표시 완료 시각이나 조종 입력부터 화면까지의 지연은 포함하지 않습니다.

각 실행은 1초 준비 뒤 5초 기록했습니다. 지형은 약 18.8×23.7km이며, 장면에는 건물 상자 17개와 공원 시설물 49개가 있었습니다. EO 픽셀은 3칸 비동기 PBO 버퍼로 읽었습니다. 실행별 원자료는 [1회차](../../benchmarks/results/archive/aerosimlab-visible-warmup-repeat-release-2026-10-23-69ecab93-run-1.json), [2회차](../../benchmarks/results/archive/aerosimlab-visible-warmup-repeat-release-2026-10-23-69ecab93-run-2.json), [3회차](../../benchmarks/results/archive/aerosimlab-visible-warmup-repeat-release-2026-10-23-69ecab93-run-3.json)입니다.

이전 리비전 `aac03875`의 보이는 창 시험은 FPS 중앙값 414.21, p95 3.704ms였습니다. 코드 리비전과 측정 시점이 다르고 PC 부하도 통제하지 않았으므로 이번 값과 비교해 정렬 변경이 화면 성능을 낮췄다고 단정할 수 없습니다. 이전 원자료는 [측정 결과 안내](../../benchmarks/results/README.md)에 있습니다.

## 드론 수와 배치가 계산 비용에 미치는 영향

**이 시험을 한 이유:** 렌더링 비용을 빼고도 운동학과 AirSim 강체 모의를 유지했을 때 드론 수와 배치가 계산 시간에 어떤 영향을 주는지 보기 위해서입니다. 멀리 떨어진 편대와 가까이 모인 편대, 협동 임무를 따로 실행했습니다. 실행이 끝났는지와 Tick 시간을 함께 기록했지만, 이 결과만으로 화면이 있는 시뮬레이터의 성능이나 실제 지도 환경의 처리 가능 규모를 판단할 수는 없습니다.

독립 비행과 밀집 배치 시험은 각 조건에서 준비 Tick 120회 뒤 최대 30,000 Tick을 실행하고, 세 번 반복했습니다. 표의 Tick p95와 실시간 배수는 세 실행 결과의 중앙값입니다. 강체 1,024대는 실행 제한에 걸려 한 번만 부분 실행됐습니다.

| 모의 방식과 부하 | 드론 수 | 반복과 작업량 | Tick p95 중앙값 | RTF 중앙값 | 결과 |
| --- | ---: | --- | ---: | ---: | --- |
| 운동학, 서로 떨어진 배치 | 1,024 | 30,000 Tick씩 3회 | 10.1µs | 약 2,116배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 512 | 30,000 Tick씩 3회 | 894.5µs | 약 24.6배 | 세 번 모두 완료, 16.67ms 초과 없음 |
| AirSim 강체, 0.55m 간격 배치 | 256 | 30,000 Tick씩 3회 | 904.2µs | 24.11배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 1,024 | 20,000 Tick까지 1회 | — | — | 30초 제한에 걸린 부분 실행 |

1,024대 강체 시험은 한 번의 부분 실행이므로 완료된 규모처럼 말할 수 없습니다. 512대 강체 결과도 실제 지도 지형과 건물·시설물 충돌을 포함하지 않습니다. 이 결과는 지정된 배치에서의 드론 간 계산 비용을 보여 줄 뿐, 실제 장면 전체가 같은 속도로 동작한다는 뜻은 아닙니다.

협동 임무는 드론이 많은 상태에서도 임무 목표와 완료 판정까지 진행되는지 확인합니다. 운동학 1,024대는 300 Tick, AirSim 강체 128대는 480 Tick을 수행해 각각 세 번 모두 임무를 마쳤습니다. 중앙 실행 시간은 각각 14.75ms와 79.43ms였습니다. 이는 시뮬레이터 안의 임무 판정 결과이며 실제 UDP 통신 장애나 편대 충돌 회피 성능을 검증하지 않습니다.

화면 없는 최신 Release 전체 결과는 [원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-69ecab93-after-sort-reuse.json)에 있습니다. 예전 기준선은 [결과 목록](../../benchmarks/results/README.md)에서 이전 Release 자료로 확인할 수 있습니다.

### 드론 수가 늘 때 프로세스 메모리는 얼마나 바뀌나?

**이 시험을 한 이유:** 드론 수가 늘 때 프로세스 전체가 추가로 사용하는 메모리의 대략적인 규모를 비교하기 위해서입니다. 이 값은 ECS Entity나 강체 객체 하나의 정확한 크기를 구하는 측정은 아닙니다.

한 번의 Release 실행 안에서 드론을 1대에서 1,024대까지 순서대로 추가했습니다. 1대일 때의 프로세스 `Private Bytes`를 기준으로 1,024대 시점까지 증가한 양을 구하고, 새로 추가한 1,023대로 나눴습니다.

| 모의 방식 | 1대에서 1,024대까지 늘어난 프로세스 메모리 | 추가 드론 1대당 단순 나눗값 |
| --- | ---: | ---: |
| 운동학 | 393,216B | 약 384B |
| AirSim 강체 | 8,331,264B | 약 8.0KiB |

각 방식은 한 번만 측정했습니다. 프로세스 메모리에는 드론 상태뿐 아니라 컨테이너 용량 증가, 메모리 할당기, 물리 엔진의 공유·내부 자료가 함께 들어갑니다. 따라서 이 값으로 객체 하나의 메모리 크기나 반복 실행의 평균을 말할 수는 없습니다. 표본과 실행 설정은 [전체 Release 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-69ecab93-after-sort-reuse.json)에 있습니다.

## 충돌 후보 정렬을 바꾼 효과

**목적:** 드론이 서로 앞지르지 않았는데도 매 Tick 전체 정렬을 다시 하는 비용을 줄이면, 넓은 배치와 밀집 배치의 물리 계산이 실제로 빨라지는지 확인했습니다.

변경 전 `94c39b94`와 변경 후 `69ecab93`를 같은 Windows Release 환경에서 측정했습니다. 각 조건은 준비 Tick 120회 뒤 30,000 Tick씩 세 번 실행했습니다. 분리 배치는 드론 간격 2.5m, 밀집 배치는 정사각 격자 간격 0.55m였습니다. 아래 값은 각 반복에서 구한 p95의 중앙값입니다.

| 배치와 드론 수 | 물리 단계 p95 전 → 후 | 접촉 후보 생성 p95 전 → 후 | 결과 해석 |
| --- | ---: | ---: | --- |
| 분리, 128대 | 190.5 → 189.7µs | 125.0 → 129.3µs | 차이가 작아 개선을 확인했다고 보기 어려움 |
| 분리, 256대 | 381.0 → 348.0µs | 247.6 → 232.8µs | 각각 8.7%, 6.0% 감소 |
| 분리, 512대 | 745.3 → 677.7µs | 470.5 → 445.6µs | 각각 9.1%, 5.3% 감소 |
| 밀집, 128대 | 474.0 → 411.9µs | 403.0 → 350.7µs | 각각 13.1%, 13.0% 감소 |
| 밀집, 256대 | 833.0 → 796.9µs | 705.1 → 676.4µs | 각각 4.3%, 4.1% 감소 |

접촉 후보 생성 구간에는 정렬뿐 아니라 충돌 상자 좌표 갱신과 후보 쌍 검사가 포함됩니다. 따라서 표의 전체 시간 감소를 정렬 비용 하나의 절감으로 볼 수는 없습니다. 이 드론 전용 시험에는 지형 격자와 정적 장애물이 없으므로, 실제 지도 장면에서의 충돌 비용은 별개입니다. 전체 실행 기록은 [변경 전](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-94c39b94-before-sort-reuse.json)과 [변경 후](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-69ecab93-after-sort-reuse.json)에 있습니다.

## 긴 프레임 원인 조사 기록

EO 픽셀 읽기, OpenGL 호출과 CPU 표본을 나눠 살펴본 조사는 별도 문제 해결 기록에 모았습니다. 그 조사는 **긴 프레임의 원인 후보를 좁히는 과정**이지, 최신 Release의 대표 성능 기준선이 아닙니다. [EO 카메라를 켜면 화면이 가끔 멈춘 문제](문제해결/화면-프레임-지연.md)에서 확인된 사실과 미확정 원인을 읽을 수 있습니다. 화면 없는 다중 드론 충돌 시험의 이전 단계는 [충돌 계산 성능 기록](문제해결/다중드론-충돌-성능.md)에 있습니다.
