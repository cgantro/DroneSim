# 성능 검증과 측정 결과

## 이 측정은 무엇을 알아보려는 건가요?

이 측정은 프로그램이 화면과 시뮬레이션 계산에 쓰는 시간을 살펴봅니다. 같은 조건에서 코드를 바꾸거나 드론 수를 늘렸을 때 달라지는 점도 확인합니다.

| 알고 싶은 것 | 어떤 시험을 했나 | 결과를 어디까지 읽을 수 있나 |
| --- | --- | --- |
| 장면과 EO 카메라를 함께 켰을 때 화면이 멈추는가? | 보이는 창에서 앱 프레임 시간을 여러 번 기록했습니다. 별도로 EO 픽셀을 GPU에서 가져오는 호출도 조사했습니다. | 보이는 창 시험은 앱이 화면을 처리한 시간입니다. 픽셀 읽기 조사는 원인 후보를 좁히는 진단이며 원인을 확정하지 않습니다. |
| 드론이 늘거나 서로 가까워지면 계산이 얼마나 무거워지는가? | 화면을 끈 채 운동학·AirSim 강체 모의와 분리·밀집 배치를 시험했습니다. | 비행·충돌 계산의 비용을 비교합니다. 장면 그리기나 실제 지도 전체의 충돌 비용은 포함하지 않습니다. |
| 통신 장애 뒤 과제를 다시 배정하는 시나리오의 실행 시간은 편대 크기에 따라 어떻게 달라지는가? | 운동학 시나리오에서 4·16·64·256대 중 25%의 보고를 끊고 임무 재배정과 전체 실행 시간을 기록했습니다. | 통신·임무 갱신과 운동학 계산을 포함한 시나리오 전체 시간입니다. 조정기만 따로 재지 않았으며, AirSim 강체·충돌 회피·화면 그리기는 포함하지 않습니다. |
| 충돌 계산 변경이 시간을 줄였는가? | 같은 PC와 비슷한 입력으로 코드 변경 전후를 측정했습니다. | 해당 배치의 측정 구간에서 달라진 점을 봅니다. 모든 장면에서의 개선을 보장하지 않습니다. |
| 큰 편대에서 임무가 끝나고 메모리는 얼마나 늘어나는가? | 가상 임무 완료 여부와 프로세스 메모리를 기록했습니다. | 시나리오가 목표까지 진행되는지와 전체 프로세스의 대략적인 메모리 증가를 봅니다. 실제 임무 성공률이나 객체 하나의 크기는 알 수 없습니다. |

화면 시험은 앱이 화면 한 장을 처리하는 시간을 잽니다. 화면 없는 시험은 렌더링을 제외한 비행·충돌·임무 계산을 잽니다. 대상이 다르므로 두 결과를 서로 비교하지 않습니다.

## 측정 환경과 결과를 읽는 방법

2026년 10월 24일 Release 빌드에서 두 종류의 시험을 진행했습니다. 화면 시험은 리비전 `edd2a04d`에서 X500 한 대와 장면·EO 카메라를 켜고, 1280×720 해상도와 VSync 끔 설정으로 5초씩 세 번 기록했습니다. 최신 화면 없는 전체 시험은 `26c7fce1-dirty` 리비전에서 숨김 OpenGL 창을 5초 기록한 뒤 드론 확장성과 협동 임무를 측정했습니다. 화면 기록은 1,921프레임(초당 약 384.1프레임), 시뮬레이션은 300 Tick이었습니다. 두 시험은 화면 표시 여부와 코드 리비전이 달라 직접 비교할 수 없습니다. 화면 시험은 앱 내부 처리 시간이며 모니터 표시 시각이나 조종 입력부터 화면까지의 지연을 재지 않았습니다. 전체 측정에 사용한 GPU는 NVIDIA GeForce RTX 3060 Ti, OpenGL은 3.3.0 NVIDIA 581.42입니다. CPU·메모리 용량과 운영체제 세부 정보는 기록에 없습니다. [전체 측정 자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-26c7fce1.json)에서 실행 기록을 확인할 수 있습니다.

- **앱 프레임 시간**은 앱이 한 화면 프레임을 처리하는 데 걸린 시간입니다. 16.67ms는 60Hz 화면의 한 프레임 예산을 가늠할 때 쓰는 기준입니다. 이번 시험은 VSync를 꺼서 실제 모니터 표시 시각은 측정하지 않았습니다.
- **패널 구성 시간**은 ImGui 프레임을 시작한 뒤 장면·카메라·상태 패널을 구성하는 구간입니다. 앱 프레임 안의 하위 구간이며, 장면과 카메라를 실제로 그리는 호출도 포함될 수 있어 다른 구간과 시간을 더하면 안 됩니다.
- **Tick 시간**은 비행 상태를 1/60초 진행하는 계산 한 번에 걸린 시간입니다. 화면 프레임 시간과 별도로 봅니다.
- **p95**는 측정 표본의 95%가 그 시간 안에 처리됐다는 뜻입니다. 드문 긴 지연을 놓치지 않도록 p99와 최댓값도 함께 봅니다.
- **실시간 배수(RTF)**는 실제 경과 시간에 비해 모의 시간이 얼마나 진행됐는지를 나타냅니다. 1배면 실제 시간과 같은 속도입니다.
- 결과를 비교할 때는 코드 리비전, 실행 시점, 장면과 부하가 같은지 확인해야 합니다. 원자료는 [측정 결과 찾아보기](../../benchmarks/results/README.md)에 모았습니다.

### 현재 리비전의 협동 임무와 확장성 결과

최신 전체 측정은 `26c7fce1-dirty` Release 실행에서 진행했습니다. 통신 장애 복구 시나리오에서는 네 대가 조사 과제를 맡고, 그중 한 대의 상태 보고를 끊었습니다. 운동학과 강체 모의에서 각각 세 번 실행해 매번 네 과제를 모두 마쳤습니다. 상태를 확인할 수 없는 드론 한 대는 미확정으로 남았습니다. 강체 모의는 매번 과제 하나를 다시 배정했고 가장 가까운 중심 간 거리는 약 2.22m였습니다. 운동학 모의는 과제 두 개를 다시 배정했고 최소 중심 간 거리는 약 3.42m였습니다. 이 수치는 해당 배치의 결과입니다.

통신 단절과 배터리 부족을 함께 둔 네 대 임무도 모의 방식마다 세 번 실행했습니다. 매번 세 과제를 마쳤고 한 대가 저전력 귀환을 시작했습니다. 강체 모의에서는 매번 충돌 회피 동작이 세 번 기록됐고 최소 중심 간 거리는 약 3.60m였습니다. 설정한 최소 간격은 2m입니다. 운동학 모의에서는 충돌 회피와 최소 간격을 재지 않았습니다. 배터리 소모량은 단순 배터리 모델의 계산값입니다.

| 드론 수 | 상태 보고가 끊긴 수 | 재할당 횟수 | 임무 완료율 | PC 실행 시간 중앙값 |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 1 | 1 | 100% | 2.210ms |
| 16 | 4 | 4 | 100% | 3.005ms |
| 64 | 16 | 16 | 100% | 7.895ms |
| 256 | 64 | 64 | 100% | 66.757ms |

규모마다 준비 실행 한 번과 측정 세 번을 진행했습니다. 시작할 때 드론마다 조사 과제를 하나씩 배정하고, 정해진 시점에 상태 보고가 끊기면 미완료 과제를 다시 나눴습니다. 실행 시간은 조정기만 따로 잰 값이 아니라 시나리오 전체의 PC 실행 시간입니다. 이 시험은 운동학 모의로 진행해 충돌 회피와 화면 렌더링은 포함하지 않았습니다. [최신 전체 측정 자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-26c7fce1.json)에 반복 결과와 다른 규모 시험이 있습니다.

## 실제 창에서 화면이 멈추는지 확인

**시험 목적:** 평균 FPS만으로는 드물게 발생하는 긴 프레임을 찾기 어려워, 장면과 EO 카메라를 켜고 보통 프레임과 오래 걸린 프레임을 따로 기록했습니다.

| 실행 | 프레임 수 | FPS | 앱 프레임 p50 | p95 | p99 | 최댓값 | 16.67ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,359 | 271.69 | 2.411ms | 7.434ms | 11.868ms | 201.880ms | 7 |
| 2 | 1,644 | 328.52 | 2.404ms | 5.715ms | 7.669ms | 39.101ms | 3 |
| 3 | 1,579 | 315.80 | 2.411ms | 6.719ms | 8.215ms | 13.348ms | 0 |

세 번의 p95 중앙값은 6.719ms, p99 중앙값은 8.215ms였습니다. 16.67ms를 넘은 프레임은 실행별로 7개, 3개, 0개였습니다. 첫 실행의 최댓값은 201.880ms였으며, 같은 프레임의 패널 구성 구간도 200.620ms였습니다. 이 구간에는 장면·카메라 렌더링 호출이 기록되지 않았습니다. 계측은 ImGui 패널 내부 작업을 더 세분하지 않아, 어떤 작업이 지연을 일으켰는지는 밝혀지지 않았습니다. 긴 프레임이 실제 창에서도 관측됐지만, 이 짧은 시험만으로 화면이 항상 매끄럽다고 판단할 수는 없습니다.

각 실행은 1초 준비 뒤 5초 기록했습니다. 지형은 약 18.8×23.7km이며, 장면에는 건물 상자 17개와 공원 시설물 49개가 있었습니다. EO 픽셀은 3칸 비동기 PBO 버퍼로 읽었습니다. 실행별 원자료는 [세 번의 화면 측정과 설정](../../benchmarks/results/archive/aerosimlab-visible-benchmark-release-2026-10-24-edd2a04d.json)에 있습니다.

이번 시험은 창을 띄우고 자동 시연을 실행했습니다. 사용자 입력부터 화면까지 걸리는 시간과 장시간 사용 중의 끊김은 측정하지 않았습니다.

## 드론 수와 배치가 계산 비용에 미치는 영향

**시험 목적:** 렌더링을 제외하고 운동학·AirSim 강체 모의에서 드론 수와 배치가 계산 시간에 미치는 영향을 확인했습니다. 드론을 떨어뜨려 놓은 경우, 가까이 모은 경우, 협동 임무를 각각 실행했습니다.

독립 비행과 밀집 배치 시험은 준비 Tick 120회 뒤 최대 30,000 Tick까지 진행하고, 세 번 반복했습니다. 표의 Tick p95와 실시간 배수는 세 실행 결과의 중앙값입니다. 강체 1,024대는 30초 제한으로 24,000 Tick까지만 한 번 실행했습니다. 아래 p95는 Tick 한 번의 계산 시간이고 전체 실행 시간과는 다릅니다.

| 모의 방식과 부하 | 드론 수 | 반복과 작업량 | Tick p95 중앙값 | RTF 중앙값 | 결과 |
| --- | ---: | --- | ---: | ---: | --- |
| 운동학, 서로 떨어진 배치 | 1,024 | 30,000 Tick씩 3회 | 11.8µs | 약 1,934배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 512 | 30,000 Tick씩 3회 | 787.9µs | 약 28.5배 | 세 번 모두 완료 |
| AirSim 강체, 0.55m 간격 배치 | 256 | 30,000 Tick씩 3회 | 899.3µs | 약 24.1배 | 세 번 모두 완료 |
| AirSim 강체, 서로 떨어진 배치 | 1,024 | 24,000 Tick까지 1회 | 1,676.6µs | 약 13.2배 | 30초 제한에 걸린 부분 실행 |

운동학 1,024대와 강체 512대는 세 번 모두 목표 Tick을 마쳤습니다. 강체 1,024대는 30초 제한으로 중단된 한 번의 부분 실행입니다. 완료 가능한 규모로 볼 수 없습니다. 강체 256대의 0.55m 간격 시험도 세 번 모두 끝났고, 모든 실행에서 16.67ms를 넘은 Tick은 없었습니다. 이 확장성 시험에는 지도 지형과 건물·시설물 충돌을 넣지 않았습니다.

대규모 임무 시험은 시작 전에 각 드론에 조사 목표 하나를 지정합니다. 따라서 편대가 커질 때 드론별 비행, 목표 도달, 완료 판정에 드는 비용을 봅니다. 조정기가 통신 장애 뒤 과제를 다시 나누는 비용은 아래의 4대 협동 시험과 재할당 규모 시험에서 따로 확인합니다.

운동학 1,024대는 300 Tick, AirSim 강체 128대는 480 Tick을 수행했고, 각 규모의 세 실행 모두 임무를 마쳤습니다. PC가 시나리오를 계산한 시간의 중앙값은 각각 29.54ms와 73.22ms였습니다. `mission_completion_time_seconds`는 첫 임무 시작부터 마지막 임무 완료까지 시뮬레이션 안에서 흐른 시간이며, 중앙값은 운동학 0.083초, AirSim 강체 1.10초였습니다. 목표는 출발점에서 0.5m 떨어져 있어 실제 장거리 임무 시간으로 볼 수 없습니다. 두 수치 중 앞은 PC 실행 시간, 뒤는 모의 임무 시간입니다. 이 시험은 미리 나눈 목표의 비행과 완료 판정을 다뤘습니다.

### 통신 단절과 임무 재배정을 함께 실행하면

**시험 목적:** 드론 수만 늘리는 시험으로는 통신 장애 뒤의 임무 재배정과 최소 간격을 확인할 수 없어, 네 대가 조사 임무를 수행하는 중 한 대의 상태 보고를 끊는 시나리오를 운동학과 AirSim 강체 모드에서 반복했습니다. 준비 실행 한 번 뒤 같은 입력으로 세 번씩 측정하고, 네 구역의 완료 여부와 미확정 드론 수, 최소 중심 간 거리를 기록했습니다.

| 모의 방식 | Tick 수 | 반복 결과 | 재배정된 구역 수 | 미확정 드론 | 네 구역 완료 | 최소 중심 간 거리 | PC 실행 시간 중앙값 | 모의 임무 시간 중앙값 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 운동학 | 320 | 3회 모두 통과 | 2 | 1 | 100% | 3.417m | 2.14ms | 3.017초 |
| AirSim 강체 | 1,800 | 3회 모두 통과 | 1 | 1 | 100% | 2.221m | 13.97ms | 9.767초 |

두 방식 모두 세 번씩 네 구역을 완료했고 최소 간격은 기준 1m를 넘었습니다. 통신이 끊긴 드론 한 대는 미확정 상태로 남겼습니다. 재배정한 구역 수와 모의 임무 시간은 모의 방식마다 달랐습니다. PC 실행 시간은 시나리오를 계산한 벽시계 시간이고, 모의 임무 시간은 첫 임무 시작부터 마지막 임무 완료까지 시뮬레이션 안에서 흐른 시간입니다. 강체 시험의 Tick 수가 더 많으므로 두 행의 PC 실행 시간을 물리 방식의 처리 속도로 비교할 수는 없습니다. 이 시험에서 실제 UDP 장애나 비행제어기의 링크 상실 동작은 다루지 않았습니다. 반복별 설정과 수치는 [전체 측정 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에 있습니다.

### 배터리 부족과 통신 단절이 함께 생기면

**시험 목적:** 통신 복구 시나리오에 배터리 부족 조건을 더해 저전력 귀환과 임무 재배정이 함께 동작하는지 확인했습니다. 운동학과 AirSim 강체 방식에서 준비 실행 한 번 뒤 같은 입력으로 세 번씩 측정했습니다.

| 모의 방식 | Tick 수 | 반복 결과 | 완료 과제 | 저전력 귀환 | 회피 동작 | 최소 중심 간 거리 | 모의 임무 시간 중앙값 | 계산 시간 중앙값 | 에너지 사용량 중앙값 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 운동학 | 720 | 3회 모두 통과 | 3/3 | 1대 | 없음 | 측정 안 함 | 3.867초 | 2.237ms | 0.779Wh |
| AirSim 강체 | 1,800 | 3회 모두 통과 | 3/3 | 1대 | 매회 3회 | 3.600m | 6.517초 | 13.080ms | 1.935Wh |

세 번씩 실행해 두 방식 모두 과제 세 개를 마쳤습니다. 충돌 회피는 강체 모의에서만 기록됐고 최소 중심 간 거리는 설정값 2m보다 컸습니다. PC 실행 시간과 모의 임무 시간은 서로 다른 값입니다. 두 방식은 Tick 수와 물리 계산도 달라 계산 시간을 직접 비교하기 어렵습니다. 에너지 사용량은 단순 배터리 모델의 계산값입니다. 운동학 모의에는 충돌 회피가 없어 최소 간격을 재지 않았습니다. 반복별 입력과 결과는 [최신 전체 측정 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-26c7fce1.json)에 있습니다. 수정 사항을 커밋하기 전에 실행한 결과라 `26c7fce1-dirty`로 표시했습니다.

### 편대가 커질 때 임무 재할당 계산은 얼마나 늘어나나?

**시험 목적:** 드론 수가 늘어날 때 임무 재할당 계산이 얼마나 늘어나는지 확인했습니다. 운동학 시나리오에서 전체의 4분의 1을 장애 대상으로 정하고 임무 시작 직전에 상태 보고를 끊었습니다. 장애 대상은 편대에 고르게 배치했으며, 각 드론에는 조사 과제를 하나씩 미리 배정했습니다.

한 Tick은 1/60초입니다. 보고 단절은 임무 시작 5 Tick 전에 발생하고, 3 Tick 동안 Heartbeat가 돌아오지 않으면 해당 드론의 상태를 미확정으로 처리합니다. 과제는 임무 시작 Tick 90에 시작하며, 모두 끝내야 하는 기한은 Tick 690입니다. 각 과제의 목표는 출발점에서 0.5m 떨어져 있습니다. 드론 수별로 준비 1회와 측정 3회를 실행했습니다.

| 드론 수 | 상태 보고 단절 | 재할당 횟수 중앙값 | 임무 완료율 | 모의 임무 시간 | 계산 시간 범위 | 계산 시간 중앙값 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 1대 | 1회 | 100% | 1.083초 | 2.055–2.172ms | 2.172ms |
| 16 | 4대 | 4회 | 100% | 1.083초 | 2.773–2.874ms | 2.783ms |
| 64 | 16대 | 16회 | 100% | 1.083초 | 7.815–8.005ms | 7.970ms |
| 256 | 64대 | 64회 | 100% | 1.083초 | 65.540–67.518ms | 65.554ms |

네 규모 모두 세 번씩 임무를 마쳤습니다. 미확정 드론과 재배정 횟수는 장애 대상 수와 같았습니다. 계산 시간은 통신 상태 갱신·임무 처리·운동학 Tick을 포함한 PC의 전체 실행 시간입니다. 모의 임무 시간이나 조정기만의 처리 시간과는 다릅니다. 드론이 늘수록 계산 시간도 길어졌습니다. 네 규모만 측정했으므로 알고리즘 복잡도나 다른 PC의 처리 한계까지 설명하지는 않습니다. 시험 설정과 반복별 원자료는 [재할당 규모가 포함된 Release 측정](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에 있습니다.

화면 없는 전체 시험의 배터리·통신·충돌 회피 통합 결과와 화면 기록은 [최신 전체 측정 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-26c7fce1.json)에 있습니다. 과거 재할당 규모와 네 대 통신 장애 시험은 [이전 전체 시험 자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-1c0c60dd.json)에서 확인할 수 있습니다. 그보다 앞선 기록은 [이전 전체 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-efa1ea8f.json), [첫 전체 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-c55c76de.json), [화면 표시 시험](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-edd2a04d.json)에 보관했습니다. 전체 드론 수별 반복 기록과 개별 계산 구간은 JSON에 보존했습니다.

### 드론 수가 늘 때 프로세스 메모리는 얼마나 바뀌나?

**시험 목적:** 드론 수가 늘 때 프로세스 전체 메모리가 얼마나 증가하는지 비교했습니다. 표의 값은 ECS Entity나 강체 객체 하나의 크기가 아니라 프로세스 메모리 증가량을 추가 드론 수로 나눈 값입니다.

별도 실행에서 드론 1대와 1,024대일 때 프로세스 `Private Bytes` 차이를 쟀습니다. 그 차이를 추가한 1,023대로 나눈 값이 아래 표에 있습니다.

| 모의 방식 | 1대에서 1,024대까지 늘어난 프로세스 메모리 | 추가 드론 1대당 단순 나눗값 |
| --- | ---: | ---: |
| 운동학 | 724,992B | 약 709B |
| AirSim 강체 | 8,192,000B | 약 7.8KiB |

각 방식은 한 번씩 측정했습니다. 프로세스 메모리에는 드론 상태 외에도 컨테이너 용량, 메모리 할당기, 물리 엔진의 공유·내부 자료가 포함됩니다. 따라서 표의 드론당 값은 메모리 증가 규모를 가늠하는 참고값입니다. [전체 Release 원자료](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-24-edd2a04d.json)에서 표본과 실행 설정을 확인할 수 있습니다.

## 충돌 후보 정렬을 바꾼 효과

**시험 목적:** 드론이 앞지르지 않은 Tick에는 전체 정렬을 생략하도록 바꿨습니다. 넓은 배치와 밀집 배치에서 물리 계산 시간이 실제로 줄었는지 확인했습니다.

변경 전 `94c39b94`와 변경 후 `69ecab93`를 같은 Windows Release 환경에서 측정했습니다. 각 조건은 준비 Tick 120회 뒤 30,000 Tick씩 세 번 실행했습니다. 분리 배치는 드론 간격 2.5m, 밀집 배치는 정사각 격자 간격 0.55m였습니다. 아래 값은 각 반복에서 구한 p95의 중앙값입니다.

| 배치와 드론 수 | 물리 단계 p95 전 → 후 | 접촉 후보 생성 p95 전 → 후 | 결과 해석 |
| --- | ---: | ---: | --- |
| 분리, 128대 | 190.5 → 189.7µs | 125.0 → 129.3µs | 차이가 작아 개선을 확인했다고 보기 어려움 |
| 분리, 256대 | 381.0 → 348.0µs | 247.6 → 232.8µs | 각각 8.7%, 6.0% 감소 |
| 분리, 512대 | 745.3 → 677.7µs | 470.5 → 445.6µs | 각각 9.1%, 5.3% 감소 |
| 밀집, 128대 | 474.0 → 411.9µs | 403.0 → 350.7µs | 각각 13.1%, 13.0% 감소 |
| 밀집, 256대 | 833.0 → 796.9µs | 705.1 → 676.4µs | 각각 4.3%, 4.1% 감소 |

접촉 후보 생성 구간에는 정렬, 충돌 상자 좌표 갱신, 후보 쌍 검사가 함께 들어갑니다. 따라서 전체 시간 변화 중 정렬이 차지하는 몫은 따로 측정하지 않았습니다. 시험에는 지형 격자와 정적 장애물이 없었습니다. [변경 전 기록](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-94c39b94-before-sort-reuse.json)과 [변경 후 기록](../../benchmarks/results/archive/aerosimlab-full-benchmark-release-2026-10-23-69ecab93-after-sort-reuse.json)에서 실행 결과를 볼 수 있습니다.

## 긴 프레임 원인 조사 기록

EO 픽셀 읽기, OpenGL 호출과 CPU 표본을 나눠 살펴본 조사는 별도 문제 해결 기록에 모았습니다. 그 조사는 **긴 프레임의 원인 후보를 좁히는 과정**이지, 최신 Release의 대표 성능 기준선이 아닙니다. [EO 카메라를 켜면 화면이 가끔 멈춘 문제](문제해결/화면-프레임-지연.md)에서 확인된 사실과 미확정 원인을 읽을 수 있습니다. 화면 없는 다중 드론 충돌 시험의 이전 단계는 [충돌 계산 성능 기록](문제해결/다중드론-충돌-성능.md)에 있습니다.
