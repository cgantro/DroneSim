# 드론 수가 늘면서 충돌 계산이 느려진 문제

드론이 멀리 떨어진 장면과 가까이 모인 장면에서 충돌 후보를 줄였을 때 계산 시간이 어떻게 달라지는지 측정했습니다.

## 증상과 첫 가설

드론이 서로 멀리 떨어져 있어도 모든 쌍을 매 Tick마다 검사했습니다. 드론 수가 두 배가 되면 검사할 쌍은 대략 네 배가 되므로, 닿을 가능성이 없는 드론끼리까지 상자 충돌 검사를 하는 비용이 커졌습니다.

## 확인하며 찾은 낭비

분리 배치와 밀집 배치를 따로 재 보니 원인이 한 가지가 아니었습니다. 멀리 떨어진 드론은 후보에서 미리 빼면 됐지만, 가까운 드론이 많은 배치에서는 후보가 여전히 많이 남았습니다. 그때는 같은 드론의 충돌 상자를 쌍마다 세계 좌표로 다시 바꾸고, A와 B가 만나는지 A 쪽에서 한 번, B 쪽에서 다시 한 번 검사하고 있었습니다.

## 바꾼 점

변경은 세 단계로 진행했습니다.

1. 드론을 위치 순서로 정렬하고, 충돌할 수 없는 먼 쌍을 후보에서 제외했습니다.
2. 한 Tick 동안 같은 자세인 드론의 충돌 상자 아홉 개를 세계 좌표로 한 번만 바꾸고 재사용했습니다. 상자의 축 정렬 바깥 경계가 서로 떨어져 있으면 회전 상자 정밀 검사도 건너뜁니다.
3. 드론 쌍마다 접촉을 한 번만 계산하고, 반대 방향 접촉을 양쪽 드론에 전달했습니다.

실제 충돌을 최종 판정하는 회전 상자 검사와 충돌 뒤 운동을 계산하는 강체 엔진은 그대로 뒀습니다. 후보를 줄이는 단계는 충돌을 확정하지 않고, 놓칠 수 있는 쌍을 만들지 않는 방향으로만 사용합니다.

후보 축소와 충돌 판정은 서로 다른 단계입니다. 정렬과 거리 검사는 멀리 있는 쌍을 빠르게 제외하는 넓은 검사이고, 남은 쌍에 대해서만 각 충돌 상자의 방향까지 고려하는 정밀 검사를 합니다. 이 넓은 검사에서 반경이나 경계 비교가 실제 충돌 범위보다 작아지면 접촉을 놓칠 수 있으므로, 최적화의 정확성은 성능 숫자와 별도로 살펴야 합니다. 현재 자동 시험은 일부 접촉 사례를 확인하지만, 옛 전체 쌍 검사와 새 후보 생성 결과를 무작위 장면 여러 개에서 대조하는 완전성 검사는 포함하지 않습니다.

## 회전 상자의 경계값을 반복 계산하던 문제

밀집 장면에서 같은 충돌 상자가 여러 후보 쌍에 들어갑니다. 그런데 정밀 충돌 검사 전에 사용하는 축 정렬 경계 상자의 반크기를 후보 쌍을 볼 때마다 다시 계산하고 있었습니다. 상자의 자세와 크기는 한 물리 Tick 동안 바뀌지 않으므로, 이 계산은 한 번만 해도 충분했습니다.

상자를 월드 좌표로 옮길 때 경계 반크기를 함께 계산해 저장하도록 바꿨습니다. 후보 쌍 검사는 저장된 값을 재사용합니다. 이 변경으로 후보에서 제외되는 쌍이나 실제 접촉 판정 기준은 달라지지 않았고, 회전 상자의 15축 정밀 검사와 충돌 응답도 그대로입니다.

변경 전후를 같은 Windows Release PC에서 비교했습니다. 두 실행 모두 NVIDIA GeForce RTX 3060 Ti, 1280×720, 밀집 배치 256대, 간격 0.55m, 준비 120 Tick 후 30,000 Tick씩 세 차례라는 조건을 사용했습니다. 표는 각 실행의 p50·p95를 구한 뒤 세 결과의 중앙값을 나타냅니다.

| 측정 구간 | 변경 전 p50 / p95 | 변경 후 p50 / p95 |
| --- | ---: | ---: |
| 접촉 생성 | 448.9 / 607.6µs | 429.2 / 496.3µs |
| 물리 단계 전체 | 506.9 / 704.6µs | 486.4 / 567.9µs |
| 시뮬레이션 Tick 전체 | 578.6 / 801.6µs | 557.9 / 648.2µs |

접촉 생성 p95 중앙값은 607.6µs에서 496.3µs로, Tick 전체 p95 중앙값은 801.6µs에서 648.2µs로 낮아졌습니다. 각 측정은 제한 시간 안에 모두 완료됐고, 변경 후 Release CTest 20개도 통과했습니다. 다만 변경 전 측정은 `0de5d066-dirty`, 변경 후는 `5b144a13` 코드에서 수행했습니다. 실행 환경과 입력 조건은 맞췄지만 측정 코드와 그 밖의 코드 변경까지 완전히 같지는 않으므로, 이 수치만으로 모든 장면에서 같은 개선 폭을 기대할 수는 없습니다.

## 충돌 후보를 두 번 훑던 문제

### 증상과 확인한 원인

드론을 X 좌표 순서로 정렬해 두고도, 각 드론마다 정렬 목록을 다시 검색하고 있었습니다. 한 드론의 충돌 반경 안에 들어오는 후보를 찾은 뒤에는 이미 처리한 쌍인지 확인해 건너뛰었습니다. 그래서 드론이 서로 떨어져 있는 장면에서도 같은 후보 구간을 양쪽 드론에서 반복해 훑었습니다. 실제 접촉 판정은 한 번만 했지만, 후보를 찾는 작업은 중복될 수 있었습니다.

### 수정

정렬된 목록을 앞에서 뒤로 한 번 훑도록 바꿨습니다. 현재 드론보다 뒤에 있는 후보만 검사하고, X 좌표 차이가 충돌할 수 있는 범위를 벗어나면 그 뒤의 후보도 더 볼 필요가 없도록 했습니다. 범위 계산에는 현재 드론과 가장 큰 충돌 반경을 사용해 크기가 다른 드론 조합도 후보에서 빠지지 않게 했습니다.

기존 충돌 시험은 드론을 만든 순서와 공간상 순서가 같았습니다. 시험의 생성 순서를 바꿔 두 순서가 반대인 경우에도 서로 겹친 드론을 찾는지 확인하게 했습니다. 시험 개수는 늘리지 않았으며, Release 빌드와 기존 CTest 20개가 통과했습니다. 다만 무작위 배치에서 예전 전체 쌍 결과와 새 후보 목록을 대조하는 시험은 여전히 없습니다.

### 같은 조건에서 다시 잰 결과

이 변경을 적용한 코드(`8623be5c`)와 기준 코드(`e2510815`)를 같은 Windows Release PC에서 측정했습니다. 분리 배치는 드론 간격 2.5m, 밀집 배치는 0.55m였고, 각 실행 전에 120 Tick을 준비한 뒤 최대 30,000 Tick을 측정했습니다. 256대와 512대는 세 번 측정해 실행별 p95의 중앙값을 비교했습니다. 1,024대는 양쪽 모두 30초 제한에 걸려 각각 한 번, 27,000 Tick까지만 측정했습니다.

| 장면 | Tick p95 중앙값, 변경 전 → 후 | 접촉 생성 p95 중앙값, 변경 전 → 후 | 실행 시간 중앙값, 변경 전 → 후 |
| --- | ---: | ---: | ---: |
| 분리 256대 | 286.8 → 301.5µs (+5.1%) | 144.5 → 145.0µs (+0.3%) | 7.865 → 7.879초 (+0.2%) |
| 분리 512대 | 599.0 → 603.9µs (+0.8%) | 298.2 → 297.0µs (-0.4%) | 16.434 → 16.194초 (-1.5%) |
| 분리 1,024대* | 1,239.2 → 1,219.4µs (-1.6%) | 624.1 → 604.3µs (-3.2%) | 30.708 → 30.078초 (-2.1%) |
| 밀집 256대 | 641.2 → 620.4µs (-3.2%) | 485.2 → 467.9µs (-3.6%) | 16.988 → 16.453초 (-3.2%) |

`*` 1,024대는 반복 실행 세 번을 마치지 못했습니다. 두 결과 모두 30초 제한으로 중단됐으며, 완료된 Tick 수도 27,000회였습니다. 따라서 이 행은 반복 측정의 중앙값이 아니라 단일 실행 비교입니다.

효과는 장면마다 달랐습니다. 밀집 256대에서는 접촉 생성 p95와 실행 시간이 약 3% 줄었습니다. 분리 512대에서는 접촉 생성 p95가 거의 같고 전체 실행 시간만 약간 줄었으며, 분리 256대는 전체 Tick p95가 오히려 높았습니다. 1,024대는 한 번씩만 실행해 참고값으로 봐야 합니다. 이 측정으로 확인된 개선은 밀집 256대 조건에 한정됩니다.

### 변경 전후를 비교할 때 주의할 점

최적화를 나누어 적용하면서 여러 기준 측정이 생겼습니다. 예를 들어 충돌 상자 재사용 전후의 32대 밀집 측정은 Tick p95 중앙값이 1,344.3µs에서 665.1µs로 나왔습니다. 다음 후보 건너뛰기 측정에서는 32대가 481.8µs에서 151.1µs, 64대가 999.0µs에서 325.1µs였습니다. 이 측정들은 서로 다른 코드 시점의 결과이므로 한 표에서 연속적인 개선률처럼 계산하지 않았습니다.

분리 배치 512대 측정은 652.7µs에서 658.1µs로 거의 달라지지 않았습니다. 후보 쌍이 원래 적은 경우에는 추가 바깥 경계 검사 비용이 절감과 비슷할 수 있음을 보여 줍니다. 밀집 128대는 이전 시험이 17,000 Tick 한 번에 30초 제한으로 끝나 후속 세 번 반복과 직접 비교할 수 없습니다. 1,024대 강체 시험도 제한 시간 안에 끝나지 않았습니다.

## 계산량이 어떻게 달라졌나

드론이 `N`대면 가능한 서로 다른 쌍은 `N × (N - 1) / 2`개입니다. 예를 들어 256대에서는 32,640쌍, 512대에서는 130,816쌍, 1,024대에서는 523,776쌍입니다. 이전처럼 매 쌍에 정밀 상자 충돌을 적용하면 드론 수가 늘수록 비용이 빠르게 커집니다.

현재는 먼저 드론 중심을 X 좌표로 정렬하고, X 방향으로 충돌 반경 밖에 있는 대상을 건너뜁니다. 남은 쌍은 중심 거리의 제곱으로 한 번 더 거르고, 실제 상자 겹침 가능성이 있을 때만 회전 상자 검사를 수행합니다. 한 쌍의 접촉 결과는 양쪽 드론에 반대 방향으로 전달합니다. 이 방식은 분리된 배치에서 불필요한 정밀 검사를 줄이지만, 드론이 한 구역에 밀집하면 후보가 대부분 남으므로 최악의 경우 쌍 수가 여전히 제곱에 비례합니다.

여기서 줄어드는 것은 모든 쌍을 정밀 검사하는 횟수입니다. 드론 상태 수집, 후보 목록 구성, 가까운 쌍의 정밀 검사와 접촉 응답은 계속 필요합니다. 따라서 드론 수가 늘어날 때 처리 시간이 완전히 선형으로 증가한다고 기대하면 안 됩니다. 특히 계속 접촉하는 밀집 편대에서는 후보 필터가 제거할 수 있는 쌍이 적습니다.

## 자동 시험에서 확인한 내용

현재 자동 시험은 건물 옆면 접촉, 드론 상자의 실제 겹침, 서로 겹친 드론의 분리를 확인합니다. 고정 난수 시드로 만든 상자 쌍 2,000개를 검사해, 정밀 상자 검사에서 접촉한 쌍을 외접구 후보 검사가 놓치지 않는지도 확인합니다. X 좌표 정렬과 후보 탐색은 이전의 전체 쌍 검사와 직접 대조하지 않았고, 충돌 후보가 많은 장면의 처리 시간도 자동 시험에서 재지 않았습니다. 표의 p95는 별도 Release 측정 결과입니다.
