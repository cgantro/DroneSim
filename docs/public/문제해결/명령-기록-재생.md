# 기록한 조종 명령을 재생하면 Tick과 상태가 달라진 문제

## 기대한 동작과 실제 문제

같은 초기 상태에서 같은 입력을 재생하면 명령이 같은 모의 Tick에 적용되고 최종 상태도 같아야 합니다. 초기 구현에서는 기록 시작·종료 요청도 시뮬레이션 시간을 한 Tick 진행했지만, 기록기가 그 경계 Tick을 기록 길이에 같은 방식으로 반영하지 않았습니다. 그래서 재생이 마지막 Tick을 건너뛰거나, 기록과 재생의 상태가 한 단계 어긋날 수 있었습니다.

또 다른 경로에서는 재생 중에도 게임패드 입력을 받을 수 있었습니다. 재생 중 수동 입력이 시뮬레이션 상태에 들어오면, 기록된 입력만 다시 실행한다는 전제가 깨집니다.

## 원인을 좁힌 과정

명령은 현재 Tick 번호에 기록된 뒤 그 Tick의 시뮬레이션이 한 번 진행됩니다. 따라서 기록 재생은 각 Tick에서 **명령 적용 → 시뮬레이션 진행 → 재생 번호 증가** 순서를 지켜야 합니다. 시작·종료 요청도 일반 명령처럼 처리 후 Tick을 진행하므로, 기록기는 해당 요청을 받은 시점의 상태뿐 아니라 Tick 시작 시 기록 중이었는지도 알아야 합니다.

종료 요청은 처리 후 `recording` 상태가 꺼집니다. 끝난 뒤의 상태만 보고 Tick을 셌다면 종료 요청이 소모한 마지막 Tick이 기록 길이에서 빠집니다. 반대로 시작 요청은 처리 중에 기록 상태가 켜지므로, 첫 Tick이 기록에 포함되어야 합니다. 이 경계 조건이 재생 종료 시점의 차이를 만들었습니다.

게임패드 문제는 기록 시간 계산과 별개의 입력 소유권 문제였습니다. 재생 중에는 기록된 명령이 입력의 기준이어야 하지만, 기존 입력 차단은 지상통제 여부만 확인했습니다. 게임패드가 새 명령을 만들거나 이미 대기 중인 명령을 남기면 재생 결과가 바뀔 수 있었습니다.

## 수정한 내용

각 명령과 적용 Tick을 함께 저장하고, 기록 중이었던 Tick의 시작 상태를 사용해 종료 요청의 마지막 Tick도 세도록 바꿨습니다. 재생기는 현재 Tick에 해당하는 명령만 꺼낸 뒤 시뮬레이션을 진행하고 다음 Tick으로 넘어갑니다. 기록이나 재생이 시작될 때는 이전 시뮬레이션 상태를 초기화합니다.

재생 중에는 게임패드에서 새 비행 명령을 받지 않고, 이미 대기 중인 게임패드 동작도 비웁니다. 지상통제 명령과 기록 재생 명령은 별도 흐름으로 유지합니다. 재생을 시작할 때 카메라 픽셀 읽기에도 이전 실행의 Tick 번호가 남지 않도록 정리하는 문제가 함께 발견됐습니다. 이 문제는 [재생 뒤 EO 화면이 갱신되지 않던 문제](카메라-재생-프레임.md)에서 따로 설명합니다.

## 검증한 범위

과거 시험에서는 시작·종료 경계 Tick, 명령이 없는 기록, 운동학 재생, 강체 재생, UDP를 거친 기록·재생을 각각 확인했습니다. 당시 상태 비교는 Tick 수, 비행 모드, 위치, 속도, 자세와 각속도를 기준으로 했습니다.

현재 시험 구성을 줄인 뒤에는 기록·재생 상태를 직접 비교하는 핵심 시험이 운동학 방식으로 남아 있습니다. 이 시험은 기록과 재생의 최종 Tick 및 드론 상태를 비교합니다. 별도의 숨김 시뮬레이터 통합 시험은 UDP로 기록 시작·비행 명령·기록 종료·재생 요청이 이어지는 흐름과 재생 종료를 확인합니다. 현재 핵심 단위 시험은 AirSim 강체 재생 상태를 직접 비교하지 않으며, 실제 화면의 카메라 픽셀 일치도 검사하지 않습니다.

## 남은 한계와 재발 방지

- 기록은 현재 메모리에 보관됩니다. 프로그램을 닫은 뒤 파일로 저장하거나 다른 버전에서 불러오는 기능은 이 동작에 포함되지 않습니다.
- UDP 통합 시험은 같은 PC의 프로그램 사이에서 명령 전달을 확인합니다. 실제 네트워크 지연·손실 환경을 재현하지는 않습니다.
- 입력 기록은 적용 Tick뿐 아니라 명령이 처리되는 시뮬레이션 단계와 함께 검토해야 합니다. 기록 시작·종료처럼 상태를 바꾸는 명령은 Tick 경계 시험 없이 구현 완료로 판단하면 안 됩니다.
- 현재 단위 시험에서 강체 재생 상태를 직접 비교하지 않으므로, AirSim 물리나 기록 순서를 바꿀 때는 그 범위의 검증이 별도로 필요합니다.
