# 정찰 중 이륙 상태가 멈추고 화면 시험이 실패한 문제

## 증상

시뮬레이터 화면에서 정찰 임무가 `목표 1/5: 이륙 중`에 머물렀습니다. 화면에는 모의 시간 99.02초, 5,941번째 Tick, 위치 X=-472m가 표시됐고 드론은 보이지 않았습니다. 기대 동작은 이륙한 뒤 첫 정찰 위치로 이동하는 것입니다.

같은 빌드의 자동 화면 시험도 종료할 때 `0xC0000409` 오류로 실패했습니다. 이 코드는 Windows가 스택의 보안 값이 손상된 것을 감지했을 때 나타납니다. 화면 정지와 종료 오류가 같은 원인인지 먼저 분리해 확인했습니다.

## 가설과 확인

처음에는 바람이나 강체 비행 제어 때문에 이륙이 끝나지 않았을 가능성을 확인했습니다. 현재 실행 코드와 같은 난수 시드, 바람 변화 주기, 바람 세기를 적용해 탄천 출발 위치에서 10초 동안 시험했습니다. 기체는 이륙 상태를 벗어났고 수평 이동도 5m 안에 머물렀습니다. 이 결과만으로 실제 화면의 정지 원인을 물리 제어라고 볼 수는 없습니다.

추가로 받은 화면에서도 모의 시간 99.02초에 X=-472m, `taking_off` 상태가 보였습니다. X=-472m는 출발 위치를 X=-410m로 옮기기 전 값입니다. 현재 저장소의 Release 실행 파일은 X=-410m를 사용합니다. 따라서 이 캡처는 수정 전 실행 파일에서 나온 것으로 판단됩니다. 캡처에 실행 파일 경로나 빌드 정보는 표시되지 않아 어느 폴더의 실행 파일이었는지는 확인할 수 없습니다.

화면에서 기체가 보이지 않는 원인도 따로 확인했습니다. 장면 카메라는 기체 뒤 18m에서 기체를 따라갑니다. 옛 출발점과 첫 정찰 대상의 방향으로 이 위치를 계산해 건물 외곽과 대조하니, 카메라가 체육관 건물 바닥 안에 들어갑니다. 그래서 카메라가 건물 안쪽에서 벽을 바라보며 기체와 주변 장면을 가렸습니다. 새 출발점에서는 카메라 위치가 체육관 외곽 밖에 놓입니다. 이 문제는 기체가 실제로 이륙했는지와 별개로, 장면 카메라가 기체를 숨기는 화면 배치 문제였습니다.

자동 화면 시험의 종료 오류는 별도로 추적했습니다. 실행 진입점이 사용하는 앱 클래스 정의는 바뀌었지만, 진입점 객체는 그 변경 뒤에도 다시 컴파일되지 않았습니다. Ninja 의존성 기록을 비교하니 진입점 객체에는 포함 헤더가 0개였고, 앱 구현 객체에는 270개가 기록돼 있었습니다. 오래된 진입점 객체는 이전 클래스 크기를 기준으로 스택 공간을 잡고, 새 앱 구현은 그보다 큰 객체를 사용했습니다. 실행 중 바람 난수 생성기의 상태를 갱신할 때 스택 경계를 넘어 보안 값이 덮였고, 종료 시점에 오류가 발견됐습니다.

## 수정

잘못된 의존성 기록이 있던 진입점 객체 파일만 지우고 다시 빌드했습니다. 새 객체에는 앱 헤더를 포함한 185개 의존성이 기록됐습니다. C++ 비행 동작은 이 문제를 고치기 위해 변경하지 않았습니다.

또한 탄천 출발 위치에서 실제 앱과 같은 바람 변화를 적용하는 10초 이륙 검사를 추가했습니다. 이 검사는 이륙 상태가 끝나는지와 출발점에서 크게 밀려나지 않는지를 함께 확인합니다. 화면 추적 위치가 이전 출발점에서는 체육관 외곽 안쪽이고 새 출발점에서는 바깥인지 확인하는 검사도 넣었습니다.

## 검증 결과

Release 빌드에서 다음 시험을 실행했습니다.

| 시험 | 결과 |
| --- | --- |
| 강체 물리 이륙과 바람 조건 검사 | 통과 |
| 장면 카메라의 체육관 가림 확인 | 이전 위치는 건물 안, 현재 위치는 건물 밖으로 판정 |
| 정찰 시나리오와 다중 기체 회귀 시험 | 통과 |
| 자동 화면 실행·종료 시험 | 수정 전 실패, 진입점 재컴파일 뒤 통과 |

관련 회귀 시험과 자동 화면 실행·종료 시험은 재컴파일 뒤 통과했습니다. 최신 Release 실행 파일을 `--demo`로 열어 프로세스가 응답하는 것도 확인했습니다. 다만 이 확인은 창이 살아 있는지만 보여 줍니다. 최신 실행 파일에서 정찰 임무가 첫 위치까지 이동하고 EO 영상이 목표를 담는지는 직접 확인하지 못했습니다. 사용자가 보낸 화면은 수정 전 출발 좌표를 표시하므로, 그 화면만으로 현재 코드가 같은 상태라고 판단할 수는 없습니다.

## 남은 확인과 재발 방지

스택 손상은 자동 화면 시험 종료 오류의 원인이었습니다. 화면에서 기체가 보이지 않은 현상은 옛 위치에서 추적 카메라가 체육관 안에 들어간 것으로 설명되며, 새 위치가 건물 밖에 놓이는 회귀 시험이 통과했습니다. 그러나 캡처의 `taking_off` 상태가 오래 유지된 이유까지는 확정되지 않았습니다. 수정 후 이륙 시험은 통과했지만, 최신 실행 파일에서 전체 정찰 임무와 EO 영상까지 확인한 것은 아닙니다. 따라서 임무 정지까지 해결됐다고 단정하지 않습니다.

출발 위치나 드론 방향을 바꿀 때는 추적 카메라 위치도 건물 외곽과 대조합니다. 빌드 후에는 자동 화면 시험을 실행하고, 앱의 클래스 정의가 바뀌면 진입점 객체가 새 정의로 다시 빌드됐는지 확인합니다. 의존성 기록이 비어 있으면 실행 파일을 배포하거나 동작을 검증하기 전에 해당 객체를 다시 빌드합니다.
