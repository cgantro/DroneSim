# 정찰 중 이륙 상태가 멈추고 화면 시험이 실패한 문제

## 증상

시뮬레이터 화면에서 정찰 임무가 `목표 1/5: 이륙 중`에 머물렀습니다. 화면에는 모의 시간 99.02초, 5,941번째 Tick, 위치 X=-472m가 표시됐고 드론은 보이지 않았습니다. 기대 동작은 이륙한 뒤 첫 정찰 위치로 이동하는 것입니다.

같은 빌드의 자동 화면 시험도 종료할 때 `0xC0000409` 오류로 실패했습니다. 이 코드는 Windows가 스택의 보안 값이 손상된 것을 감지했을 때 나타납니다. 화면 정지와 종료 오류가 같은 원인인지 먼저 분리해 확인했습니다.

## 가설과 확인

처음에는 바람이나 강체 비행 제어 때문에 이륙이 끝나지 않았을 가능성을 확인했습니다. 현재 실행 코드와 같은 난수 시드, 바람 변화 주기, 바람 세기를 적용해 탄천 출발 위치에서 10초 동안 시험했습니다. 기체는 이륙 상태를 벗어났고 수평 이동도 5m 안에 머물렀습니다. 이 결과만으로 실제 화면의 정지 원인을 물리 제어라고 볼 수는 없습니다.

추가로 받은 화면에는 모의 시간 99.02초, X=-472m, `taking_off`가 표시됐습니다. X=-472m는 출발 위치를 X=-410m로 옮기기 전 값과 같습니다. 현재 소스의 기본 출발 위치는 X=-410m지만, 캡처에 실행 파일 버전이나 임무 경로는 표시되지 않습니다. 따라서 오래된 실행 파일일 가능성은 있어도, 좌표만으로 단정할 수는 없습니다.

화면에서 기체가 보이지 않는 원인도 따로 확인했습니다. 장면 카메라는 기체 뒤 18m, 위 10m에서 기체를 따라갑니다. 캡처 좌표와 기본 진행 방향을 적용한 재현 시험에서 카메라가 체육관 안에 들어갔습니다. 카메라가 건물 안에 있으면 외벽이 화면을 가리고 기체와 주변 장면은 보이지 않습니다. 이 현상은 비행 물리가 멈췄다는 증거가 아니라 관찰 카메라가 건물에 가려진 문제입니다.

자동 화면 시험의 종료 오류는 별도로 추적했습니다. 실행 진입점이 사용하는 앱 클래스 정의는 바뀌었지만, 진입점 객체는 그 변경 뒤에도 다시 컴파일되지 않았습니다. Ninja 의존성 기록을 비교하니 진입점 객체에는 포함 헤더가 0개였고, 앱 구현 객체에는 270개가 기록돼 있었습니다. 오래된 진입점 객체는 이전 클래스 크기를 기준으로 스택 공간을 잡고, 새 앱 구현은 그보다 큰 객체를 사용했습니다. 실행 중 바람 난수 생성기의 상태를 갱신할 때 스택 경계를 넘어 보안 값이 덮였고, 종료 시점에 오류가 발견됐습니다.

## 수정

잘못된 의존성 기록이 있던 진입점 객체 파일만 지우고 다시 빌드했습니다. 새 객체에는 앱 헤더를 포함한 185개 의존성이 기록됐습니다. C++ 비행 동작은 이 문제를 고치기 위해 변경하지 않았습니다.

탄천의 옛 출발점과 새 출발점에서 각각 10초 동안 강체 이륙을 시험했습니다. 두 위치 모두 `taking_off` 상태를 벗어났습니다. 이는 캡처의 장시간 정지를 출발 위치의 지형이나 단순 이륙 동작만으로는 재현하지 못했다는 뜻입니다.

카메라 가림은 출발점을 옮기는 것만으로 처리하지 않도록 보정했습니다. 원하는 카메라 위치가 건물 안이면 기체를 향해 0.5m 간격으로 확인하고, 건물 밖인 위치를 찾으면 그곳으로 카메라를 옮깁니다. 카메라가 원래 건물 밖에 있으면 기존 위치를 유지합니다. 건물 외곽 안에 점이 있는지 확인하는 계산은 경로 탐색과 물 영역 판정이 함께 쓰도록 한곳으로 모았습니다.

## 검증 결과

Release 빌드에서 다음 시험을 실행했습니다.

| 시험 | 결과 |
| --- | --- |
| 강체 물리 이륙: 옛 출발점·새 출발점 | 두 위치 모두 10초 안에 이륙 완료 |
| 강체 물리 이륙과 바람 조건 검사 | 통과 |
| 카메라가 체육관 안에 들어가는 위치 확인 | 건물 안에 들어감을 재현하고, 보정 위치는 확인된 건물 밖으로 이동 |
| 정찰 시나리오와 다중 기체 회귀 시험 | 통과 |
| 자동 화면 실행·종료 시험 | 수정 전 실패, 진입점 재컴파일 뒤 통과 |

관련 회귀 시험과 자동 화면 실행·종료 시험은 재컴파일 뒤 통과했습니다. 이번 카메라 보정 뒤에는 시뮬레이션 시험 6개 묶음이 모두 통과했고, 시뮬레이터 앱 라이브러리도 컴파일됐습니다. 다만 실행 중인 프로그램이 실행 파일을 사용하고 있어 새 실행 파일을 다시 연결하거나 화면을 직접 확인하지 못했습니다. 창 제목과 응답 상태만으로 화면 갱신이나 정찰 임무 진행을 확인할 수는 없습니다.

## 남은 확인과 재발 방지

스택 손상은 자동 화면 시험 종료 오류의 원인이었습니다. 기체가 보이지 않은 현상은 관찰 카메라가 건물 안에 들어간 경우로 확인했고, 건물 밖으로 카메라를 옮기는 계산과 회귀 시험을 추가했습니다. 옛 위치의 강체 이륙도 독립 시험에서는 완료됐습니다. 하지만 캡처에서 99초 넘게 `taking_off`로 남은 원인은 아직 찾지 못했습니다. 새 실행 파일에서 전체 정찰 임무와 EO 영상이 정상 동작하는지도 직접 확인하지 못했습니다. 그러므로 임무 정지까지 해결됐다고 보지는 않습니다.

출발 위치와 드론 방향이 바뀌어도 카메라가 건물 안에 들어가지 않게 매 프레임 위치를 확인합니다. 빌드 뒤에는 자동 화면 시험을 실행하고, 앱의 클래스 정의가 바뀌면 진입점 객체도 새 정의로 다시 빌드됐는지 확인합니다. 의존성 기록이 비어 있으면 실행 파일을 사용하기 전에 해당 객체를 다시 빌드합니다.
