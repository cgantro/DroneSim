# 기록을 다시 재생하면 EO 화면이 새 프레임으로 바뀌지 않던 문제

## 증상: 비행 상태는 초기화됐는데 영상은 이전 실행에 머물렀다

기록 시작이나 재생을 요청하면 시뮬레이션 Tick이 처음부터 다시 시작됩니다. 그때 드론 상태는 새 실행으로 초기화됐지만, EO 화면은 이전 프레임을 계속 보여 주거나 새 프레임으로 바로 바뀌지 않는 경로가 있었습니다.

상태 재설정과 카메라 픽셀 처리는 서로 다른 시간표를 따릅니다. 시뮬레이션은 고정 Tick으로 즉시 초기화되지만, OpenGL의 픽셀 읽기는 GPU에 요청한 뒤 준비가 끝났을 때 CPU가 회수하는 비동기 작업입니다. 상태만 초기화하면 이전 실행에서 시작한 픽셀 작업까지 자동으로 취소되지는 않습니다.

## 원인: 새 Tick 번호가 이전 읽기 요청보다 작아졌다

EO 화면은 드론 카메라를 그린 뒤 GPU 버퍼에 픽셀 읽기를 요청합니다. 마지막으로 요청한 시뮬레이션 Tick을 기억해 같은 Tick을 중복 요청하지 않도록 합니다. 정상 실행에서는 Tick 번호가 계속 증가하므로 이 기준이 동작합니다.

기록을 다시 시작하면 시뮬레이션 Tick은 0으로 돌아가지만, 픽셀 읽기 쪽의 마지막 요청 번호는 이전 실행의 큰 값으로 남아 있을 수 있습니다. 새 프레임 번호가 이 값보다 작으면 중복 방지 조건에 걸려 읽기 요청을 생략합니다. 이때 GPU에 이전 읽기가 남아 있다면 결과 회수 시점에 이전 세션과 새 세션의 픽셀을 구분하기도 어려워집니다.

화면 버퍼만 비우면 GPU 대기열에 남은 이전 결과가 새 실행의 프레임처럼 표시될 수 있습니다. 시뮬레이션 Tick, GPU 작업, 마지막 요청 번호와 표시 프레임을 세션이 바뀔 때 함께 초기화해야 합니다.

비동기 읽기에서는 현재 Tick의 카메라 장면과 CPU가 가진 최신 픽셀이 잠시 다를 수 있습니다. 새 세션에서 표시 버퍼만 비우면 GPU 대기열에 남은 과거 결과가 뒤늦게 도착할 수 있고, 요청 번호만 초기화하면 그 결과를 새 프레임으로 오인할 수 있습니다.

## 수정: 이전 GPU 작업을 마무리하고 새 세션 기준을 다시 설정

시뮬레이션 상태를 초기화하기 전에 진행 중인 픽셀 읽기를 마무리하고 결과를 회수하도록 했습니다. 그 다음 마지막 요청 Tick을 0으로 되돌리고, CPU 쪽에 보관한 EO 프레임도 비웁니다. 이후 첫 카메라 프레임은 새 실행의 Tick 기준으로 다시 요청됩니다.

이 순서는 기록 시작과 재생처럼 시뮬레이션 시간을 되돌리는 경로에서 사용합니다. GPU가 버퍼를 읽는 동안 앱이 같은 픽셀 메모리를 다시 사용하지 않도록 버퍼 수명도 유지합니다. 이는 프레임 번호 초기화와 버퍼 소유권을 서로 독립된 문제로 다루지 않기 위한 조치입니다.

재생 시작 시 대기 중인 읽기를 마무리하므로 그 순간에는 지연이 생길 수 있습니다. 매 프레임 GPU 완료를 기다리는 대신, 세션이 바뀌는 경계에서만 이전 결과를 정리합니다. 대기 요청이 여러 개이거나 창을 닫는 상황은 별도로 검증해야 합니다.

## 검증 결과와 현재 회귀 시험의 범위

수정 당시에는 재생 전후 프레임 번호가 어긋나는 경로를 반복해 10회 연속 확인했고, 당시 Release 전체 시험 20개도 통과했습니다. 현재 숨김 시뮬레이터 통합 시험은 UDP를 통한 기록 시작·비행 명령·기록 종료·재생 요청 흐름을 확인합니다.

현재 자동 시험은 OpenGL 읽기 대기열의 초기화와 EO 패널의 새 픽셀 표시를 직접 확인하지 않습니다. 과거 10회 반복은 수정 당시의 확인 결과이며, 이 그래픽 경로를 검사하는 회귀 시험은 현재 없습니다.

## 남은 한계와 재발 방지

- GPU가 읽기를 끝낸 시점과 화면에 새 영상이 나타나는 시점은 다를 수 있습니다.
- 숨김 창 시험은 실제 EO 패널의 프레임 갱신을 다루지 않습니다.
- 시뮬레이션 Tick을 0으로 되돌리는 새 경로를 추가할 때는 GPU 작업, 마지막 요청 번호, 표시 프레임도 같은 세션 기준으로 초기화되는지 확인해야 합니다.
- 새 실행의 첫 프레임이 늦게 나타나는 현상과 이전 프레임이 계속 표시되는 현상은 서로 다른 결과이므로 구분해 재현해야 합니다.
