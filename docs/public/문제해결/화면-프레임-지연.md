# EO 카메라 화면에서 간헐적으로 프레임이 멈춘 문제

## 증상

드론 화면과 EO 카메라를 함께 띄우면 평균 프레임 속도는 높았지만, 가끔 화면이 약 0.1초 멈췄습니다. 평균 FPS만 보면 괜찮아 보여도, 순간적으로 긴 프레임 하나가 조작감을 망가뜨리는 상황이었습니다.

## 먼저 의심한 곳

카메라 화면을 CPU 메모리로 가져오는 동기식 `glReadPixels`가 의심됐습니다. GPU가 화면을 다 그릴 때까지 CPU가 기다릴 수 있기 때문입니다. 초기 숨김 창 측정에서 픽셀을 읽은 프레임과 읽지 않은 프레임의 차이는 다음과 같았습니다.

| 측정 항목 | EO 픽셀 읽기가 있던 프레임 | EO 픽셀 읽기가 없던 프레임 |
| --- | ---: | ---: |
| 프레임 시간 p95 | 8.23ms | 2.66ms |
| 가장 긴 프레임 | 115.04ms | 7.06ms |
| 픽셀 읽기 호출 최댓값 | 111.20ms | 해당 없음 |

이 수치는 초기 한 번의 측정에서 얻었습니다. 픽셀을 읽는 프레임에서 지연이 더 컸지만, 두 범주의 조건이 완전히 같다는 뜻은 아니며 한 호출만으로 전체 원인을 확정할 수는 없습니다.

이 결과는 리드백이 문제에 관여할 가능성을 보여 줬지만, 특정 호출의 지연만으로 모든 긴 프레임의 원인이 확인된 것은 아니었습니다.

## 바꾼 뒤 드러난 맹점

CPU가 기다리는 일을 줄이려고 GPU 픽셀 버퍼 세 개를 돌려 쓰는 비동기 읽기 방식(PBO 링 버퍼)을 적용했습니다. GPU가 아직 결과를 만들고 있으면 그 프레임의 픽셀을 건너뛰고, 준비된 결과만 가져옵니다.

같은 PC와 장면에서 숨김 창으로 세 차례 다시 쟀습니다. 프레임 통계는 아래와 같습니다.

| 항목 | 세 차례 측정 범위 |
| --- | ---: |
| 평균 FPS | 360.8~362.5 |
| 프레임 p95 | 5.78~5.80ms |
| 프레임 p99 | 5.89~6.00ms |
| 프레임 최댓값 | 84.30~94.19ms |

세 번째 실행에서는 EO 픽셀 읽기가 없는 프레임도 84.30ms까지 늘어났습니다. 최신 단일 측정에서도 결과 확인 구간과 긴 프레임이 함께 나타났지만, 두 최댓값이 같은 프레임에서 나온 것인지 확인할 자료는 없었습니다.

세 번의 측정에서 각 처리 구간의 p95는 다음 범위였습니다.

| 처리 구간 | p95 범위 |
| --- | ---: |
| GPU에 새 픽셀 읽기 요청 | 약 2.35ms |
| 준비 상태 확인과 픽셀 결과 가져오기 | 약 2.35ms |
| OpenCV 영상 분석 | 3.17~3.21ms |

그래서 PBO 적용은 동기식 대기를 줄인 변경으로 볼 수 있어도, 화면 멈춤 전체를 해결했다고 말할 수는 없습니다. 결과 확인 구간에는 GPU 완료 확인과 픽셀 복사가 함께 있어 어느 쪽이 시간을 썼는지도 아직 분리되지 않았습니다.

## CPU 표본 기록에서 확인한 내용

원인을 더 좁히려고 Release 데모를 31.58초 동안 CPU 표본 방식으로 기록했습니다. 기록에는 이벤트 손실이 없었습니다. 표본 가중치에서 확인한 주요 항목은 다음과 같습니다.

| 표본에 나타난 영역 | WPA 출력 표본 가중치 | 확인한 내용 |
| --- | ---: | --- |
| Windows 커널, 기호 미해석 | 30,233,212 | 세부 호출 경로를 알 수 없음 |
| NVIDIA OpenGL 드라이버 | 3,228,266 | 드라이버 안의 CPU 표본이며 GPU 실행 시간이 아님 |
| 동시성 런타임 | 3,194,864 | 런타임 내부 표본 |
| OpenCV 영상 필터 | 2,993,883 | 영상 분석 경로에서 확인 |
| OpenCV 색상 변환 | 1,911,861 | RGB 변환 경로에서 확인 |
| 앱 코드 함수 | 458,141 | 긴 프레임과 연결되는 특정 호출은 확인되지 않음 |

이 기록의 전체 표본 가중치는 47,975,566입니다. 표본 가중치는 CPU에서 실행 중이던 시간을 추정하는 값이지, 함수 한 번의 경과 시간이 아닙니다. Windows 커널 표본의 기호를 충분히 해석하지 못했고 GPU 실행 시간도 수집하지 못했습니다. 따라서 이 기록만으로 그래픽 드라이버나 OpenCV를 범인으로 지목할 수 없습니다.

## 가장 최근 프레임에서 분리해 잰 구간

리비전 `23d537be`의 한 차례 화면 측정에서는 픽셀 결과를 확인한 프레임의 최댓값이 92.305ms였습니다. 확인할 픽셀이 없던 프레임은 최장 10.134ms였습니다. 구간별 최댓값은 아래처럼 나타났습니다.

| 구간 | 최댓값 |
| --- | ---: |
| 준비된 픽셀 결과 확인·복사 | 89.039ms |
| 새 픽셀 읽기 요청 제출 | 10.127ms |
| OpenCV 영상 분석 | 4.474ms |

이 최댓값들은 서로 다른 프레임에서 나왔을 수 있습니다. 특히 결과 확인 구간은 GPU 완료 확인과 CPU 복사를 함께 재므로, GPU 대기와 메모리 복사 중 어느 쪽이 시간을 썼는지는 아직 분리되지 않았습니다.

이 기록은 CPU가 실행 중 어느 영역에 머문 표본이 많았는지 보여 줍니다. 함수 한 번의 실행 시간은 아니며, CPU가 GPU를 기다린 시간과 GPU 자체의 실행 시간도 구분하지 못합니다. 커널 표본의 상당 부분은 기호를 해석하지 못해 세부 호출 경로를 알 수 없었습니다. 따라서 이 결과만으로 그래픽 드라이버나 OpenCV를 범인으로 지목할 수 없습니다.

## 지금까지 확인된 것

- 비동기 픽셀 읽기 뒤 일반 프레임의 p95·p99는 안정적이었지만, 드물게 긴 프레임은 남았습니다.
- 긴 프레임은 픽셀 읽기 결과 확인 구간에서 관찰된 적이 있지만, 읽기가 없는 프레임에서도 발생했습니다.
- CPU 표본에는 커널·드라이버·영상 분석 작업이 보였지만, 특정 작업과 긴 프레임을 같은 시각에 연결하지 못했습니다.
- 측정은 숨김 창과 한 대의 PC에서 진행했습니다. 실제 모니터에 표시할 때의 대기나 조작 입력부터 화면까지의 지연은 확인하지 않았습니다.

## 다음에 원인을 잡으려면

긴 프레임이 발생한 한 순간의 타임라인에서 화면 그리기, 버퍼 완료 확인, CPU 복사, OpenCV 분석, 화면 교체와 GPU 작업을 함께 봐야 합니다. 현재 프로젝트 측정에는 각 실행의 p50·p95·p99와 최댓값이 남지만, 이 구간들을 한 프레임 단위로 연결한 자료는 없습니다. GPU 실행과 CPU 대기를 분리해 기록할 수 있는 프로파일러로 같은 장면을 다시 측정해야 합니다.

세 차례 측정의 원본과 전체 성능 시험은 [화면 측정 결과](../../../benchmarks/results/aerosimlab-graphics-repeats-release-2026-10-23.json), [전체 Release 측정](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-23d537be.json)에서 확인할 수 있습니다. CPU 표본 기록은 관리자 권한으로 수집한 31.58초 ETL과 WPA 요약을 바탕으로 했습니다. ETL은 시스템 경로와 프로세스 정보를 포함할 수 있어 공개 저장소에 포함하지 않았습니다.
