# EO 카메라를 켜면 화면이 가끔 멈춘 문제

## 증상

드론 화면과 EO 카메라를 함께 띄우면 평균 프레임 속도는 높았지만, 화면이 간헐적으로 약 0.1초 멈췄습니다. 평균 FPS만으로는 이 현상을 설명하기 어려웠습니다. 대부분의 프레임은 빠르게 그려져도 긴 프레임 하나가 조작감과 화면 흐름을 끊을 수 있기 때문입니다.

## 측정 환경과 읽는 법

기록된 비교는 Windows Release 빌드에서 숨김 OpenGL 창으로 진행했습니다. 장면에는 드론 한 대, 약 18.8km × 23.7km 크기의 SRTM 지형, OSM 건물 상자 17개, 공원 시설물 49개가 있었습니다. 해상도는 1280 × 720이고, 그래픽 장치는 NVIDIA GeForce RTX 3060 Ti, 드라이버의 OpenGL 버전은 3.3.0 NVIDIA 581.42였습니다. 각 실행은 약 5초였습니다.

여기서 프레임 시간은 CPU가 한 프레임을 처리하는 데 걸린 시간입니다. p50은 표본의 절반이 이 값 이하였다는 뜻이고, p95·p99는 각각 95%·99%의 표본이 이 값 이하였다는 뜻입니다. 최댓값은 가장 긴 표본 하나입니다. 최댓값은 드문 멈춤을 찾는 데 유용하지만, 어떤 처리 때문에 늘어났는지는 그 값 하나만으로 알 수 없습니다.

숨김 창에서는 실제 모니터로 화면을 내보낼 때 생기는 수직 동기화나 디스플레이 대기를 측정하지 않습니다. 이 결과는 같은 프로그램 안의 렌더링·EO 픽셀 처리 경로를 비교하는 자료이며, 실제 화면에서의 조작 지연을 그대로 나타내지는 않습니다.

## 처음 의심한 곳: 동기식 픽셀 읽기

EO 카메라 화면을 영상 분석에 쓰려면 GPU가 그린 픽셀을 CPU 메모리로 가져와야 합니다. 처음에는 이때 사용하던 동기식 `glReadPixels`가 의심됐습니다. GPU가 화면 그리기를 마치고 픽셀을 넘길 때까지 CPU가 기다리면, 카메라를 읽는 프레임이 길어질 수 있습니다.

초기 5초 측정은 리비전 `b1cabc8c`에서 한 번 수행했습니다. 화면 전체에서 1,517개 프레임을 기록했고, 그중 293개는 EO 픽셀 읽기가 있었습니다. 읽기가 있는 프레임과 없는 프레임의 분포는 달랐습니다.

| 항목 | EO 픽셀 읽기 있음: 293개 | EO 픽셀 읽기 없음: 1,224개 |
| --- | ---: | ---: |
| 프레임 p50 | 6.076ms | 2.382ms |
| 프레임 p95 | 8.233ms | 2.661ms |
| 프레임 p99 | 14.911ms | 3.093ms |
| 프레임 최댓값 | 115.039ms | 7.058ms |
| 픽셀 읽기 호출 p95 / 최댓값 | 3.779ms / 111.203ms | 해당 없음 |

전체 프레임의 p50은 2.387ms, p95는 6.681ms, p99는 8.212ms였습니다. 대부분의 프레임은 짧았지만, 가장 긴 프레임은 115.039ms였습니다. 픽셀 읽기가 있던 프레임에서 긴 지연과 높은 백분위가 함께 나타났고, 픽셀 읽기 호출 자체도 최악의 경우 111.203ms였습니다.

이 결과는 동기식 읽기가 멈춤에 관여할 수 있다는 가설을 뒷받침했습니다. 다만 한 번의 측정이고 두 프레임 집단의 다른 작업량까지 통제하지는 않았습니다. 따라서 이때 확인한 것은 강한 연관성이며, 픽셀 읽기가 모든 멈춤의 유일한 원인이라는 증명은 아니었습니다.

## 비동기 읽기를 적용한 뒤

CPU가 픽셀을 기다리는 일을 줄이기 위해 GPU 버퍼 세 개를 차례로 쓰는 비동기 읽기 방식(PBO 링 버퍼)을 적용했습니다. GPU가 아직 결과를 만들지 않았다면 현재 프레임에서 픽셀 처리를 건너뛰고, 준비된 결과만 가져옵니다. 변경 뒤 같은 PC·장면·해상도로 세 번 반복 측정했습니다. 이 결과의 코드 리비전은 `1d76004d`입니다.

아래 표는 요약 범위 대신 각 실행을 따로 보여 줍니다. 시간은 밀리초이고, 프레임 표본 수도 함께 적었습니다.

| 실행 | 측정 시간 | 프레임 수 | FPS | 프레임 p50 | p95 | p99 | 프레임 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 5.002초 | 1,807 | 361.24 | 2.387 | 5.804 | 5.924 | 89.185 |
| 2 | 5.000초 | 1,804 | 360.78 | 2.387 | 5.803 | 6.001 | 94.189 |
| 3 | 5.002초 | 1,813 | 362.48 | 2.387 | 5.778 | 5.892 | 84.303 |

일반적인 프레임 시간은 세 번 모두 비슷했습니다. p95는 5.778~5.804ms, p99는 5.892~6.001ms였고, FPS는 360.78~362.48이었습니다. 하지만 최댓값은 84.303~94.189ms로 남았습니다. 백분위와 평균 FPS가 안정적이어도 드물게 화면이 멈추는 문제는 계속될 수 있다는 뜻입니다.

프레임을 픽셀 읽기 여부로 나눠 보면 실행별 차이가 더 잘 보입니다.

| 실행 | 읽기가 있던 프레임 수 | 해당 프레임 p95 | 해당 프레임 최댓값 | 읽기가 없던 프레임 수 | 해당 프레임 p95 | 해당 프레임 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 588 | 5.896ms | 89.185ms | 1,219 | 2.472ms | 3.437ms |
| 2 | 587 | 5.916ms | 94.189ms | 1,217 | 2.476ms | 5.308ms |
| 3 | 588 | 5.853ms | 6.452ms | 1,225 | 2.473ms | 84.303ms |

첫 번째와 두 번째 실행에서는 가장 긴 프레임이 픽셀 읽기가 있던 프레임에서 나왔습니다. 세 번째 실행에서는 반대로 픽셀 읽기가 없던 프레임에서 84.303ms가 나왔습니다. 따라서 PBO 적용 뒤에도 픽셀 읽기 경로가 긴 프레임에 관여할 가능성은 있지만, 모든 긴 프레임을 그 경로만으로 설명할 수는 없습니다.

## 처리 구간별로 확인한 결과

각 실행에서 새 픽셀 읽기 요청, 이전 결과 확인, OpenCV 분석을 따로 측정했습니다. p95는 평소 처리 시간을, 최댓값은 해당 실행에서 가장 긴 표본을 보여 줍니다.

| 실행 | 새 읽기 요청 p95 | 새 읽기 요청 최댓값 | 결과 확인 p95 | 결과 확인 최댓값 | 영상 분석 p95 | 영상 분석 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 2.355ms | 6.108ms | 2.349ms | 85.443ms | 3.177ms | 4.352ms |
| 2 | 2.351ms | 7.167ms | 2.345ms | 90.409ms | 3.208ms | 4.258ms |
| 3 | 2.362ms | 3.150ms | 2.356ms | 2.510ms | 3.166ms | 4.500ms |

1·2회차에는 결과 확인 구간의 최댓값이 각각 85.443ms와 90.409ms였습니다. 3회차의 같은 구간은 최댓값이 2.510ms였지만, 앞 표에서 확인했듯 EO 읽기가 없는 프레임이 84.303ms까지 늘었습니다. 각 구간의 최댓값은 같은 프레임에서 발생했다고 보장되지 않으므로, 이 수치들을 더하거나 긴 프레임의 원인을 단정하는 데 쓰면 안 됩니다.

OpenCV 분석의 p95는 세 번 모두 약 3.2ms였고, 최댓값도 4.258~4.500ms였습니다. 이 측정에서 영상 분석은 지속적인 수십 밀리초 지연을 설명하지 못합니다. 다만 별도의 CPU 표본 기록에는 OpenCV 작업도 나타났으므로, 모든 장면·상태에서 영향이 없다고 일반화하지는 않습니다.

## CPU 표본 기록은 원인을 확정하지 못했다

추가로 Release 데모를 31.58초 동안 Windows Performance Recorder로 기록하고 WPA에서 CPU 표본을 확인했습니다. 기록 손실은 없었습니다. 전체 표본 가중치는 47,975,566이었고, 주요 항목은 다음과 같습니다.

| WPA에서 묶인 영역 | 표본 가중치 | 해석과 한계 |
| --- | ---: | --- |
| Windows 커널, 기호 미해석 | 30,233,212 | 가장 큰 항목이지만, 세부 호출 경로를 해석하지 못함 |
| NVIDIA OpenGL 드라이버 | 3,228,266 | CPU가 드라이버 코드에서 실행된 표본이며 GPU 실행 시간이 아님 |
| 동시성 런타임 | 3,194,864 | 런타임 내부의 CPU 표본 |
| OpenCV 영상 필터 | 2,993,883 | 영상 분석 경로에서 관찰됨 |
| OpenCV 색상 변환 | 1,911,861 | 픽셀 색상 변환 경로에서 관찰됨 |
| 앱 코드 함수 | 458,141 | 특정 긴 프레임에 연결된 호출은 확인되지 않음 |

표본 가중치는 CPU가 어느 코드 영역에서 실행 중이었는지를 표본으로 추정한 값입니다. 함수 한 번의 실행 시간이나 GPU가 실제 계산한 시간으로 읽으면 안 됩니다. 특히 커널 표본의 기호를 해석하지 못했고, 긴 프레임이 발생한 시각과 표본을 프레임 단위로 연결하지 못했습니다. 이 기록으로 드라이버나 OpenCV를 원인으로 지목할 수는 없습니다.

## 다른 코드 시점의 측정

리비전 `23d537be`의 Release 측정은 위 세 번의 `1d76004d` 측정과 코드 시점이 다릅니다. 이 실행은 약 5초 동안 1,773프레임을 기록했습니다. 두 리비전은 같은 PC·장면·해상도를 썼지만, 코드 변경이 함께 들어간 상태라 PBO 효과만 분리한 엄밀한 전후 비교로 볼 수 없습니다.

| 프레임 구분 | 표본 수 | p50 | p95 | p99 | 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전체 | 1,773 | 2.402ms | 5.707ms | 5.878ms | 104.992ms |
| EO 결과 확인이 있던 프레임 | 579 | 4.056ms | 5.827ms | 5.952ms | 92.305ms |
| EO 결과 확인이 없던 프레임 | 1,194 | 2.379ms | 2.498ms | 2.618ms | 10.134ms |

| 처리 구간 | 표본 수 | p50 | p95 | p99 | 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 새 픽셀 읽기 요청 제출 | 290 | 2.168ms | 2.380ms | 2.432ms | 10.127ms |
| 이전 픽셀 결과 확인·복사 | 1,773 | 0.0001ms | 2.339ms | 2.453ms | 89.039ms |

이 실행에서도 EO 결과 확인 프레임과 결과 확인 구간의 최댓값은 각각 길게 측정됐습니다. 그러나 이들이 같은 프레임에서 발생했는지는 기록만으로 확인할 수 없습니다. 결과 확인 측정은 GPU 완료 확인과 CPU 메모리 복사를 한 구간에서 재기 때문에, 둘 중 무엇이 오래 걸렸는지도 분리되어 있지 않습니다.

## 현재 결론과 다음 확인

- 동기식 픽셀 읽기를 사용하던 초기 측정에서는 픽셀 읽기 프레임의 지연과 읽기 호출 최댓값이 컸습니다. 이는 해당 경로가 문제에 관여했다는 가설을 뒷받침하지만 단일 실행이므로 원인 전체를 확정하지는 않습니다.
- PBO를 적용한 세 실행에서는 일반 프레임의 p95·p99가 서로 비슷했지만, 최댓값은 매번 84ms 이상이었습니다. 따라서 화면 멈춤이 완전히 사라졌다고 할 수 없습니다.
- PBO 이후의 긴 프레임은 EO 읽기 프레임과 읽기 없는 프레임 양쪽에서 관찰됐습니다. 화면 처리 바깥의 작업이나 드라이버·운영체제 대기 등 다른 원인도 남아 있지만, 현재 자료만으로 어느 원인인지 확정할 수 없습니다.
- CPU 표본 기록에는 커널, 그래픽 드라이버, OpenCV가 나타났지만 프레임 타임라인과 연결되지 않았습니다. 표본 가중치를 함수 시간이나 GPU 시간으로 해석할 수도 없습니다.
- 모든 그래픽 측정은 숨김 창과 한 대의 PC에서 이뤄졌습니다. 실제 모니터에서 화면 교체까지 포함한 프레임 지연과 입력부터 화면까지의 체감 지연은 확인하지 않았습니다.

원인을 좁히려면 한 번의 긴 프레임에서 화면 그리기, PBO 완료 확인, CPU 복사, OpenCV 분석, 화면 교체와 GPU 작업을 같은 타임라인으로 연결해야 합니다. 현재 자료는 각 구간의 분포와 최댓값은 제공하지만, 각 값이 같은 프레임에서 발생했는지는 보여 주지 않습니다. 다음 프로파일링에서는 그 연결을 확인하고 CPU 대기와 GPU 실행 시간도 별도로 측정해야 합니다.

세 차례 반복 측정, 초기 픽셀 읽기 측정, 전체 Release 측정은 [원본 화면 성능 기록](../../../benchmarks/results/aerosimlab-graphics-repeats-release-2026-10-23.json), [초기 읽기 지연 기록](../../../benchmarks/results/aerosimlab-eo-readback-correlation-release-2026-10-23.json), [전체 측정 자료](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-23d537be.json)에서 확인할 수 있습니다. CPU 표본 내용은 관리자 권한으로 수집한 31.58초 ETL과 WPA 요약을 바탕으로 했습니다. ETL 원본에는 시스템 경로와 프로세스 정보가 포함될 수 있어 공개 자료에는 넣지 않았습니다.
