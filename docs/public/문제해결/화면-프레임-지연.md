# EO 카메라를 켜면 화면이 가끔 멈춘 문제

## 증상

드론 화면과 EO 카메라를 함께 띄우면 평균 프레임 속도는 높았지만, 화면이 간헐적으로 약 0.1초 멈췄습니다. 평균 FPS만으로는 이 현상을 설명하기 어려웠습니다. 대부분의 프레임은 빠르게 그려져도 긴 프레임 하나가 조작감과 화면 흐름을 끊을 수 있기 때문입니다.

## 측정 환경과 읽는 법

기록된 비교는 Windows Release 빌드에서 숨김 OpenGL 창으로 진행했습니다. 장면에는 드론 한 대, 약 18.8km × 23.7km 크기의 SRTM 지형, OSM 건물 상자 17개, 공원 시설물 49개가 있었습니다. 해상도는 1280 × 720이고, 그래픽 장치는 NVIDIA GeForce RTX 3060 Ti, 드라이버의 OpenGL 버전은 3.3.0 NVIDIA 581.42였습니다. 각 실행은 약 5초였습니다.

여기서 프레임 시간은 CPU가 한 프레임을 처리하는 데 걸린 시간입니다. p50은 표본의 절반이 이 값 이하였다는 뜻이고, p95·p99는 각각 95%·99%의 표본이 이 값 이하였다는 뜻입니다. 최댓값은 가장 긴 표본 하나입니다. 최댓값은 드문 멈춤을 찾는 데 유용하지만, 어떤 처리 때문에 늘어났는지는 그 값 하나만으로 알 수 없습니다.

숨김 창에서는 실제 모니터로 화면을 내보낼 때 생기는 수직 동기화나 디스플레이 대기를 측정하지 않습니다. 이 결과는 같은 프로그램 안의 렌더링·EO 픽셀 처리 경로를 비교하는 자료이며, 실제 화면에서의 조작 지연을 그대로 나타내지는 않습니다.

## 처음 의심한 곳: 동기식 픽셀 읽기

EO 카메라 화면을 영상 분석에 쓰려면 GPU가 그린 픽셀을 CPU 메모리로 가져와야 합니다. 처음에는 이때 사용하던 동기식 `glReadPixels`가 의심됐습니다. GPU가 화면 그리기를 마치고 픽셀을 넘길 때까지 CPU가 기다리면, 카메라를 읽는 프레임이 길어질 수 있습니다.

초기 5초 측정은 리비전 `b1cabc8c`에서 한 번 수행했습니다. 화면 전체에서 1,517개 프레임을 기록했고, 그중 293개는 EO 픽셀 읽기가 있었습니다. 읽기가 있는 프레임과 없는 프레임의 분포는 달랐습니다.

| 항목 | EO 픽셀 읽기 있음: 293개 | EO 픽셀 읽기 없음: 1,224개 |
| --- | ---: | ---: |
| 프레임 p50 | 6.076ms | 2.382ms |
| 프레임 p95 | 8.233ms | 2.661ms |
| 프레임 p99 | 14.911ms | 3.093ms |
| 프레임 최댓값 | 115.039ms | 7.058ms |
| 픽셀 읽기 호출 p95 / 최댓값 | 3.779ms / 111.203ms | 해당 없음 |

전체 프레임의 p50은 2.387ms, p95는 6.681ms, p99는 8.212ms였습니다. 대부분의 프레임은 짧았지만, 가장 긴 프레임은 115.039ms였습니다. 픽셀 읽기가 있던 프레임에서 긴 지연과 높은 백분위가 함께 나타났고, 픽셀 읽기 호출 자체도 최악의 경우 111.203ms였습니다.

이 결과는 동기식 읽기가 멈춤에 관여할 수 있다는 가설을 뒷받침했습니다. 다만 한 번의 측정이고 두 프레임 집단의 다른 작업량까지 통제하지는 않았습니다. 따라서 이때 확인한 것은 강한 연관성이며, 픽셀 읽기가 모든 멈춤의 유일한 원인이라는 증명은 아니었습니다.

## 비동기 읽기를 적용한 뒤

CPU가 픽셀을 기다리는 일을 줄이기 위해 GPU 버퍼 세 개를 차례로 쓰는 비동기 읽기 방식(PBO 링 버퍼)을 적용했습니다. GPU가 아직 결과를 만들지 않았다면 현재 프레임에서 픽셀 처리를 건너뛰고, 준비된 결과만 가져옵니다. 변경 뒤 같은 PC·장면·해상도로 세 번 반복 측정했습니다. 이 결과의 코드 리비전은 `1d76004d`입니다.

아래 표는 요약 범위 대신 각 실행을 따로 보여 줍니다. 시간은 밀리초이고, 프레임 표본 수도 함께 적었습니다.

| 실행 | 측정 시간 | 프레임 수 | FPS | 프레임 p50 | p95 | p99 | 프레임 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 5.002초 | 1,807 | 361.24 | 2.387 | 5.804 | 5.924 | 89.185 |
| 2 | 5.000초 | 1,804 | 360.78 | 2.387 | 5.803 | 6.001 | 94.189 |
| 3 | 5.002초 | 1,813 | 362.48 | 2.387 | 5.778 | 5.892 | 84.303 |

일반적인 프레임 시간은 세 번 모두 비슷했습니다. p95는 5.778~5.804ms, p99는 5.892~6.001ms였고, FPS는 360.78~362.48이었습니다. 하지만 최댓값은 84.303~94.189ms로 남았습니다. 백분위와 평균 FPS가 안정적이어도 드물게 화면이 멈추는 문제는 계속될 수 있다는 뜻입니다.

프레임을 픽셀 읽기 여부로 나눠 보면 실행별 차이가 더 잘 보입니다.

| 실행 | 읽기가 있던 프레임 수 | 해당 프레임 p95 | 해당 프레임 최댓값 | 읽기가 없던 프레임 수 | 해당 프레임 p95 | 해당 프레임 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 588 | 5.896ms | 89.185ms | 1,219 | 2.472ms | 3.437ms |
| 2 | 587 | 5.916ms | 94.189ms | 1,217 | 2.476ms | 5.308ms |
| 3 | 588 | 5.853ms | 6.452ms | 1,225 | 2.473ms | 84.303ms |

첫 번째와 두 번째 실행에서는 가장 긴 프레임이 픽셀 읽기가 있던 프레임에서 나왔습니다. 세 번째 실행에서는 반대로 픽셀 읽기가 없던 프레임에서 84.303ms가 나왔습니다. 따라서 PBO 적용 뒤에도 픽셀 읽기 경로가 긴 프레임에 관여할 가능성은 있지만, 모든 긴 프레임을 그 경로만으로 설명할 수는 없습니다.

## 처리 구간별로 확인한 결과

각 실행에서 새 픽셀 읽기 요청, 이전 결과 확인, OpenCV 분석을 따로 측정했습니다. p95는 평소 처리 시간을, 최댓값은 해당 실행에서 가장 긴 표본을 보여 줍니다.

| 실행 | 새 읽기 요청 p95 | 새 읽기 요청 최댓값 | 결과 확인 p95 | 결과 확인 최댓값 | 영상 분석 p95 | 영상 분석 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 2.355ms | 6.108ms | 2.349ms | 85.443ms | 3.177ms | 4.352ms |
| 2 | 2.351ms | 7.167ms | 2.345ms | 90.409ms | 3.208ms | 4.258ms |
| 3 | 2.362ms | 3.150ms | 2.356ms | 2.510ms | 3.166ms | 4.500ms |

1·2회차에는 결과 확인 구간의 최댓값이 각각 85.443ms와 90.409ms였습니다. 3회차의 같은 구간은 최댓값이 2.510ms였지만, 앞 표에서 확인했듯 EO 읽기가 없는 프레임이 84.303ms까지 늘었습니다. 각 구간의 최댓값은 같은 프레임에서 발생했다고 보장되지 않으므로, 이 수치들을 더하거나 긴 프레임의 원인을 단정하는 데 쓰면 안 됩니다.

OpenCV 분석의 p95는 세 번 모두 약 3.2ms였고, 최댓값도 4.258~4.500ms였습니다. 이 측정에서 영상 분석은 지속적인 수십 밀리초 지연을 설명하지 못합니다. 다만 별도의 CPU 표본 기록에는 OpenCV 작업도 나타났으므로, 모든 장면·상태에서 영향이 없다고 일반화하지는 않습니다.

## CPU 표본 기록은 원인을 확정하지 못했다

추가로 Release 데모를 31.58초 동안 Windows Performance Recorder로 기록하고 WPA에서 CPU 표본을 확인했습니다. 기록 손실은 없었습니다. 전체 표본 가중치는 47,975,566이었고, 주요 항목은 다음과 같습니다.

| WPA에서 묶인 영역 | 표본 가중치 | 해석과 한계 |
| --- | ---: | --- |
| Windows 커널, 기호 미해석 | 30,233,212 | 가장 큰 항목이지만, 세부 호출 경로를 해석하지 못함 |
| NVIDIA OpenGL 드라이버 | 3,228,266 | CPU가 드라이버 코드에서 실행된 표본이며 GPU 실행 시간이 아님 |
| 동시성 런타임 | 3,194,864 | 런타임 내부의 CPU 표본 |
| OpenCV 영상 필터 | 2,993,883 | 영상 분석 경로에서 관찰됨 |
| OpenCV 색상 변환 | 1,911,861 | 픽셀 색상 변환 경로에서 관찰됨 |
| 앱 코드 함수 | 458,141 | 특정 긴 프레임에 연결된 호출은 확인되지 않음 |

표본 가중치는 CPU가 어느 코드 영역에서 실행 중이었는지를 표본으로 추정한 값입니다. 함수 한 번의 실행 시간이나 GPU가 실제 계산한 시간으로 읽으면 안 됩니다. 특히 커널 표본의 기호를 해석하지 못했고, 긴 프레임이 발생한 시각과 표본을 프레임 단위로 연결하지 못했습니다. 이 기록으로 드라이버나 OpenCV를 원인으로 지목할 수는 없습니다.

## 픽셀 읽기 요청의 상태 조회를 줄인 뒤

PBO 적용만으로 긴 프레임이 사라지지 않아 새 픽셀 요청 경로를 더 잘게 나눠 측정했습니다. 요청을 넣기 전에는 현재 OpenGL 상태를 보존하려고 `glGetIntegerv`를 네 번 호출하고 있었습니다. 측정 결과 이 상태 조회 구간의 CPU 호출 시간은 중앙값 2.220ms, p95 2.363ms였습니다. 같은 요청 안의 버퍼 설정과 상태 복구는 대부분 마이크로초 단위였고, `glReadPixels` 자체의 중앙값은 54.6µs였습니다.

이 경로를 호출하는 곳을 확인해 보니 화면 그리기가 끝난 뒤 기본 프레임버퍼로 돌아온 상태에서만 픽셀 읽기를 요청하고 있었습니다. 그래서 임의의 OpenGL 상태를 저장하고 복원하는 대신, 호출부가 보장하는 기본 상태인 읽기 프레임버퍼 0, `GL_BACK`, 픽셀 정렬 4, 픽셀 전송 버퍼 0으로 되돌리도록 바꿨습니다. 이 변경은 해당 호출 경로의 상태 계약을 전제로 합니다.

같은 Release 빌드와 숨김 창, 1280×720 장면에서 각각 5초간 실행한 결과입니다. 첫 측정은 상태 조회를 제거하기 전이고, 뒤의 두 측정은 제거한 코드로 반복했습니다.

| 실행 | 앱 프레임 p50 / p95 / 최댓값 | 새 픽셀 요청 p50 / p95 / 최댓값 | 결과 확인 p95 / 최댓값 |
| --- | ---: | ---: | ---: |
| 상태 조회 제거 전 | 2.418 / 5.633 / 90.611ms | 2.283 / 2.426 / 90.241ms | 2.321 / 3.212ms |
| 제거 후 1회차 | 2.399 / 5.552 / 108.743ms | 0.064 / 2.380 / 108.367ms | 2.202 / 2.628ms |
| 제거 후 2회차 | 2.418 / 5.666 / 94.157ms | 2.282 / 2.429 / 5.360ms | 2.333 / 90.616ms |

첫 번째 실행에서는 요청 중앙값이 2.283ms에서 64µs로 줄었습니다. 하지만 두 번째 실행의 요청 중앙값은 다시 약 2.282ms였고, 이때는 `glReadPixels` 호출의 중앙값이 2.276ms였습니다. 반대로 제거 후 첫 실행에서는 요청을 넣는 쪽의 최댓값이 108.367ms였고, 두 번째 실행에서는 이전 결과를 확인하는 쪽에서 90.616ms가 나왔습니다. 긴 대기가 어느 호출에서 보이는지는 실행마다 달랐습니다.

세 실행의 앱 프레임 중앙값과 p95는 비슷한 범위였지만, 최댓값은 모두 90ms를 넘었습니다. 따라서 상태 조회 제거는 첫 실행의 일반적인 요청 비용을 낮춘 흔적을 보였으나, 화면 전체가 빨라졌거나 멈춤이 해결됐다고 결론 내릴 수는 없습니다. CPU 호출 시간을 측정한 결과이므로 이 수치만으로 GPU 작업 시간이나 드라이버 내부의 대기 원인을 특정할 수도 없습니다. 현재 자료는 지연이 요청 제출과 결과 확인 사이에서 다르게 나타날 수 있음을 보여 주는 정도입니다.

상태 조회 제거 전후와 반복 실행의 세부 호출 통계는 [상태 조회 진단 기록](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-0de5d066-dirty-state-query-diagnostic.json), [제거 후 첫 실행](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-0de5d066-dirty-state-query-removed.json), [제거 후 두 번째 실행](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-0de5d066-dirty-state-query-removed-repeat-2.json)에서 확인할 수 있습니다.

## 완료된 EO 픽셀 버퍼를 매핑할 때 생기던 긴 대기

보이는 창을 다시 측정한 뒤에도 84~101ms짜리 프레임이 남았습니다. 이때는 프레임 전체 시간만 기록하지 않고, 한 프레임 안에서 EO 결과를 기다리고 PBO를 매핑하고 픽셀을 복사하는 시간을 나눠 쟀습니다. PBO는 GPU가 화면 픽셀을 임시로 써 두는 버퍼입니다.

### 증상과 확인

변경 전 Release 빌드(`f4b11b75`)에서 같은 장면을 5초씩 세 번 실행했습니다. 1280×720 보이는 창, VSync 끔, 자동 비행, RTX 3060 Ti 조건이었습니다. 세 실행의 초당 프레임 수는 약 366~367이었고, 모두 97~102ms짜리 프레임이 있었습니다.

세 실행 중 두 번은 같은 프레임에서 `glMapBufferRange` 호출이 약 96ms를 차지했습니다. 그 프레임의 fence 확인은 약 2µs, CPU 픽셀 복사는 약 0.2ms였습니다. GPU 작업 완료를 기다린 시간이나 복사 시간이 아니라, 이미 완료된 PBO를 CPU가 읽을 수 있게 매핑하는 호출에서 긴 지연이 발생한 셈입니다. 나머지 한 실행에는 EO 읽기가 없는 프레임도 약 97ms까지 늘어났습니다. 따라서 매핑은 긴 프레임 중 일부를 설명하지만 전체 원인은 아니었습니다.

| 변경 전 실행 | 앱 프레임 p50 | p95 | 최댓값 | 매핑 호출 최댓값 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 2.381ms | 5.801ms | 97.424ms | 10.822ms |
| 2 | 2.399ms | 3.919ms | 100.370ms | 95.783ms |
| 3 | 2.394ms | 5.823ms | 101.534ms | 96.829ms |

이 측정으로 확인한 원인은 특정 PBO 매핑 호출이 오래 걸린 현상입니다. 드라이버 내부에서 왜 그런 대기가 생겼는지까지는 확인하지 못했습니다. fence가 완료됐다고 해서 매핑 호출 시간이 항상 짧아지는 것은 아니었습니다.

### 시도와 수정

먼저 fence 신호가 온 뒤라면 매핑의 동기화를 생략할 수 있는지 확인했습니다. 하지만 `GL_MAP_UNSYNCHRONIZED_BIT`는 `GL_MAP_READ_BIT`와 함께 쓸 수 없습니다. 이 조합을 시험했을 때 EO 영상에 픽셀이 들어오지 않아 Viewer 스모크와 시뮬레이터 통합 시험이 실패했고, 원래 매핑 옵션으로 되돌리자 두 시험이 다시 통과했습니다. [OpenGL 명세](https://registry.khronos.org/OpenGL/specs/gl/glspec45.core.withchanges.pdf)는 읽기 매핑에 이 옵션을 함께 쓸 수 없다고 규정합니다.

대신 `GL_ARB_buffer_storage`를 지원하는 그래픽 환경에서는 PBO를 `GL_MAP_PERSISTENT_BIT`와 `GL_MAP_COHERENT_BIT`로 한 번 매핑하고, 각 프레임의 fence가 끝난 뒤 그 주소에서 픽셀을 복사하도록 바꿨습니다. 매 프레임 매핑을 열고 닫는 호출을 없앤 것입니다. 이 확장을 지원하지 않는 환경에서는 기존 매핑 경로를 그대로 사용합니다. 크기가 바뀌거나 프레임버퍼를 없앨 때는 진행 중인 읽기를 끝낸 다음 매핑을 해제합니다.

### 검증 결과와 남은 지연

수정한 Release 빌드(`2ac11e99`)에서 같은 조건으로 세 번 더 측정했습니다. per-frame 매핑 단계의 최댓값은 세 번 모두 0.1µs였습니다. 이 값은 지속 매핑을 사용할 때 매 프레임 실제 GL 매핑을 호출한 시간이 아니라, 기존 계측 구간 안에서 이미 만들어 둔 메모리 주소를 가져오는 데 든 시간입니다. 초기 매핑은 버퍼를 준비할 때 한 번 수행합니다.

| 변경 후 실행 | 앱 프레임 p50 | p95 | 최댓값 | 프레임별 매핑 단계 최댓값 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 2.399ms | 3.889ms | 96.131ms | 0.1µs |
| 2 | 2.398ms | 3.740ms | 97.433ms | 0.1µs |
| 3 | 2.402ms | 3.663ms | 100.873ms | 0.1µs |

세 번 모두 픽셀 읽기가 계속됐고 전체 CTest 20개와 Viewer 스모크가 통과했습니다. 변경 전후의 앱 프레임 p50은 비슷했고, p95는 변경 후 세 번 모두 3.7~3.9ms 범위였습니다. 측정한 매핑 지연은 사라졌지만 긴 프레임은 남았으므로, 전체 화면 멈춤을 해결했다고 볼 수는 없습니다. 실행 처리량도 변경 후 약 377~404FPS로 편차가 있어, 이 결과만으로 전체 성능이 그만큼 개선됐다고 단정하지 않습니다. 현재 PC에서는 지속 매핑 기능을 확인했지만, 이 기능을 지원하지 않는 그래픽 환경에서 기존 매핑 경로가 동작하는지는 별도 장비로 검증하지 않았습니다.

수정 후 세 번 모두 가장 긴 프레임은 `RenderFrame` 전체에서 약 96~100ms였고, 장면 패널 그리기는 약 20µs, 카메라 장면 그리기는 해당 프레임에서 실행되지 않았습니다. EO 읽기 처리 구간은 약 3.5~3.6ms였고, 매핑·fence·복사는 이 프레임 지연을 설명하지 못했습니다. 현재 계측은 `RenderFrame` 안의 남은 작업을 충분히 나누지 않아, 어느 하위 호출이나 시스템 대기가 원인인지는 미확인입니다. 다음에는 이 구간을 더 나눠 같은 프레임의 호출 시간으로 확인해야 합니다.

비교 전후의 세 번씩 측정한 원본은 [PBO 매핑 변경 성능 결과](../../../benchmarks/results/aerosimlab-visible-pbo-persistent-map-2026-10-23.json)에 함께 보관했습니다. 여기 기록한 시간은 CPU가 각 호출에서 보낸 벽시계 시간입니다. GPU 실행 시간이나 모니터에 실제로 표시된 시각은 측정하지 않았습니다.

## 현재 결론과 다음 확인

- 동기식 픽셀 읽기를 사용하던 초기 측정에서는 픽셀 읽기 프레임의 지연과 읽기 호출 최댓값이 컸습니다. 이는 해당 경로가 문제에 관여했다는 가설을 뒷받침하지만 단일 실행이므로 원인 전체를 확정하지는 않습니다.
- PBO를 적용한 세 실행에서는 일반 프레임의 p95·p99가 서로 비슷했지만, 최댓값은 매번 84ms 이상이었습니다. 따라서 화면 멈춤이 완전히 사라졌다고 할 수 없습니다.
- PBO 이후의 긴 프레임은 EO 읽기 프레임과 읽기 없는 프레임 양쪽에서 관찰됐습니다. 화면 처리 바깥의 작업이나 드라이버·운영체제 대기 등 다른 원인도 남아 있지만, 현재 자료만으로 어느 원인인지 확정할 수 없습니다.
- CPU 표본 기록에는 커널, 그래픽 드라이버, OpenCV가 나타났지만 프레임 타임라인과 연결되지 않았습니다. 표본 가중치를 함수 시간이나 GPU 시간으로 해석할 수도 없습니다.
- 이번에는 창을 실제로 띄운 상태에서도 세 차례 측정했습니다. 앱 프레임의 p50은 2.385~2.399ms였고, p95는 3.938~5.827ms, 최댓값은 96.916~100.910ms였습니다. 평균 처리량은 세 번 모두 약 367FPS였습니다. 보이는 창에서도 긴 프레임이 남았다는 점은 확인했지만, VSync를 끈 측정이라 모니터 표시 타이밍이나 입력부터 화면까지의 지연을 잰 것은 아닙니다.
- 상태 조회를 줄인 뒤에도 앱 프레임의 최댓값은 90ms 이상이었고, 요청 제출과 결과 확인 중 긴 시간이 기록된 위치는 반복 실행마다 달랐습니다. 따라서 상태 조회는 일부 실행의 요청 중앙값에 영향을 줬지만, 긴 프레임의 원인 전체로 볼 수는 없습니다.
- PBO를 지속 매핑한 뒤 세 번의 실행에서 프레임별 매핑 단계는 0.1µs 이하였지만, 프레임 최댓값은 여전히 96~101ms였습니다. 최근 긴 프레임은 렌더 호출에 집중됐고, 장면 패널 그리기 시간과 EO 읽기 세부 시간은 그 길이를 설명하지 못했습니다. 렌더 호출 내부의 남은 작업은 아직 나눠 측정하지 않았습니다.
- 보이는 창 측정도 화면 표시가 끝난 시각이나 GPU 내부 실행 시간을 직접 재지는 않았습니다. Windows Performance Recorder는 이번에도 시스템 성능 프로파일링 권한을 활성화하지 못해 새 ETL 기록을 만들지 못했습니다. 긴 프레임과 CPU·GPU 작업을 같은 타임라인으로 연결하는 일은 아직 남아 있습니다.

다음 확인은 `RenderFrame` 내부 작업을 긴 프레임별로 나눠 기록하는 것입니다. 그 결과를 Windows 프로파일러의 CPU 타임라인과 연결하면 앱 코드 실행, 운영체제 대기, 드라이버 호출 중 어느 구간에서 시간이 늘어났는지 더 좁힐 수 있습니다. 현재 자료로는 GPU 실행 시간과 실제 화면 표시 지연을 판단할 수 없습니다.

세 차례 반복 측정, 초기 픽셀 읽기 측정, 전체 Release 측정은 [원본 화면 성능 기록](../../../benchmarks/results/aerosimlab-graphics-repeats-release-2026-10-23.json), [초기 읽기 지연 기록](../../../benchmarks/results/aerosimlab-eo-readback-correlation-release-2026-10-23.json), [전체 측정 자료](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-23d537be.json)에서 확인할 수 있습니다. 이번 보이는 창의 세 실행별 원본 데이터는 [보이는 창 측정 결과](../../../benchmarks/results/aerosimlab-visible-gui-release-2026-10-23.json)에 모았습니다. CPU 표본 내용은 관리자 권한으로 수집한 31.58초 ETL과 WPA 요약을 바탕으로 했습니다. ETL 원본에는 시스템 경로와 프로세스 정보가 포함될 수 있어 공개 자료에는 넣지 않았습니다.
