# EO 카메라 화면을 읽을 때 프레임이 멈춘 문제

## 처음 나타난 현상

드론 화면과 EO 카메라를 함께 띄웠을 때 평균 프레임 속도는 높았지만, 가끔 화면이 0.1초가량 멈췄습니다. 당시에는 카메라 픽셀을 화면을 그리는 과정에서 바로 읽고 있었습니다.

5초 측정에서 EO 픽셀을 읽은 프레임은 p95가 8.23ms, 최장 115.04ms였습니다. 읽지 않은 프레임의 p95는 2.66ms, 최장은 7.06ms였습니다. 픽셀을 읽는 호출 하나가 최장 111.20ms 걸린 기록도 있었습니다. 같은 실행에서 화면 멈춤과 픽셀 읽기 지연이 함께 나타났습니다.

## 원인과 변경

동기식 `glReadPixels`는 GPU가 화면을 준비할 때까지 CPU를 기다리게 할 수 있습니다. 이를 줄이기 위해 픽셀을 세 칸의 GPU 버퍼에 차례로 맡기고, 완료 신호가 온 뒤 준비된 결과만 가져오도록 바꿨습니다. GPU가 아직 읽는 중이면 기다리지 않고 다음 화면 처리를 계속합니다.

## 변경 뒤 측정

같은 PC와 장면에서 숨김 창으로 5초씩 세 번 측정했습니다. 평균 FPS는 360.8~362.5였고, 프레임 p95는 5.78~5.80ms, p99는 5.89~6.00ms였습니다. 하지만 프레임 최댓값은 여전히 84.30~94.19ms였습니다. 이전 측정보다 p95·p99는 낮았지만 코드 리비전이 달라 이 차이를 버퍼 방식 하나의 효과라고 단정할 수 없습니다. 긴 멈춤도 해결되지 않았습니다.

픽셀을 GPU에 맡기는 시간과 준비 상태를 확인하는 시간은 각각 p95 약 2.35ms였습니다. 영상 분석 시간은 p95 3.17~3.21ms였습니다. 실행별 측정값은 [화면·카메라 측정 결과](../../../benchmarks/results/aerosimlab-graphics-repeats-release-2026-10-23.json)에 있습니다.

여기서 프레임 시간은 그리기와 화면 교체에 걸린 시간입니다. 입력 확인과 시뮬레이션 갱신까지 포함한 앱 프레임 전체 시간도 따로 측정합니다. 현재 Release 측정은 리비전 `8faf19f5`에서 숨김 창으로 한 번 진행했습니다. 5초 동안 1,767프레임을 그렸고 평균은 353.38FPS였습니다. 앱 프레임 p50·p95·p99는 2.401·5.697·5.951ms, 최댓값은 105.986ms였습니다. 그리기와 화면 교체만 잰 값은 p50·p95·p99 2.386·5.684·5.922ms, 최댓값 95.770ms였습니다. 반복 측정이 아니며 화면에 실제로 표시했을 때의 입력 반응을 측정한 것도 아닙니다. 실행 조건과 전체 확장성 표본은 [이번 Release 측정 결과](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-8faf19f5.json)에 있습니다.

원인을 좁히려고 실행별 최댓값도 확인했습니다. 첫 두 실행에서는 EO 픽셀 읽기가 있던 프레임 범주에서 89.19ms와 94.19ms가 기록됐고, 결과 확인 구간의 최댓값도 각각 85.44ms와 90.41ms였습니다. 세 번째 실행은 EO 픽셀 읽기가 없던 프레임에서 84.30ms가 나왔고, 결과 확인 구간은 최장 2.51ms였습니다. 이 값들은 실행별 최댓값이라 서로 같은 프레임에서 발생했다고 확인할 수 없습니다. 따라서 픽셀 결과 확인이 두 번의 긴 프레임에 관여했을 가능성은 있지만, 전체 원인으로 확정할 수는 없습니다.

## 성능 측정이 오래 걸리는 이유

`--benchmark`는 화면을 5초 동안 측정한 뒤 바로 끝나지 않습니다. 이어서 운동학과 AirSim 강체 방식, 분리·밀집 배치, 공동 임무의 확장성 시험을 실행합니다. 드론 수마다 세 번 반복하고, 일부 실행은 한 번에 최대 30초까지 측정하므로 전체 실행은 몇 분 걸릴 수 있습니다. 결과 파일도 모든 시험이 끝난 뒤 저장됩니다.

현재 Release 리비전으로 실행한 전체 시험은 4분 15초 걸렸습니다. 화면 측정은 5.00초였고 평균 353.38FPS였습니다. 앱 프레임 p95는 5.697ms, p99는 5.951ms, 최댓값은 105.986ms였습니다. 강체 분리 배치 1,024대는 27,000 Tick, 밀집 배치 256대는 25,000 Tick을 각각 한 번 측정한 뒤 30초 제한으로 멈췄습니다. 밀집 128대는 30,000 Tick을 3회 마쳤습니다. `elapsed_seconds`는 전체 실행 시간이 아니라 화면 측정 5초를 나타냅니다. 반복별 결과와 실행 환경은 [이번 Release 측정 원본](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-8faf19f5.json)에 있습니다. 변경 전 원본은 [이전 Release 측정](../../../benchmarks/results/aerosimlab-full-benchmark-release-2026-10-23-e13116a9.json)에서 확인할 수 있습니다.

처음에는 15초 안에 끝나지 않는 것을 멈춤으로 잘못 판단해 세 번 실행을 중단했습니다. 이 시간 안에 결과가 없었던 것은 전체 시험이 끝나기 전이었기 때문입니다. 이전에 보인 긴 프레임 문제와 이 실행 시간은 별개입니다. 실행 옵션 안내도 전체 시험에 걸리는 시간을 충분히 설명하지 못해 함께 고쳤습니다.

## CPU 병목을 프로파일러로 찾기

기본 측정 결과는 프레임·Tick·물리·영상 처리 구간에 각각 얼마나 걸렸는지 보여줍니다. 어느 함수가 CPU 시간을 많이 쓰는지는 Visual Studio의 CPU Usage 프로파일러로 찾을 수 있습니다. 이 도구는 코드를 수정하거나 타이머를 추가하지 않고 CPU 실행 중의 호출 경로를 표본으로 모읍니다.

1. Visual Studio에서 `Alt+F2`를 눌러 성능 프로파일러를 엽니다.
2. `CPU Usage`를 선택하고 AeroSimLab 시뮬레이터를 실행 대상으로 골라 수집을 시작합니다.
3. 느려지는 장면을 재현한 뒤 수집을 멈춥니다.
4. 호출 트리나 불꽃 그래프에서 `Self CPU`가 큰 함수를 먼저 살펴봅니다. `Total CPU`는 그 함수가 호출한 다른 함수의 시간까지 합친 값입니다.

표본 방식은 코드에 타이머를 직접 심는 방식보다 실행에 미치는 영향이 작지만, 함수 한 번의 정확한 실행 시간을 재지는 않습니다. 소스 줄까지 확인하려면 실행 파일과 같은 Release 빌드에서 나온 디버그 기호가 필요합니다. 이 프로젝트는 OpenGL을 사용하므로 Visual Studio의 GPU Usage 도구로 GPU 실행 시간을 측정할 수 없습니다. CPU 프로파일 결과와 실제 프레임 시간을 함께 봐야 합니다. [Visual Studio CPU 프로파일러 안내](https://learn.microsoft.com/en-us/visualstudio/profiling/cpu-usage?view=vs-2022) · [GPU Usage 지원 그래픽 API](https://learn.microsoft.com/en-us/visualstudio/profiling/gpu-usage?view=visualstudio)

현재 문서의 측정값은 프로젝트 내 벤치마크 결과입니다. Visual Studio CPU 프로파일러로 수집한 결과는 아직 없으므로, 함수별 병목을 확인한 것으로 해석하면 안 됩니다.

## 남은 한계

- 측정은 숨김 창과 한 대의 그래픽 카드에서 진행했습니다. 실제 화면이 보일 때의 반응과 조종 입력부터 화면까지 걸리는 시간은 확인하지 않았습니다.
- 드라이버나 그래픽 카드가 달라져도 같은 결과가 나는지는 확인하지 않았습니다.
- GPU가 세 버퍼를 모두 사용 중이면 새 픽셀 읽기를 건너뜁니다. 영상 분석에 모든 화면이 전달된다고 보장하지 않습니다.
- 드물게 긴 프레임의 원인을 확정하려면 같은 프레임에서 픽셀 확인, 화면 교체, CPU 대기와 GPU 실행 시간을 연결해 기록해야 합니다.
