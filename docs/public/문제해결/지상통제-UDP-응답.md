# 명령줄에서는 응답을 받았지만 지상통제 창에서는 시간 초과된 문제

## 증상: 같은 주소와 포트인데 창만 응답을 기다리다 끝났다

시뮬레이터는 UDP 요청을 받는 중이었고, 같은 주소와 포트를 지정한 명령줄 프로그램은 응답을 받았습니다. 반면 Windows 지상통제 창은 응답 시간 초과를 표시했습니다. 겉으로 보면 두 클라이언트가 같은 요청 형식을 사용하므로 주소나 서버 포트 설정만 비교해서는 차이를 설명할 수 없었습니다.

UDP는 데이터그램을 보내도 전달이나 응답을 보장하지 않습니다. 창에 시간 초과가 표시됐다는 사실만으로는 다음 세 경우를 구분할 수 없습니다.

1. 요청이 시뮬레이터에 도착하지 않았습니다.
2. 요청은 처리됐지만 응답이 돌아오지 않았습니다.
3. 응답은 돌아왔지만 창이 다른 요청의 응답으로 판단해 사용하지 않았습니다.

따라서 증상만으로 포트 오류나 Windows 방화벽을 원인으로 확정할 수 없었습니다.

## 원인을 좁힌 과정: 요청 형식보다 소켓과 작업의 수명이 달랐다

명령줄 프로그램은 요청과 응답을 한 흐름에서 처리했습니다. 창은 화면이 멈추지 않도록 UDP 요청을 별도 작업으로 보내고, UI 스레드는 타이머가 완료 여부를 확인하는 구조였습니다. 이 차이 때문에 화면 갱신이 계속되는 동안 소켓과 비동기 작업이 언제 만들어지고 정리되는지가 중요했습니다.

초기 창 구현은 요청을 보낼 때마다 UDP 소켓을 열고 닫았습니다. 반면 명령줄 프로그램과 시뮬레이터는 소켓을 각 실행 흐름에서 더 오래 유지했습니다. 창과 명령줄이 같은 메시지를 만들더라도 소켓의 출발 포트와 수명, 응답을 기다리는 동안의 작업 방식은 같지 않았습니다.

소켓을 요청마다 만들고 닫는 구조를 고친 이력은 확인할 수 있습니다. 그러나 이전 시간 초과가 운영체제의 어떤 동작 때문에 생겼는지 보여 주는 패킷 캡처나 요청·응답의 공통 시간표는 없습니다. 소켓 재사용 후 코드가 바뀌었다는 사실만으로 Windows 네트워크 계층이 원인이었다고 단정하지 않습니다.

이 조사에서 중요한 점은 두 클라이언트가 “같은 주소와 포트”를 썼다는 사실만으로 네트워크 동작까지 같다고 볼 수 없다는 것입니다. UDP 서버는 응답을 요청을 보낸 출발 주소와 포트로 돌려보냅니다. 소켓을 새로 만들고 닫는 클라이언트와 오래 유지하는 클라이언트는 출발 포트와 응답 대기 기간이 다를 수 있고, 비동기 UI는 응답 도착과 화면의 요청 상태 갱신도 별도로 맞춰야 합니다. 당시 자료는 이 차이를 조사할 이유를 제공하지만, 과거 실패를 어느 하나로 확정하지는 않습니다.

## 수정: 창이 소켓을 보유하고 요청을 하나씩 처리

지상통제 창이 UDP 소켓 하나를 보유하고 여러 요청에서 재사용하도록 바꿨습니다. 요청 하나가 진행 중일 때 다른 조작 요청이 같은 소켓을 함께 읽거나 쓰지 않도록 합니다. 상태 조회 중 사용자가 조작 명령을 누르면 그 명령은 대기하고, 현재 요청이 끝난 뒤 전송됩니다.

응답은 출발 주소와 포트, 명령 식별값, 순번이 현재 요청과 모두 맞을 때만 그 요청의 결과로 인정합니다. 다른 응답이나 오래된 응답은 현재 조작의 성공으로 표시하지 않습니다.

| 동작 | 현재 코드의 처리 |
| --- | --- |
| 일반 명령 | 요청을 보낸 뒤 400ms 간격으로 다시 보내며, 기본 대기 시간은 최대 4초입니다. |
| 상태 조회 | 한 번에 350ms까지 기다리고, 다음 조회는 약 250ms 뒤 예약합니다. |
| 창이 요청 결과 확인 | UI 타이머가 40ms 간격으로 비동기 작업을 확인합니다. |
| 응답 판별 | 서버 주소·포트와 명령 식별값·순번이 현재 요청과 맞아야 합니다. |
| 창 닫기 | 진행 중인 요청에 취소를 알리고, 비동기 작업이 소켓 사용을 마친 다음 소켓을 정리합니다. |

여기서 재전송은 UDP의 누락 가능성을 보완하려는 동작입니다. 서버가 명령을 이미 적용했지만 응답만 사라진 경우에는 같은 명령이 다시 도착할 수 있으므로, 명령 식별값과 순번을 이용한 중복 요청 처리도 서버 쪽에서 함께 고려해야 합니다.

시간 제한도 요청 종류에 따라 다릅니다. 일반 명령은 같은 식별값과 내용을 유지해 재전송하며 최대 4초 동안 응답을 기다립니다. 상태 조회는 한 번의 짧은 대기 뒤 다음 조회를 예약합니다. 따라서 사용자가 보는 시간 초과를 분석할 때는 “요청을 한 번 보냈는가”만 볼 것이 아니라 실제 재전송 횟수, 마지막 전송 시각, 응답의 식별값, UI가 결과를 소비한 시각을 같은 요청 단위로 비교해야 합니다.

## 확인 결과: 통신 코드와 실제 Windows 창은 검증 수준이 다르다

현재 자동 통신 시험은 같은 PC에서 두 UDP 소켓을 열고, 클라이언트가 명령을 보내면 서버 역할이 요청을 해석해 같은 명령 식별값과 순번으로 응답하는 흐름을 확인합니다. 응답 승인 여부와 적용 Tick도 함께 확인합니다.

숨김 시뮬레이터 통합 시험은 실제 시뮬레이터 프로세스에 상태 조회, 기록 시작, 비행 명령, 드론 추가, 기록 종료, 재생 요청을 보내는 흐름을 확인합니다. 이는 프로토콜과 서버 처리를 검증하지만, Windows 창의 화면 갱신·사용자 입력·실제 네트워크 환경은 검사하지 않습니다.

자동 시험은 재전송 횟수, 오래되거나 잘못된 응답이 섞이는 상황, 요청 취소와 창 닫기가 동시에 일어나는 상황을 모두 확인하지 않습니다. 따라서 코드 경로가 정리됐다는 사실과 실제 네트워크에서 시간 초과가 재현되지 않는다는 결론은 구분해야 합니다. 이 문서에 기록된 자료만으로 모든 시간 초과가 해결됐다고 보증할 수는 없습니다.

## 다시 발생했을 때 원인을 나누는 방법

1. 시간 초과가 난 시각, 입력한 주소·포트, 창의 연결 상태를 기록합니다.
2. 같은 시각에 시뮬레이터가 실행 중이었는지와 서버가 요청을 처리했는지 확인합니다.
3. 요청 종류, 명령 식별값, 순번, 재전송 시각, 서버 응답 상태를 함께 보존합니다.
4. 가능하면 패킷 캡처로 요청이 서버에 도착했는지, 응답의 목적지 주소와 포트가 어디였는지 확인합니다.

이 자료가 있어야 요청 전달 실패, 서버 응답 누락, 클라이언트의 응답 판별 실패를 구분할 수 있습니다. 현재 프로토콜은 UDP이므로 연결 확인, 인증, 암호화, 전달 보장을 제공하지 않습니다.
