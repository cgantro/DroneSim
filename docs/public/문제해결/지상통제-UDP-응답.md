# 명령줄에서는 되는데 지상통제 창에서는 UDP 응답이 시간 초과된 문제

## 증상과 비교 기준

같은 시뮬레이터 주소와 UDP 포트를 사용했는데, 명령줄 프로그램은 응답을 받고 Windows 지상통제 창은 시간 초과를 표시했습니다. 두 프로그램이 같은 요청 형식과 서버를 쓴다는 점 때문에 처음에는 포트 설정만의 문제가 아닐 수 있다고 보고, 창이 요청을 보내고 응답을 기다리는 흐름을 살폈습니다.

UDP는 응답 전달을 보장하지 않습니다. 시간 초과만으로 요청이 서버에 도착하지 않았는지, 서버가 적용했지만 응답이 돌아오지 않았는지, 창이 응답을 받았으나 일치하지 않는 패킷으로 버렸는지는 알 수 없습니다.

## 확인 과정에서 발견한 차이

지상통제 창은 UI를 멈추지 않도록 별도 작업에서 요청을 보내고, 창 스레드는 타이머로 작업 완료를 확인합니다. 초기 구현은 이 요청마다 UDP 소켓을 만들고 닫았습니다. 명령줄과 창은 같은 통신 형식을 사용하더라도 소켓 수명과 비동기 작업 수명은 달랐습니다.

코드 이력은 이 수명 차이를 수정한 사실을 보여 줍니다. 다만 이전 Windows 실행에서 운영체제나 네트워크 계층이 왜 응답을 놓쳤는지는 패킷 캡처나 동일 요청의 양쪽 타임라인으로 확인하지 않았습니다. 소켓 재사용 뒤 동작이 바뀌었다는 사실만으로 특정 Windows 소켓 동작을 원인으로 확정하지 않습니다.

## 바꾼 점

창이 UDP 소켓을 소유하고 여러 요청에서 재사용하도록 바꿨습니다. 한 요청이 진행되는 동안에는 다른 조작 요청이 같은 소켓을 동시에 사용하지 않게 하고, 상태 조회 중 들어온 사용자 명령은 조회가 끝난 뒤 처리합니다.

일반 명령은 같은 요청을 400ms 간격으로 다시 보내며 최대 4초까지 기다립니다. 상태 조회는 350ms 안에 응답을 기다리고, 창은 약 250ms 간격으로 다음 조회를 예약합니다. 서버 주소와 포트, 명령 식별값, 순번이 현재 요청과 맞는 응답만 완료 결과로 사용합니다. 창을 닫을 때는 비동기 요청에 취소를 알리고, 요청이 소켓 사용을 마친 뒤 정리되도록 소켓과 작업의 수명을 맞춥니다.

## 확인 결과

현재 자동 통신 시험은 같은 PC의 두 UDP 소켓 사이에서 명령을 보내고, 서버 역할의 소켓이 일치하는 응답을 돌려주는 흐름을 확인합니다. 응답의 승인 여부와 명령 식별값·순번·적용 Tick을 비교합니다. 재전송 횟수, 잘못된 응답이 섞이는 경우, 취소 중 소켓 종료는 이 시험에서 직접 확인하지 않습니다.

숨김 시뮬레이터 통합 시험은 UDP로 상태 조회, 기록 시작, 비행 명령, 드론 추가, 기록 종료와 재생 요청을 보내는 흐름을 확인합니다. 이 시험은 실제 사용자의 Windows 창과 화면 갱신을 검증하지 않습니다. 현재 문서에 기록된 결과만으로 실제 네트워크 환경에서 모든 응답 시간 초과가 해결됐다고 보장할 수 없습니다.

## 다시 발생했을 때 필요한 자료

1. 지상통제 창의 주소·포트·상태 표시와 시간 초과 시각을 기록합니다.
2. 같은 시각의 시뮬레이터 실행 로그와 프로세스 상태를 확인합니다.
3. 요청의 명령 식별값·순번·명령 종류와 서버의 응답 상태를 보존합니다.
4. 가능하면 요청이 서버에 도착했는지, 응답이 어느 주소와 포트로 돌아왔는지 패킷 캡처로 확인합니다.

그 자료가 없으면 “요청이 전달되지 않았다”와 “응답이 창에 도착하지 않았다”를 구분할 수 없습니다. 현재 프로토콜은 UDP이며 인증·암호화·전달 보장을 제공하지 않습니다.
