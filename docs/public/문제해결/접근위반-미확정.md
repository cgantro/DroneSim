# 접근 위반 오류, 원인 미확인

## 보고된 증상

Visual Studio에서 시뮬레이터가 `0xC0000005` 접근 위반으로 종료됐다는 보고가 있었습니다. 주소만으로는 어느 코드가 잘못된 메모리를 읽었는지 알 수 없습니다.

## 현재 확인 상태

재현 순서와 당시 빌드의 실행 파일·디버그 기호는 저장소에 남아 있지 않습니다. 물리 입력의 잘못된 수치를 거르는 수정도 별도로 있지만, 이 접근 위반과 관련 있다는 증거는 없습니다.

Windows 오류 기록을 확인해 2026년 10월 22일에 `0xC0000005` 접근 위반이 두 차례 발생한 사실을 확인했습니다. 오류 위치는 각각 `0x57f69`, `0x57f79`였습니다. 다음 날에는 `0xC0000409` 예외가 두 차례 기록됐고, 오류 위치는 모두 `0x1a2d51`이었습니다. 서로 다른 예외가 같은 원인에서 나왔는지는 확인하지 못했습니다.

이후 사용자 계정의 CrashDumps 폴더에서 해당 시각의 미니덤프 네 개를 찾아 WinDbg로 분석했습니다. 두 접근 위반은 모두 `0xffffffffffffffff` 주소를 읽으려 했습니다. 각 덤프에는 충돌 지점 한 프레임만 남아 있었고, 그 다음 반환 주소가 유효한 프로그램 주소가 아니어서 호출 경로를 이어갈 수 없었습니다. 두 `0xC0000409` 덤프는 모두 스택 보호값 손상 감지(`FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`)였고, 프로그램 기준 위치와 호출 지점이 같았습니다.

덤프는 충돌 종류와 주소를 확인해 주지만, 당시 실행 파일과 맞는다고 확인할 수 있는 디버그 기호가 없어 주소를 함수나 소스 줄로 신뢰성 있게 바꾸지 못했습니다. 현재 남아 있는 실행 파일과 기호는 덤프가 만들어진 시점과 달라 일치 여부를 확인할 수 없습니다. 따라서 네 번의 오류가 같은 메모리 손상에서 비롯됐는지, 어느 코드가 잘못된 값을 만들었는지는 아직 모릅니다. 오류 양상은 확인했지만 원인과 수정은 미확정입니다.

`0xC0000409` 기록에 함께 남은 값 `2`는 Windows SDK에서 `FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`로 정의합니다. 스택 메모리의 보호값이 바뀐 사실을 감지했다는 뜻입니다. 어느 코드가 처음 손상을 일으켰는지는 이 기록만으로 알 수 없습니다. [Windows SDK의 오류 코드 정의](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/winnt.h)

오류 보고서에 적힌 임시 위치에는 덤프가 없었지만, 사용자 계정의 CrashDumps 폴더에서 네 개의 미니덤프를 찾았습니다. 이 덤프에서 예외 주소와 충돌 시점의 레지스터는 확인했지만, 메모리 손상이 시작된 앞선 호출 경로는 복원하지 못했습니다. 오류 보고서 원본은 현재 계정에서 열 수 없고, 당시 실행 파일도 남아 있지 않습니다. 따라서 오류 위치만으로 현재 코드의 원인을 단정하지 않습니다.

## 원인 추적에 필요한 자료

오류가 다시 발생해 Visual Studio가 멈추면 다음 자료를 남깁니다.

1. 예외 창에 표시된 오류 코드, 읽기·쓰기 구분, 메모리 주소와 현재 코드 위치를 복사합니다.
2. **디버그 > 창 > 호출 스택**을 열어 전체 내용을 복사합니다. 현재 줄만으로 원인을 판단하지 말고, 그 줄까지 이어진 호출 경로도 함께 봅니다. [호출 스택 보는 방법](https://learn.microsoft.com/en-us/visualstudio/debugger/how-to-use-the-call-stack-window?view=visualstudio)
3. 디버거가 멈춘 상태에서 **디버그 > 덤프 파일로 저장**을 선택합니다. 가능하면 힙 정보를 포함한 덤프를 저장합니다. 힙 덤프에는 당시 프로그램 메모리가 들어가므로 공개 저장소에 올리지 말고 개인적으로 전달합니다. [덤프 파일 저장 안내](https://learn.microsoft.com/en-us/visualstudio/debugger/using-dump-files?view=visualstudio)
4. 오류 직전의 입력, 프로그램 상태, 화면과 재현 순서를 함께 적습니다.
5. 같은 순서로 다시 발생하는지 확인합니다.

다시 발생하면 당시 실행 파일과 같은 빌드에서 나온 디버그 기호 파일도 함께 보관합니다. 기존 덤프와 이 자료를 대조해 객체 수명, 인덱스 범위, 비동기 작업 종료 순서를 확인합니다. 현재 덤프만으로 원인을 단정하거나 수정 완료로 기록하지 않습니다.
