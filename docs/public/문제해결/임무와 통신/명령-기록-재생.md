# 기록한 조종 명령을 재생하면 Tick과 상태가 달라진 문제

> 이 글은 조종 명령 기록·재생 기능을 사용하던 과거 동작을 설명합니다. 이 기능과 전용 시험은 2026년 10월 29일 제품에서 제거했습니다. 아래 내용은 당시 문제 해결 기록이며 현재 사용법이 아닙니다.

## 기대한 동작과 실제 증상

같은 초기 상태에서 같은 명령을 다시 실행하면 각 명령이 같은 시뮬레이션 Tick에 적용되고 최종 상태도 같아야 합니다. 초기 구현에서는 기록 시작·종료 요청도 시뮬레이션 시간을 한 Tick 진행했지만, 기록기는 그 경계 Tick을 재생 길이에 동일하게 포함하지 않았습니다. 그 결과 재생이 마지막 Tick을 건너뛰거나 기록과 재생의 상태가 한 단계 어긋날 수 있었습니다.

재생 중 게임패드 입력이 섞이는 문제도 있었습니다. 같은 기록을 재현하려면 기록에 담긴 명령만 적용해야 합니다. 두 문제 중 하나는 Tick 경계 계산, 다른 하나는 입력 소유권에서 생겼습니다.

## 원인 1: 기록 시작과 종료가 Tick 경계에서 상태를 바꿨다

명령 기록은 현재 Tick에 명령을 붙이고, 그 다음 시뮬레이션이 한 번 진행되는 순서입니다. 시작·종료 요청도 같은 처리 흐름을 따르므로 요청을 받은 Tick 자체가 기록 길이에 포함되는지 결정해야 합니다.

| Tick 시작 시점 | Tick 안에서 처리한 명령 | Tick 종료 시점 | 기록에 포함할지 |
| --- | --- | --- | --- |
| 기록 중이 아님 | 기록 시작 | 기록 상태가 켜짐 | 시작 명령이 적용된 첫 Tick을 포함 |
| 기록 중임 | 일반 비행 명령 | 기록 상태가 유지됨 | 명령과 Tick을 기록 |
| 기록 중임 | 기록 종료 | 기록 상태가 꺼짐 | 종료 요청이 소비한 마지막 Tick도 포함 |

종료 뒤의 상태만 보고 기록 길이를 계산하면 이미 기록 상태가 꺼졌기 때문에 종료 Tick이 빠집니다. 반대로 시작 명령이 처리된 뒤의 상태를 무시하면 첫 기록 Tick이 빠집니다. 기록 시작 전후의 현재 상태 하나만으로는 두 경계를 같은 방식으로 처리할 수 없습니다.

재현할 때는 시작 명령 직전, 시작 명령을 처리한 Tick, 첫 비행 명령이 적용된 Tick, 종료 명령을 처리한 Tick을 따로 세어야 합니다. 최종 위치만 비교하면 한 Tick이 빠진 원인이 기록 경계인지 제어기 응답 차이인지 구분하기 어렵습니다. 그래서 확인에서는 기록된 명령 수와 재생 Tick 수를 먼저 맞춘 뒤 위치와 자세 같은 최종 상태를 비교했습니다.

## 원인 2: 재생 중 입력의 우선순위가 고정되지 않았다

재생 중에는 기록 명령이 시뮬레이션 입력의 기준이어야 합니다. 하지만 기존 입력 차단은 지상통제가 명령을 보내는지 확인하는 데 집중되어 있었습니다. 게임패드가 새 명령을 만들거나, 이전 프레임에 만들어 둔 명령이 대기열에 남으면 재생 명령과 같은 Tick에 섞일 수 있었습니다.

따라서 재생 중 게임패드 입력을 새로 받지 않는 것만으로 충분하지 않습니다. 재생을 시작할 때 이미 만들어 둔 수동 명령도 비워야 다음 Tick의 입력이 오직 기록에서 오도록 보장할 수 있습니다. 지상통제와 기록 재생은 서로 다른 입력 경로이므로 각각의 우선순위도 구분합니다.

## 수정: Tick 기록 경계와 입력 소유권을 분리해 정리

각 명령과 적용 Tick을 함께 저장하고, Tick 시작 시점에 기록 중이었는지를 기준으로 종료 요청의 마지막 Tick을 셉니다. 재생에서는 현재 Tick의 명령을 먼저 꺼내 적용하고, 그 Tick의 시뮬레이션을 진행한 뒤 재생 번호를 증가시킵니다. 기록이나 재생이 시작될 때는 이전 시뮬레이션 상태를 초기화합니다.

재생 중에는 게임패드에서 새 비행 명령을 받지 않고, 이미 대기 중인 게임패드 입력도 제거합니다. 지상통제 명령은 별도의 통신 경로에서 들어오므로 재생 명령과 혼합되지 않도록 처리합니다.

재생 한 단계는 기록된 해당 Tick의 명령 적용, 시뮬레이션 1회 진행, 재생 인덱스 증가 순서입니다. 인덱스를 먼저 늘리면 첫 명령을 건너뛰고, 시뮬레이션을 먼저 진행한 뒤 명령을 적용하면 모든 명령이 한 Tick 늦게 반영됩니다. 이 순서는 운동학과 강체 모드 모두에서 동일한 기록 경계를 유지하기 위한 것입니다. 다만 강체 엔진의 내부 물리 계산이 플랫폼과 라이브러리 버전 사이에서도 비트 단위로 같다는 뜻은 아닙니다.

재생 초기화 과정에서는 EO 카메라 픽셀 읽기의 이전 Tick 기준도 함께 정리해야 했습니다. 그 경로는 시뮬레이션 상태 기록과는 별개이므로 [재생 뒤 EO 화면이 새 프레임으로 바뀌지 않던 문제](../화면과%20카메라/카메라-재생-프레임.md)에서 따로 설명합니다.

## 검증 결과: 과거 확인과 현재 남은 회귀 검사를 구분

과거 시험은 기록 시작·종료 경계, 명령이 없는 기록, 운동학 재생, 강체 재생, UDP를 거친 기록·재생을 각각 확인했습니다. 상태 비교에는 Tick 수, 비행 모드, 위치, 속도, 자세, 각속도가 포함됐습니다.

당시에는 기록과 재생의 최종 Tick 및 드론 상태를 비교하는 운동학 시험과, UDP를 거친 통합 시험을 실행했습니다. 기능을 제거하면서 전용 단위 시험과 UDP 기록·재생 흐름도 함께 정리했습니다. 현재 UDP 통합 시험은 두 드론의 이륙·착륙 명령과 정상 종료를 확인합니다.

현재 자동 시험은 기록 자료와 명령 흐름을 확인합니다. 강체 재생 결과 비교, 실제 게임패드 입력 차단, 재생 후 화면의 카메라 픽셀 갱신은 시험하지 않습니다. 따라서 물리 상태와 화면 결과가 매번 같다고 판단할 자료는 없습니다.

## 남은 한계와 재발 방지

- 기록은 현재 프로그램 메모리에 보관됩니다. 파일로 저장하거나 다른 버전에서 읽는 기능은 이 동작에 포함되지 않습니다.
- UDP 통합 시험은 같은 PC의 프로그램 사이에서 메시지를 주고받습니다. 네트워크 지연·손실을 포함한 실제 연결 품질을 재현하지는 않습니다.
- 기록 시작·종료처럼 상태를 바꾸는 명령은 명령 처리 시점뿐 아니라 Tick 시작과 종료의 기록 상태를 함께 검토해야 합니다.
- 재생 입력이 추가되거나 우선순위가 바뀌면, 게임패드 대기 명령까지 비워지는지 확인해야 합니다.
- 이 기능은 현재 코드에서 지원하지 않습니다. 같은 임무를 다시 시험하려면 저장소의 JSON 시나리오 실행 기능을 사용합니다.
