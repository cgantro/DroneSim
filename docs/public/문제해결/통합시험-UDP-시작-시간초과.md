# Linux Sanitizer 통합 시험에서 UDP 기록 재생이 시간 초과된 문제

## 증상

2026년 10월 23일 GitHub Actions의 GCC ASan·UBSan 통합 시험에서 `SimulatorSessionTests.CoreScenarios`가 실패했습니다. 시험은 약 35.9초 동안 실행됐고 앱은 종료 코드 4를 반환했습니다. 출력에는 UDP 기록·재생 명령의 응답 시간 초과가 남았습니다. 같은 실행에서 나머지 통합 시험 7개는 통과했고, Viewer 스모크 시험에는 약 6초가 걸렸습니다.

기대 동작은 숨김 시뮬레이터가 UDP 상태 조회와 기록 시작·이륙·착륙·드론 추가·기록 종료·재생 요청을 처리한 뒤 재생을 마치고 정상 종료하는 것입니다. 실패 로그에는 어느 명령이 응답을 받지 못했는지 표시되지 않았습니다.

## 확인한 실행 순서와 원인 후보

실패 당시 시험은 시뮬레이터 앱을 `std::jthread`에서 실행했습니다. 앱은 그 스레드에서 GLFW 초기화, 창 생성, 이벤트 처리를 했습니다. 저장소에 포함된 GLFW 안내는 이 작업을 메인 스레드에서만 하도록 정하고 있습니다. 따라서 시험은 GLFW의 스레드 규칙을 어기고 있었습니다. Windows에서 통과하더라도 Linux에서 같은 동작이 보장되지는 않습니다.

통신을 시작하는 순서에도 요청을 놓칠 수 있는 구간이 있었습니다. 앱은 그래픽 초기화와 장면 자산 로드를 마친 뒤 UDP 소켓을 열었습니다. 시험은 앱 실행 직후 상태 조회를 보내고, 당시에는 응답을 5초만 기다렸습니다. 그래픽 초기화가 그보다 오래 걸리면 첫 요청이 수신 소켓이 열리기 전에 도착해 버려질 수 있었습니다.

시뮬레이터는 그래픽과 UDP 초기화가 끝난 뒤 네트워크 스모크 시험을 최대 30초 실행합니다. 그 안에 재생 완료 조건을 만족하지 못하면 종료 코드 4를 반환합니다. CI에서 관찰한 약 35.9초는 짧은 응답 대기와 앱의 30초 제한이 함께 나타난 상황과 맞습니다. 다만 실패 로그에 명령별 시각이 없어, 이 시간만으로 어떤 명령이 처음 실패했는지는 확정할 수 없습니다.

## 수정

UDP 소켓을 그래픽 초기화보다 먼저 열어 장면을 준비하는 동안 도착한 요청이 운영체제의 수신 대기열에 남도록 했습니다. 실제 요청 처리는 앱 이벤트 루프가 시작된 뒤 이뤄집니다.

통합 시험에서는 시뮬레이터를 메인 스레드에서 실행하고 UDP 클라이언트만 `std::jthread`로 옮겼습니다. 응답 검증에서 발생한 예외는 클라이언트 스레드 밖으로 전달하고, 스레드가 끝난 뒤 시험 스레드에서 보고합니다. 초기 상태 조회의 대기 시간은 15초로 늘렸으며, 시간 초과 메시지에 실패한 단계를 표시하도록 했습니다.

## 검증 결과와 한계

수정 뒤 Windows Release에서 통합 시험을 반복했습니다. 당시 확인한 리비전 `d3c4be1c`에서는 UDP 기록·재생 시험이 세 번 모두 통과했고, 전체 CTest도 20개 모두 통과했습니다. 이 결과는 Windows Release에서 확인한 내용이며, Linux Sanitizer 결과를 대신하지 않습니다.

| 확인 항목 | 결과 | 확인 범위 |
| --- | --- | --- |
| UDP 기록·재생 반복 | 0.58초, 0.57초, 0.56초로 3회 모두 통과 | 숨김 창에서 상태 조회부터 재생 완료까지 확인 |
| 전체 CTest | 20/20 통과, 총 2.22초 | Windows Release 빌드의 단위·통합·화면 스모크 시험 |
| 수정 리비전의 원격 Linux 시험 | 당시 실행되지 않음 | 수정한 리비전이 GitHub Actions에서 실행되지 않아 Linux Sanitizer 결과를 확인하지 못함 |

2026년 10월 23일에 확인한 [Native CI 실행](https://github.com/cgantro/DroneSim/actions/runs/39904294643), [웹 빌드 실행](https://github.com/cgantro/DroneSim/actions/runs/39904294664), [Native Quality 실행](https://github.com/cgantro/DroneSim/actions/runs/39904294685)은 모두 이전 리비전 `ff08bb07`에서 실패했습니다. 세 실패가 서로 다른 단계에서 발생했습니다.

| 검사 단계 | 실제 결과 | 확인된 원인 또는 한계 |
| --- | --- | --- |
| 네이티브 빌드 | 성공 | 빌드가 끝난 뒤 이어진 정적 분석 단계에서 워크플로가 실패함 |
| 정적 분석 | 실패 | 실행 환경의 `run-clang-tidy`가 `-source-filter` 인자를 인식하지 못함. C++ 분석 결과가 아니라 도구 실행 인자에서 멈춘 문제였음 |
| Emscripten 웹 빌드 | 실패 | 앱 종료 경로가 웹 빌드에서 선언되지 않은 EO 읽기 정리 함수를 호출해 컴파일되지 않음 |
| GCC Sanitizer 단위 시험 | 12개 통과 | 해당 실행의 단위 시험 단계는 통과함 |
| GCC ASan·UBSan 통합 시험 | 통합 시험 8개 중 7개 통과. `CoreScenarios`는 약 35.9초 뒤 종료 코드 4와 UDP 응답 시간 초과로 실패 | 당시 로그에 명령별 시각이 없어 어느 요청이 처음 실패했는지는 확정할 수 없음 |
| GCC Coverage | 워크플로 성공 | 당시 측정 대상은 `modules/`와 `apps/simulator/`였음. 줄 74.1%(3,554/4,797), 함수 85.5%(370/433), 분기 33.6%(3,023/8,994)이며 전체 저장소의 커버리지로 해석하면 안 됨 |

그 뒤 관련 코드를 바꿨습니다. `f17b5b36`에서 그래픽 자산을 읽기 전에 UDP 소켓을 열도록 했고, `98e652f2`에서는 GLFW 창을 만드는 시뮬레이터를 시험의 메인 스레드에서 실행하게 했습니다. 정적 분석은 `889d368f`에서 지원하지 않는 필터 인자 대신 Git이 추적하는 C++ 파일 목록을 넘기도록 바꿨습니다. 웹 종료 경로는 `c6874f30`에서 EO 읽기 정리 함수를 네이티브 빌드에서만 호출하도록 고쳤습니다.

Windows Release의 반복 시험은 새 통합 시험 구조가 그 환경에서 동작함을 확인합니다. 그러나 과거 Linux 시간 초과가 GLFW의 스레드 규칙 위반 때문이었는지, 초기 UDP 요청을 놓친 탓인지, 두 문제가 함께 영향을 줬는지는 분리 검증하지 못했습니다. 위 GitHub 실행은 수정 전 리비전에서 시작했으므로 수정 후 Linux·웹 CI 통과를 증명하지 않습니다. 수정한 리비전도 원격 CI에서 확인하지 않았으므로 Linux·웹 결과는 미검증입니다.

현재 작업 PC에서는 수정된 Linux Sanitizer 실행을 재현할 수 없습니다. WSL 목록에는 `docker-desktop`만 있고, 이 PC에는 Emscripten 명령도 없습니다. 따라서 현재 리비전의 Linux GCC ASan·UBSan과 Emscripten 결과는 미검증 상태입니다.

## 다음 확인

수정된 리비전으로 GitHub Actions가 실행되면 Linux Sanitizer 통합 시험, Clang 정적 분석, Emscripten 빌드를 각각 확인합니다. UDP 시험이 다시 시간 초과되면 단계별 오류 메시지에서 마지막으로 응답을 받은 명령을 먼저 찾습니다. CI 통과는 해당 자동 시험의 확인일 뿐, 실제 지상통제 창이나 다른 운영체제의 연결까지 검증했다는 뜻은 아닙니다.
