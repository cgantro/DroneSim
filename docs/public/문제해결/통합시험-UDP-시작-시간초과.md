# Linux Sanitizer 통합 시험에서 UDP 기록 재생이 시간 초과된 문제

## 증상

2026년 10월 23일 GitHub Actions의 GCC ASan·UBSan 통합 시험에서 `SimulatorSessionTests.CoreScenarios`가 실패했습니다. 시험은 약 35.9초 동안 실행됐고 앱은 종료 코드 4를 반환했습니다. 출력에는 UDP 기록·재생 명령의 응답 시간 초과가 남았습니다. 같은 실행에서 나머지 통합 시험 7개는 통과했고, Viewer 스모크 시험에는 약 6초가 걸렸습니다.

기대 동작은 숨김 시뮬레이터가 UDP 상태 조회와 기록 시작·이륙·착륙·드론 추가·기록 종료·재생 요청을 처리한 뒤 재생을 마치고 정상 종료하는 것입니다. 실패 로그에는 어느 명령이 응답을 받지 못했는지 표시되지 않았습니다.

## 확인한 실행 순서와 원인 후보

실패 당시 시험은 시뮬레이터 앱을 `std::jthread`에서 실행했습니다. 앱은 그 스레드에서 GLFW 초기화, 창 생성, 이벤트 처리를 했습니다. 저장소에 포함된 GLFW 안내는 이 작업을 메인 스레드에서만 하도록 정하고 있습니다. 따라서 시험은 GLFW의 스레드 규칙을 어기고 있었습니다. Windows에서 통과하더라도 Linux에서 같은 동작이 보장되지는 않습니다.

통신을 시작하는 순서에도 요청을 놓칠 수 있는 구간이 있었습니다. 앱은 그래픽 초기화와 장면 자산 로드를 마친 뒤 UDP 소켓을 열었습니다. 시험은 앱 실행 직후 상태 조회를 보내고, 당시에는 응답을 5초만 기다렸습니다. 그래픽 초기화가 그보다 오래 걸리면 첫 요청이 수신 소켓이 열리기 전에 도착해 버려질 수 있었습니다.

시뮬레이터는 그래픽과 UDP 초기화가 끝난 뒤 네트워크 스모크 시험을 최대 30초 실행합니다. 그 안에 재생 완료 조건을 만족하지 못하면 종료 코드 4를 반환합니다. CI에서 관찰한 약 35.9초는 짧은 응답 대기와 앱의 30초 제한이 함께 나타난 상황과 맞습니다. 다만 실패 로그에 명령별 시각이 없어, 이 시간만으로 어떤 명령이 처음 실패했는지는 확정할 수 없습니다.

## 수정

UDP 소켓을 그래픽 초기화보다 먼저 열어 장면을 준비하는 동안 도착한 요청이 운영체제의 수신 대기열에 남도록 했습니다. 실제 요청 처리는 앱 이벤트 루프가 시작된 뒤 이뤄집니다.

통합 시험에서는 시뮬레이터를 메인 스레드에서 실행하고 UDP 클라이언트만 `std::jthread`로 옮겼습니다. 응답 검증에서 발생한 예외는 클라이언트 스레드 밖으로 전달하고, 스레드가 끝난 뒤 시험 스레드에서 보고합니다. 초기 상태 조회의 대기 시간은 15초로 늘렸으며, 시간 초과 메시지에 실패한 단계를 표시하도록 했습니다.

## 검증 결과와 한계

수정한 뒤 Windows Release에서 UDP 기록·재생 시험을 세 번 연속 실행해 모두 통과했습니다. 각 실행은 약 0.54초, 0.29초, 0.27초였습니다. 이어 `464a3a9c`에서 Release 전체를 다시 빌드하고 CTest 20개를 실행했으며 모두 통과했습니다. 이때 `SimulatorSessionTests`는 0.60초, 전체 시험은 1.83초에 끝났습니다. 시험은 숨김 창에서 상태 조회부터 재생 완료까지 확인합니다. 이 결과는 Windows에서 해당 경로가 동작한다는 뜻이며, Linux Sanitizer 결과를 대신하지 않습니다.

2026년 10월 23일에 확인한 원격 실행은 모두 `ff08bb07`에서 시작했습니다. GCC ASan·UBSan 통합 시험은 8개 중 7개가 통과했고, 실패한 한 시험은 UDP 기록·재생 응답을 기다리다 시간 초과됐습니다. 같은 기준 리비전에서 정적 분석도 실패했습니다. 설치된 `run-clang-tidy`가 설정에 적힌 `-source-filter` 인자를 지원하지 않아 분석 전에 종료됐습니다.

실패 로그를 만든 원격 실행은 모두 수정 전 리비전 `ff08bb07`에서 시작했습니다. 그 리비전에서는 ASan·UBSan 통합시험 8개 중 7개가 통과했고, 실패한 `CoreScenarios`는 약 35.9초 뒤 UDP 시간초과로 종료됐습니다. 정적 분석은 지원하지 않는 `-source-filter` 인자를 받아들일 수 없어 분석을 시작하기 전에 끝났습니다. 웹 빌드도 Emscripten에서만 필요한 함수 선언이 빠져 컴파일 단계에서 멈췄습니다.

이후 수정은 원인을 각각 겨냥했습니다. `f17b5b36`은 그래픽 초기화 전에 UDP 수신 소켓을 열어 준비 중 도착한 요청을 보관합니다. `98e652f2`는 GLFW가 메인 스레드 실행을 요구한다는 규칙에 맞춰 앱을 시험의 메인 스레드에서 실행합니다. `889d368f`는 정적 분석 도구가 받지 못하는 정규식 옵션을 없애고 Git이 추적하는 C++ 파일 목록을 직접 전달합니다. `c6874f30`은 웹에서 사용할 수 없는 EO 정리 함수를 네이티브 빌드에서만 호출하도록 했습니다.

현재 코드(`e39812b1`)에도 이 수정이 포함되어 있습니다. Windows Release에서 UDP 기록·재생 통합시험은 0.60초에 통과했고, 전체 CTest 20개도 1.61초에 모두 통과했습니다. 이 실행으로 Windows 경로의 수정은 확인했습니다. 과거 Linux 실패의 직접 원인이 메인 스레드 위반인지, 초기 수신 지연인지, 둘 다였는지는 당시 명령별 기록이 없어 확정할 수 없습니다.

이 작업에서는 로컬 변경을 원격으로 푸시하지 않았으므로 수정 리비전의 GitHub Actions 결과는 확인하지 않았습니다. 이 PC에는 Emscripten 명령이 없고, WSL에는 `docker-desktop` 배포판만 있습니다. Docker Desktop Linux 엔진의 정보 요청은 HTTP 500을 반환했습니다. 따라서 이 PC에서는 수정된 웹 빌드와 Linux GCC ASan·UBSan을 재현하지 못했으며, 두 경로 모두 통과가 검증되지 않았습니다.

## 다음 확인

수정된 리비전으로 GitHub Actions를 실행할 수 있게 되면 Linux Sanitizer의 UDP 통합시험, Clang 정적 분석, Emscripten 빌드를 각각 확인합니다. UDP 시험이 다시 실패하면 새로 추가한 단계 이름을 기준으로 어느 요청에서 멈췄는지 추적합니다. 이 CI 결과가 통과하더라도 실제 Windows 지상통제 창의 연결 상태까지 검증한 것으로 확대 해석하지 않습니다.
