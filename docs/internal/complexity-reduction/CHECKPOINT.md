# 작업 재개 기록

## 현재 상태

- Jolt 단계는 강체 기초에서 X500 로터 연동으로 진행 중이다. `JoltPhysicsWorld`가 X500 질량·관성·로터 배치를 받아 모터 응답, 제곱 추력, 로터 위치에 따른 힘, 회전 반작용 토크를 계산한다. 앱의 실제 비행 경로와 제어기는 아직 AirSim을 사용하므로 Jolt 전환은 완료되지 않았다. Windows Release 전체 빌드와 CTest 31/31, Jolt 로터 시험 5/5를 확인했다.
- 후속 변경에서는 Jolt에 높이 격자 지형, 다각형 건물 기둥 충돌체, 바람에 대한 단순 공기 저항을 더했다. DEM·건물 접촉과 X500 로터 기초 시험 6/6, Release 전체 CTest 32/32, 앱을 포함한 전체 Release 빌드가 통과했다. `SimulationCore`는 아직 AirSim을 사용하며 웹 빌드는 확인하지 않았다.
- 비행 제어기를 Jolt에 직접 연결한 시험에서 좌표 변환과 yaw 반작용 부호 오류를 찾아 고쳤다. X500의 이륙·경유점 이동·착륙 시험과 로터 차등 추력 방향 시험이 통과한다. 전체 Release 빌드와 CTest 34/34도 통과했다. 이 시험은 제어기와 Jolt의 결합을 검증하지만, 앱의 Flecs `SimulationCore`는 아직 AirSim 경로이므로 P4 통합은 끝나지 않았다.
- Jolt 드론 충돌체를 단일 중심 상자에서 X500 설정의 9개 몸체·다리·프로펠러 상자로 바꿨다. 복합 충돌 형상을 넣은 제어기 비행 시험과 전체 Release CTest 34/34가 통과했다. `SimulationCore`의 AirSim 교체는 다음 단계다.
- 이번 설정 검사 분리 작업의 시작 커밋은 `d54ce2b2`다. 완료한 변경 `301435b5`는 원격 `main`에 반영했다.
- 시나리오 회피 방향을 별도 저장하던 상태를 없애고 예측 경로에서 매 Tick 계산하도록 바꿨다. 강체 시험의 8m 최소 간격과 전체 CTest 28/28을 확인했으며 변경 `dc5e0440`을 원격 `main`에 올렸다.
- 임무 실행 중 입력 파서가 이미 보장하는 드론 이름을 다시 확인하던 분기를 제거했다. 한 번만 쓰는 경유점 선택 함수도 호출부에 합쳤다. 전체 CTest 28/28 통과, 코드 변경 `bada45d3`·`b880eec5`를 원격 `main`에 반영했다.
- 임무 명령과 충돌 회피는 작업 목록을 각각 읽지만 상태 처리 시점이 다르다. 한 Tick의 양쪽 동작을 억지로 합치지 않고, 회피 대상 선택에서 실제 쓰이지 않던 값을 만드는 분기만 제거했다. 전체 CTest 28/28 통과.
- 회피 중 드론을 담은 별도 집합을 없앴다. 이미 쓰던 회피 목표 표로 진입·종료 여부를 판정하도록 바꿨으며, Release 전체 CTest 28/28 통과.
- 시나리오 목표 좌표, 최상위 기본 드론 상태, 임무 완료 여부와 임무 판정의 중복 저장을 제거했다. 임무 일부만 끝났는데 전체 완료 시각이 표시되던 문제를 고쳤고, 드론 시작 상태를 하나의 `DroneState`로 모았다. Windows Release 전체 CTest 28/28 통과.
- 사용자가 미리 삭제한 `assets/models/source/x500-v2/README.md`는 미커밋 상태로 남겨 두었다.
- 장면 패널의 드롭다운이나 카메라 패널의 드론 이름을 누르면 주 시점 카메라가 선택한 기체를 따라간다. 선택을 안 하면 기존 주 드론을 따라간다. 이 조작은 네이티브 시뮬레이터에만 적용했고 웹 화면은 변경하지 않았다.
- `apps/` 현재 파일은 28개다. 앱 파일별 이전 감사표는 32개 경로를 기준으로 하므로 현재 경로 목록과 대조할 것.
- 이번 시나리오 감사에서 앱 임무와 JSON Runner가 서로 다른 실행 경로이며, 시나리오 시험이 화면 임무를 검증하지 않는 점을 확인했다. 상세 내용은 `AUDIT_SIMULATION.md`에 덧붙였다.
- JSON 명령의 지연·유실·중복·순번 처리를 제거하고 지정 Tick에 명령을 적용하도록 줄였다. 직접 통신 단절 시험은 GCS 상태가 오래된 정보로 바뀌는 흐름을 확인한다.
- 시나리오 결과의 `outcome`과 중복 저장하던 `passed` 값을 없애고, 결과 상태에서 성공 여부를 계산하도록 바꿨다.
- 시나리오 작업 입력은 단일 목표와 경유점 목록 두 문법을 쓰고 있었다. 입력을 경유점 목록 하나로 통일했고, 결과 JSON의 기존 목표 좌표 항목은 유지했다. 세부 검증은 `VERIFICATION.md`에 덧붙인다.
- `survey_area` 자동 분할은 시나리오 자료나 앱에서 쓰이지 않고 시험 한 곳에서만 사용됐다. 구현을 제거하고, 같은 네 대 정찰 시험을 드론별 경유점 목록으로 유지했다.
- 통신 장애 뒤 제자리 정지를 선택하는 코드를 없앴다. 실제 기체 궤적은 목표에 도달하지만, 단절 중 GCS에는 마지막 위치만 보이고 임무 완료 여부도 미확정으로 남는다.
- 시나리오의 기대 비행 결과도 단일 드론용 필드와 다중 드론용 목록으로 나뉘어 있었다. `expected.drones` 목록 하나로 통일하고, 드론 이름을 명시하도록 고쳤다. 기존 단일 드론 형식은 오류로 거부한다. 변경 후 Release 전체 CTest 28/28 통과.
- 시나리오 JSON에서만 쓰던 카메라 켜기·끄기·고장·복구 시간표를 제거했다. 기본 카메라 상태와 영상은 유지한다. 시나리오 시험은 Release 전체 CTest 28/28 통과.
- 시나리오 충돌 회피의 경로 예측을 단순화했다. 경유점에서 멈추는 구간을 나눠 계산하지 않고, 현재 목표 속도가 예측 시간 동안 이어진다고 본다. 이 방식은 실제 비행 안전 검증용이 아니다. Release 전체 CTest 28/28 통과.
- 임무 완료 수·완료율·방문 경유점 비율·전체 완료 Tick은 작업 목록에서 바로 계산하도록 바꿨다. 결과 JSON은 이전 항목을 유지한다. Release 전체 CTest 28/28 통과.
- 임무 명령 적용에서 같은 드론의 앞선 작업을 반복 검색하지 않도록 한 번의 순회로 바꿨다. 유효한 순차 작업 시나리오를 시험에 추가했고 Release 전체 CTest 28/28 통과.
- 충돌 회피의 드론 쌍 검사와 회피 명령 적용에서 반복하던 진행 중 임무 검색 조건을 하나로 모았다. Release 전체 CTest 28/28 통과.
- 드론 쌍 검사에 쓰는 연결 상태와 활성 임무를 드론마다 한 번만 구해 재사용한다. Release 전체 CTest 28/28 통과.
- `ScenarioRunner`의 드론 ID, 관측 상태, 귀환 위치, 이전 위치, 비행 거리·시간을 여섯 맵에서 한 드론 실행 상태로 모았다. Windows Release 전체 CTest 28/28 통과. 시나리오 JSON 파싱과 실행은 파일은 나뉘어 있지만 같은 모듈이며, 입력 검사는 형식 검사와 여러 설정 사이의 규칙이 함께 있어 목적별 검토가 필요하다.
- JSON 필드 형식·범위 검사는 읽는 함수에 두고, 강체 전용 값·다중 드론 설정·배터리 예비량 등 여러 항목의 조합 검사는 네 개의 목적별 사전 검사로 묶었다. 새 클래스나 모듈은 만들지 않았고, Release 전체 CTest 28/28 통과.
- `drones`를 생략한 JSON도 파서에서 기본 드론 항목으로 정규화한다. 관측·배터리·궤적·최종 결과는 이제 하나의 드론 목록을 사용하며, SimulationCore가 만든 기본 기체는 계속 재사용한다. Release 전체 CTest 28/28 통과.
- 다음에는 앱 임무와 JSON Runner가 각각 어떤 M01–M03 동작을 수행하는지 다시 대조하고, 실제 중복 동작을 확인한 뒤에만 공통 규칙을 정한다. Runner와 앱의 임무 코드는 서로 다른 실행 경로다.

## 영상 품질 분석 경로 제거 — 2026-10-30

- 현재 목표에는 사람·시설물 인식이나 카메라 조건에 따른 정찰 합격 판정이 없다. 그래서 화면 밝기·대비·선명도만 계산하던 `vision`과 픽셀 보관용 `sensor` 모듈은 제품 동작에 필요하지 않다고 판단했다.
- OpenCV, CPU 픽셀 읽기용 PBO 링, 분석 수치·벤치마크 항목과 전용 시험을 제거했다. 카메라 화면은 기존 GPU 색 텍스처를 패널에 직접 표시한다.
- 앱 감사에서 지상통제 경계도 다시 확인했다. `apps/ground_control`은 명령 전송 정적 라이브러리이며 실행 파일에서 사용하지 않는다. 현재 조작 UI와 UDP 수신은 시뮬레이터 앱 안에 있다.
- 사용자가 미리 삭제한 `assets/models/source/x500-v2/README.md`는 이 변경에 포함하지 않는다.

## 운동학 모델의 바람 설정 검사 수정 — 2026-10-30

- 설정 검증이 바람을 강체 물리 전용으로 막고 있었지만, 운동학 이동 코드도 바람 속도를 반영하고 있었다. 지원 코드와 검증 조건이 서로 달라 해당 제한을 제거했다.
- 기존 바람 경로 시험에 운동학 모델 사례를 보태 실제 위치가 변하는지 확인한다. Release 전체 CTest 결과는 `VERIFICATION.md`에 기록했다.

## 시나리오 목표 좌표 중복 제거 — 2026-10-29

- `MissionTask`는 목표 좌표와 경유점 목록을 모두 저장하고 있었다. 목표는 항상 첫 경유점과 같으므로 목표 좌표 필드를 없애고, headless JSON 출력에서 첫 경유점을 기존 `target_position_meters` 항목으로 내보낸다.
- 사용자가 미리 삭제한 `assets/models/source/x500-v2/README.md`는 이 변경에 포함하지 않는다.
- `01299827`로 변경과 기록을 커밋하고 원격 `main`에 올렸다. Release 전체 CTest 28/28이 통과했다. 자세한 빌드 의존성 문제와 복구 결과는 `VERIFICATION.md`를 확인한다.

## 최상위 기본 드론 상태 중복 제거 — 2026-10-30

- 결과 구조체에서 최상위 비행·카메라 상태를 없앴다. 이 값은 드론별 목록의 첫 항목과 같았고, Headless JSON의 최상위 `final_state`·`camera` 항목은 첫 드론에서 만들어 기존 출력 모양을 유지한다.
- Windows Release의 `aerosimlab_headless`와 시나리오 시험을 빌드하고 전체 CTest 28/28을 통과했다. JSON 실행 결과에서 최상위 상태와 첫 드론 상태가 같은 것도 확인했다.

## 임무 완료 상태 중복 제거 — 2026-10-30

- 각 임무가 `completed`와 `completedTick`을 함께 저장하던 중복을 없앴다. 완료 여부는 완료 Tick의 유무에서 계산하고 JSON 출력 필드는 유지한다.
- 시나리오 실행기, 결과 출력과 기존 시험을 새 판정식에 맞췄다. Windows Release 전체 CTest 28/28 통과.

## 부분 완료 임무의 완료 시각 수정 — 2026-10-30

- 개별 작업 일부만 완료된 미확정 임무에 전체 임무 `completed_tick`이 기록되던 오류를 고쳤다. 이제 모든 작업이 완료됐을 때만 전체 완료 시각을 제공한다.
- 완료 집계, 경유점 진행률, 실패 판정을 한 번의 작업 순회에서 계산한다. 직접 통신 단절 사례는 4개 중 3개 작업을 완료하고도 전체 완료 시각을 내보내지 않는 것을 확인했다.
- Windows Release 전체 CTest 28/28 통과.

## 시나리오 드론 시작 상태 모으기 — 2026-10-30

- 시나리오 입력의 위치·방향·속도·자세·로터 속도·비행 모드를 여러 필드로 나눠 저장한 뒤 실행 단계에서 `DroneState`로 다시 조립하던 구조를 없앴다.
- 내부 정의는 `DroneState` 하나를 보관한다. 위치·방향 외의 초기 상태가 JSON에 있었는지를 나타내는 표시는 운동학 시나리오에서 강체 전용 설정을 거르는 데만 사용한다.
- Windows Release 전체 CTest 28/28 통과.

## 임무 판정을 작업 상태에서 계산 — 2026-10-30

- 작업별 완료·실패 상태가 이미 있으므로 `Mission`에 결과 열거형을 따로 저장하지 않는다. `GetOutcome()`이 작업 목록을 보고 성공·실패·미확정을 계산하며 JSON 출력 모양은 유지한다.
- Windows Release 전체 CTest 28/28 통과.

## 시나리오 실행 경로 재검토 — 2026-10-29

- 현재 시나리오 JSON은 리더 추종 링크 사례를 제거해 8개다. CMake headless 연기 시험 4개 외에 물성 덮어쓰기·4대 조사 장애·저배터리 자료는 GoogleTest fixture로도 읽힌다. `normal-flight.json`은 코드 검색에서 참조를 찾지 못했다.
- JSON 읽기와 항목 간 규칙 검사는 나뉘어 있지만 호출 경계가 파서 함수 안에 숨겨져 있었다. 파서 이름과 실행 순서를 분명하게 바꿔 `ParseScenarioDefinition` 다음 `ValidateScenarioDefinition`을 실행기가 차례로 부르게 했다. 값의 형식·범위는 읽을 때, 드론 참조·설정 조합은 읽은 뒤 검사한다.
- `ScenarioRunner.cpp`는 여전히 Tick 실행·임무·통신 장애·배터리·카메라·결과 판정을 맡는다. 다음에는 이 처리 흐름에서 같은 상태를 중복 계산하는지 살핀다.
- `RunScenario`는 headless와 시나리오 시험에서 호출된다. 시뮬레이터 앱은 별도 M01–M03 임무와 가상 통신 경로를 사용한다. 동작이 다르므로 지금 공통 엔진으로 합치지 않는다.

- 따라서 지도 적용은 아직 시작하지 않았다. 다음에는 사용 허가와 시험 구역을 확정하고, 실제 지면 자료·정사영상과 건물 자료의 좌표계·기준점을 맞춘 뒤 훈련장 하드코딩을 데이터 기반 장면으로 바꾼다.

## Jolt 강체 물리 기초 — 2026-10-30

- Jolt 5.6.0을 고정 커밋으로 네이티브 CMake 빌드에 연결했다. 샘플, 뷰어, 직렬화, 프로파일러, 그래픽 연산과 내부 작업 스레드는 끄고 프로젝트에서 필요한 물리 라이브러리만 빌드한다.
- `JoltPhysicsWorld`는 상자 모양의 고정·움직이는 강체, 힘·토크 적용, 상태 읽기·복원, 1/60초 물리 갱신과 강체 해제를 제공한다. 공개 좌표는 ENU이며 Jolt의 Y-up 좌표로 경계에서 바꾼다. 정적·움직이는 물체를 두 충돌 층으로 나눴다.
- 기존 AirSim 경로는 아직 `PhysicsWorld`에서 사용 중이다. 이번 변경은 Jolt 기초를 검증하는 단계이며 앱 비행·충돌 경로를 Jolt로 교체하거나 X500 로터 동역학을 연결하지 않았다. Emscripten 빌드에도 Jolt를 넣지 않았다.
- Jolt 시험은 자유낙하와 바닥 접촉, 같은 힘에서 질량별 가속도, 같은 토크에서 관성별 회전, 상태 복원, 잘못된 입력과 강체 해제를 확인한다. 시작할 때 단일 스레드 작업 슬롯을 만들지 않아 갱신 중 접근 위반이 났고, Jolt API에 맞춰 1,024개 작업 슬롯을 초기화해 해결했다.
- Windows Release 전체 빌드에서 시뮬레이터·헤드리스·시험 실행 파일을 링크했고 CTest 30/30을 통과했다. 지도 자산과의 충돌, 네 대의 드론 비행, 웹 빌드는 아직 확인하지 않았다.

## Flecs SimulationCore를 네이티브 Jolt에 연결 — 2026-10-30

- 강체 핸들·상태와 기체 충돌 상자를 물리 엔진 이름과 분리했다. Flecs 코어는 작은 `SimulationPhysics` 경계만 호출하고 CMake가 네이티브 Jolt 또는 웹 AirSim 구현 하나를 선택한다. 코어 소스에는 플랫폼 전처리 분기를 넣지 않았다.
- 네이티브 앱은 이제 Jolt로 모터 동역학·힘 적분·지형과 장애물 접촉·강체 상태를 계산하며, Flecs 컴포넌트는 계산 결과를 받는다. 웹은 아직 빌드하지 않았고 기존 AirSim 구현을 남겼다.
- 높이 정보가 없는 비행 금지 외곽선 API를 `SimulationCore`에서 제거했다. 별도 호출 시험 때문에 구형 AirSim `PhysicsWorld`에는 아직 남아 있으며, AirSim 제거 단계에서 함께 정리해야 한다. 높이를 지정한 상자·프리즘과 지형은 유지한다.
- 코어 수준의 네 대 임무 시험에서 이륙·각자 경유점 이동·착륙을 확인했다. 지형이 없는 실행에도 지면이 필요해 Jolt 어댑터가 기본 평지를 제공하고, 실제 지형을 설정하면 기본 평지를 제거하게 했다. 앱·헤드리스·Jolt·회귀 시험을 포함한 Windows Release CTest 34/34 통과.
- PX4 참조 로그의 기본 고도 실행에서 Jolt RMSE는 동쪽 0.72m, 북쪽 0.60m, 자세 29.70도, 속도 0.56m/s였다. 시작 높이만 100m 올린 시험에서는 동쪽 26.60m, 북쪽 17.82m, 자세 96.41도, 속도 3.60m/s였고 최저 고도는 41.90m였다. 고도 조건에 따라 결과 차이가 커서 장시간 고도 유지와 제어 안정성은 미완료다. 제어·모터 파라미터와 지면 접촉 영향을 추가 조사해야 한다.
- 확보한 도시 지도와의 비행·충돌, Emscripten 빌드와 브라우저 실행은 미검증이다.

## PX4 참조 구간의 지면 접촉 확인 — 2026-10-30

- Release 헤드리스 실행에서 2026-10-16 자료의 고도는 시작 때 0.976m, 1초에 0.217m였고 4초까지 0.217m에 머물렀다. 이 실행의 낮은 위치 RMSE는 공중 비행 재현을 입증하지 않는다.
- 자료의 초기 ESC 회전수와 저장된 X500 기체 질량 2.064kg·추력 계수 8.54858e-6 N/(rad/s)^2로 계산하면 초기 네 로터의 총 추력은 약 9.62N, 기체 무게는 약 20.24N이다. 평균 입력 비율 0.278은 같은 모형에서 필요한 호버 추력 비율 약 0.592보다 낮다.
- 시작 높이를 100m 올린 실행도 최저 41.90m까지 내려갔다. 현재 PX4 자료는 공중 비행 정확도 기준으로 쓰지 않는다. 다른 계수로 수치를 억지로 맞추지 말고 실제 공중 구간을 확인할 수 있는 입력 자료를 확보한다. X500 모터 상수는 [PX4 공식 모델](https://github.com/PX4/PX4-gazebo-models/blob/main/models/x500/model.sdf)과 대조했다.
- 2025-12-05 자료도 1초에 0.121m, 2초에 0.048m로 내려간 뒤 바닥에 머물렀다. 호버·제어기 경유점 시험은 이 참조 재생과 별도로 본다. 도시 지도 통합을 포함한 P4는 미완료다.

## 네이티브 Jolt와 4대 임무 시험 재확인 — 2026-10-30

- 현재 CMake는 네이티브 빌드에서 `SimulationPhysicsJolt.cpp`, 웹 빌드에서 `SimulationPhysicsAirSim.cpp`를 선택한다. `SimulationCore`는 공통 물리 어댑터를 쓰므로 네이티브 앱 경로는 Jolt다.
- Jolt 전용 시험 8개와 `SimulatorSessionTests` 4개, 네 대 정찰 헤드리스 시험 1개를 실행해 모두 통과했다. ViewerSmoke도 별도로 통과했다. 앱 Release 빌드도 성공했다.
- GLB 변환을 적용한 결과, X500 표시 모델 범위는 약 0.41 × 0.30 × 0.64m다. 지도 GLB의 바닥판은 약 16.6 × 49.8m이고 가장 긴 구조물 조각은 약 2.0 × 0.96 × 3.22m다. 그 조각이 차량인지 파일 정보만으로 식별할 수 없어 화면에서 보인 크기 차이의 원인은 확정하지 않았다.
- 관찰 카메라 간격을 5.5m에서 12m로 바꾼 소스는 Release 빌드와 ViewerSmoke까지 확인했다. 사용자는 시점이 원인이 아니라고 정정했으므로 이 변경은 시각적인 크기 문제의 해결 근거로 취급하지 않는다. 현재 지도 크기 문제는 추가 추측이나 수정 없이 보류한다.
