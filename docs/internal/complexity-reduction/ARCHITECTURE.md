# DroneSim 구조와 데이터 위치

확인 기준은 2026년 10월 29일 작업 트리다. 각 C++ 모듈은 Luna로 파일·빌드 연결·주요 호출처를 읽어 살폈고, Graphify의 기존 코드 그래프에서 장면·렌더러·SimulationCore의 연결도 확인했다. 아래 정리 순서는 조사에서 나온 후보이며, 사용자가 요청한 Terra 또는 Sol의 독립 판단 검토는 아직 받지 못했다. 코드 단순화 내용과 확인 결과를 아래에 이어 기록한다.

## 구조 한눈에 보기

DroneSim은 여러 정적 라이브러리를 CMake로 묶은 한 프로그램이다. 모듈 간 순환 참조는 찾지 못했다. 시뮬레이션 상태와 비행 계산은 `simulation_core`, 편대 배치와 편대가 통과할 경로는 `flight_planning`, JSON 시험 입력과 실행은 `scenario`, 지도 자료와 경로는 `terrain`, 화면 그리기는 `graphics`, 통신은 `communication`, 프로그램 조립과 임무 진행은 `apps/simulator`가 맡는다.

```text
apps/headless ──▶ scenario ──▶ simulation_core ──▶ terrain
apps/simulator ──▶ graphics
      ├─────────▶ communication ──▶ simulation_core
      ├─────────▶ manual_control ─▶ simulation_core
      └─────────▶ flight_planning ─▶ terrain
      └─────────▶ simulation_core
지상통제 클라이언트 ──▶ communication
vision ──▶ sensor
```

화살표는 직접 빌드 의존성을 나타낸다. `simulation_core`는 Flecs와 AirSim을 사용하지만, AirSim 물리 진행은 Flecs 시스템 호출 바깥에서 일어난다. 따라서 “모든 비행 계산이 ECS 안에서 처리된다”고 설명하면 맞지 않는다.

## 모듈별 책임

| 영역 | 현재 책임 | 검토 결과 |
|---|---|---|
| `simulation_core` | 드론 상태·제어·고정 Tick·AirSim 연동·배터리·카메라·충돌 | 비행 모의 핵심을 맡는다. Flecs·AirSim 경계와 별도 저장 자료는 추가 정리가 남았다. |
| `flight_planning` | 편대 위치 계산·편대 폭을 고려한 이동 경로 요청 | Simulation Core와 독립된 계산으로 분리했다. 지형 모듈에 의존하며 화면 앱과 시험에서 사용한다. |
| `scenario` | JSON 시험 입력 검사·시뮬레이션 실행·결과 요약 | 자동 시험 책임을 코어에서 분리했다. `simulation_core`에 한 방향으로 의존한다. |
| `terrain` | 높이 격자·좌표 변환·건물/도로/나무/물/교량 읽기·비행 경로 | 실제 지도 자료와 경로 기능이 함께 있다. 현재 앱 경로에 사용되므로 기능별 호출처 확인 없이 쪼개지 않는다. |
| `graphics` | 창·카메라·셰이더·메시·GLB·화면 출력 | 화면 기반 모듈로 책임은 대체로 맞다. GLB 로더 진입점이 둘이고 내부 파서가 공개 헤더로 노출된 점은 정리 후보다. |
| `communication` | 명령 형식·UDP 소켓·직접 가상 통신 | 현재는 순환 의존이 없다. 메시지 형식이 시뮬레이션 자료형을 직접 사용해 Simulation Core와 강하게 묶여 있다. |
| `manual_control` | 게임패드 축을 비행 명령으로 바꾸는 계산 | GLFW 입력 수집은 앱에 있고 계산은 모듈에 있어 경계가 비교적 명확하다. |
| `sensor` | 픽셀·크기·Tick을 담는 RGB 프레임 | 현재는 프레임 자료형 하나만 제공한다. 지금 이름을 바꾸거나 더 큰 센서 계층을 만들 이유는 부족하다. |
| `vision` | 프레임을 빌려 밝기·대비·선명도를 계산 | 픽셀을 소유하지 않고 결과만 계산한다. 현재 책임은 단순하다. |
| `media` | 삭제됨 | 사용자가 라이브 영상 전송도 제거하도록 요청했다. 화면 패널 표시는 그래픽스 안에서 직접 처리한다. |
| 앱 | 창·GUI·임무·환경 연결·텔레메트리 표시 | 프로그램 연결을 맡는 위치다. 다만 임무와 상태가 한 앱 클래스에 모여 있어 찾아가기 어렵다. |

주요 빌드 경계는 `CMakeLists.txt`의 모듈 선언에 있다. `scenario`는 JSON 입력을 검사하고 Simulation Core를 실행한다. `flight_planning`은 편대 배치와 편대 폭을 반영한 경로 요청을 계산하며, `simulation_core`를 참조하지 않는다. JSON 라이브러리는 시나리오와 통신 프로토콜에서 쓰며, `simulation_core`의 컴파일 항목과 의존성에서는 빠졌다. `communication`은 `DroneCommand` 등 Simulation Core 타입을, `manual_control`은 `FlightMode`를 직접 사용하므로 공개 의존성을 둔다. 이 두 모듈을 독립 제품처럼 재사용할 요구가 없어 변환 계층은 추가하지 않았다.

## Flecs와 비행 상태

Flecs는 실제로 사용한다. 각 드론 엔티티에 비행 상태와 제어 목표가 들어가며, 카메라 상태도 컴포넌트로 관리한다. 네이티브 강체 모드에는 물리 객체 식별 정보도 붙는다. Flecs 시스템이 제어·운동학·카메라 갱신을 수행한다.

모든 드론별 자료가 ECS에 있는 것은 아니다. `SimulationCore::EcsStorage`는 드론 ID에서 Flecs 엔티티를 찾는 맵과 별도의 배터리 모델 맵을 가진다. 배터리는 선택 사항이고 `BatteryModel`에는 기본 생성자가 없다. 이를 컴포넌트로 강제하면 현재 Flecs 설정에서 실행 중단이 났으며, 기본 상태나 선택형 래퍼를 더하는 방식은 저장 구조를 더 복잡하게 만든다. 그래서 배터리 맵은 유지한다. 드론을 지울 때 배터리 항목도 함께 지우는 동작은 계속 필요하다. 지형, 충돌 장애물, 바람, 계측값도 월드 컴포넌트가 아니라 코어 소유 자료로 관리한다. 모든 상태를 억지로 ECS에 넣지 않고, 엔티티의 생애와 함께 움직이는 값만 컴포넌트로 둔다.

배터리는 드론별 값이지만 Flecs 컴포넌트로 옮기는 시험에서 기본 생성자 오류가 발생했다. 이를 우회할 래퍼를 더하면 구조가 복잡해지므로 현재는 별도 맵을 유지한다. Flecs를 쓰는 것 자체가 목적은 아니며, 엔티티에 붙는 상태와 선택적으로 관리하는 모델을 구분한다.

## 장면은 어디서 관리하나

화면용 장면 관리자는 그래픽스 모듈이나 Flecs 안에 없다. 앱이 `TrainingRangeScene`을 소유한다. 이 클래스의 배치 목록을 읽어 GLB 모델 인스턴스를 만들고, 같은 배치로 건물 장애물과 정찰 지점을 구성한다.

현재 데이터 흐름은 다음과 같다.

```text
TrainingRangeScene 배치 목록
  ├─ GLB 모델 인스턴스 → 화면에 그리기
  ├─ 충돌 상자 → SimulationCore에 등록
  ├─ MapBuilding 목록 → 경로·가림·무선 장애물 자료로 변환
  └─ 정찰 위치 → 앱의 임무 목표 목록
```

따라서 렌더 배치와 물리 충돌 자료는 서로 다른 저장소에 있지만 한 배치 목록에서 파생된다. 이는 현재 훈련장에서는 동작을 맞추기 쉽게 하는 장점이 있다. 다만 배치 원본과 파생 사본의 구분, 다시 생성해야 하는 시점이 코드에 충분히 드러나지 않는다. 다음 정리에서는 새 `SceneManager`나 `AssetManager`를 추가하기보다, 배치 원본을 하나로 정하고 충돌·가림·통신 자료가 그 원본에서 만들어지는 과정을 분명하게 하는 편이 낫다.

## 데이터마다 기준 위치와 사본이 다르다

| 자료 | 기준이 되는 저장 위치 | 다른 곳의 자료 | 사본이 필요한 이유 |
|---|---|---|---|
| 드론의 위치·자세·비행 모드 | Flecs의 `DroneState` | 네트워크 노드 위치, 관제 상태 | 링크 판정 시점의 위치 및 실제 전달된 과거 상태를 표현한다. |
| 드론 카메라 자세 | Flecs의 `CameraState` | GPU 프레임과 맞추는 마지막 생성 Tick | 코어는 카메라 상태·자세·프레임 진행을 관리한다. 임무 완료를 촬영 구도나 해상도로 판정하지 않는다. |
| 배터리 | `EcsStorage::batteries` 맵 | 앱 임무 표시·복귀 판단 | 현재는 ECS 드론 컴포넌트와 별도 관리한다. 정리 전 API 사용처 확인이 필요하다. |
| 카메라 픽셀 | GPU 프레임버퍼/PBO, 완료 후 앱의 `eoFrame_` | OpenCV 분석용 빌린 화면 | GPU에서 읽은 화면을 앱에 전달해 로컬 표시와 품질 계산에 쓴다. 영상 전송과 파일 저장은 제거했다. |
| 임무 진행 | 앱의 `fleetReconnaissance_`, `completeFleetMission_`, `formationTransit_` | 화면 표시 상태 | 구형 단일 드론 점검 흐름은 제거했다. 드론별 정찰과 전체 임무의 단계 정보는 아직 앱에 함께 있어 갱신 책임을 더 살펴야 한다. |
| 건물·정찰 환경 | `TrainingRangeScene` 배치 | `obstacles_`, `formationRadioObstacles_`, 정찰 목표, SimulationCore 충돌 형상 | 장면 배치에서 화면·충돌·통신·정찰 자료를 만든다. 가림막과 자동 촬영 평가는 제거했으며, 남은 파생 자료의 생성 위치와 기준 목록은 정리 대상이다. |
| 네트워크 노드 위치 | Simulation Core의 현재 위치 | `VirtualMeshNetwork::nodes_` | 약 6 Tick마다 전달한 위치로 링크 거리·가림을 판정한다. 갱신 주기만큼 오래된 샘플일 수 있다. |
| 관제·리더 텔레메트리 | 실제 비행 상태는 Simulation Core | `telemetryAtGroundControl_`, `peerTelemetryAtLeader_` | 메시지가 끊긴 동안 마지막으로 받은 위치를 유지한다. 실제 현재 상태와 구분해야 하므로 의도된 사본이다. |

사본이 있다는 사실만으로 중복 구현은 아니다. 마지막 수신 텔레메트리, 비동기 프레임 Tick, 네트워크 위치는 지연이나 처리 시점을 나타내므로 별도 보관이 필요하다. 혼란을 줄이는 핵심은 **원본 상태인지, 시점이 고정된 사본인지, 계산해 만든 파생 자료인지** 이름과 갱신 위치에서 구분하는 것이다.

가장 정리가 필요한 곳은 앱의 임무 단계 상태와 파생 환경 자료다. 구형 단일 드론 임무는 제거했지만, 편대 이동·드론별 정찰·전체 임무 단계가 나뉘어 있으므로 남은 각 상태의 기준과 갱신 순서를 더 확인해야 한다. 건물은 `TrainingRangeScene`의 배치 목록에서 경로·통신·충돌 자료로 이어진다.

## 파일로 저장되는 자료

실행 중인 상태와 디스크에 남는 파일은 다른 종류다. 현재 파일 저장 지점은 아래처럼 쓰임새에 따라 나뉜다.

| 자료 | 위치 | 저장 주체와 기준 |
|---|---|---|
| 지도·모델 원본 | `assets/` | 프로그램이 읽는 입력 자료다. 실행 중 생성하지 않는다. |
| 임무와 시험 설정 | `scenarios/`, `tests/data/` | 사람이 관리하는 시나리오와 시험 입력이다. 실행 결과가 이 파일들을 덮어쓰지 않는다. |
| 화면 배치 | Windows의 `%LOCALAPPDATA%/AeroSimLab/imgui.ini` | ImGui가 패널 위치와 크기를 저장한다. 사용자 설정이므로 빌드 폴더와 분리되어 있다. |
| 성능 측정 결과 | Windows는 실행 파일 옆의 `benchmark-latest.json`, 그 외에는 현재 실행 폴더의 같은 이름 파일 | 벤치마크가 결과를 쓴다. `AEROSIMLAB_BENCHMARK_OUTPUT` 환경 변수로 저장 경로를 바꿀 수도 있다. |
| 변환한 지형 격자 | 변환 도구를 실행할 때 지정한 출력 경로 | `terrain_grid_converter`가 ASCII 격자를 `.aerotrn`으로 바꿔 저장한다. 앱은 준비된 지형 파일을 읽고, 변환 도구와 시험만 파일을 쓴다. |
| 수동 조종 명령 | 실행 중 입력 큐와 명령 패킷 | 통신 응답·드론 상태 | 입력은 적용 후 버린다. 앱 내 기록·재생 기능은 제거했다. 반복 시험은 JSON 시나리오가 맡는다. |

사용자가 직접 위치를 정하는 출력은 지형 변환 결과다. 화면 배치는 사용자 설정으로 따로 보관하고, 성능 결과는 기본 경로가 실행 파일 위치를 따라간다. 서로 다른 파일을 한 폴더에 강제로 모으기보다, **입력 자산·시험 자료·실행 중 사용자 설정·생성 결과**를 구분하고 각 쓰기 위치를 한곳에서 찾을 수 있게 유지한다. 벤치마크 결과가 빌드 폴더에 쌓이는 점은 출력 위치가 실행 파일 위치에 따라 달라질 수 있으므로, 이후 빌드·결과 정리를 다룰 때 고정된 저장 위치를 선택할 후보로 남긴다.

## 파일 배치와 이름

- 공개 모듈 헤더는 대부분 `modules/<모듈>/include/<모듈>/`에 있고 구현은 `src/` 아래에 있다.
- `modules/simulation_core/src/CollisionGeometry.h`, `modules/scenario/src/ScenarioDefinition.h`, `modules/terrain/src/MapGeometry.h`는 여러 내부 구현 파일이 공유하는 비공개 헤더다. `include`는 외부에 약속하는 공개 인터페이스 위치다. 이 헤더를 모두 `include`로 옮기면 구현 세부를 공개 API로 노출하게 된다. 현재처럼 `src`에 두거나, 한 파일에서만 쓴다면 해당 `.cpp` 안으로 합치는 편이 맞다. 별도 `detail` 폴더를 만들 필요는 없다.
- `Mesh::LoadGlb()`는 저장소 안에서 호출되지 않아 제거했다. `GlbModel::Load()`가 현재 GLB 모델을 불러오는 진입점이다.
- `GlbData.h`는 GLB 내부 파서인데 현재 `graphics/include`에 있다. 외부 공개용이 아니라면 `include`에 둔 것은 공개 범위가 넓다. 내부 파서 위치는 별도로 검토해야 한다.
- 그래픽스 시험의 include 경로에서 이전 `modules/graphics/src/graphics` 경로를 제거했다.
- JSON 시나리오 실행기와 점검 입력 파서는 `scenario` 모듈로 옮겼다. 전용 시험도 별도 실행 파일로 빌드한다. 앱 HUD에서 쓰지 않던 시나리오 헤더 포함도 제거했다.
- `simulation_core`에서 시나리오 실행과 JSON 파싱을 떼어 냈다. 통신 구현에 있던 사용하지 않는 시나리오 헤더 의존도 제거했다.
- 편대 위치·통과 경로 계산을 `flight_planning`으로 옮겼다. 구현과 헤더가 Simulation Core에 의존하지 않으므로 코어 타깃에서 빼고, 시뮬레이터와 편대 시험이 새 모듈을 직접 사용하게 했다. 알고리즘 동작은 이번 변경에서 바꾸지 않았다.

## 우선 정리 순서

1. **환경 자료의 파생 과정을 분명히 한다.** 건물 기준 목록은 장면에서 직접 읽도록 바꿨다. 촬영 가림막과 통신 장애물은 목적별 파생 자료로 남아 있으므로, 생성 위치와 갱신 시점을 확인하며 정리한다.
2. **임무 상태의 기준을 정한다.** 단일 정찰, 드론별 정찰, 편대 이동, 전체 임무의 실제 사용처를 확인하고 더 이상 활성 목표에 필요하지 않은 상태부터 정리한다.
3. **의도된 사본에 이름을 붙인다.** 관제와 리더의 마지막 수신 상태, 네트워크 위치 샘플, 카메라 Tick 스냅샷은 최신 실제 상태와 헷갈리지 않게 이름·주석을 정리한다.
4. **GLB 파서의 공개 범위를 검토한다.** 중복 로더를 제거했다. 내부 파서를 공개 `include`에서 감출 방법은 아직 남은 후보다.
5. **Simulation Core 내부 책임을 계속 살핀다.** 배터리를 ECS 컴포넌트로 옮기는 시도는 기본 생성자 요구와 불필요한 래퍼 때문에 되돌렸다. 다음은 `SimulationCore.cpp`를 새 헤더 계층 없이도 책임별로 이해하기 쉽게 나눌 수 있는지 확인한다.

시나리오 실행·JSON 파싱을 별도 모듈로 옮겨 코어에서 JSON 의존성을 제거했다. `SimulationCore` 클래스 자체의 책임 분리와 Flecs 컴포넌트·별도 맵 사이의 저장 구조 정리는 아직 남아 있다. 이번 변경에서는 앱 임무 처리나 물리 동작을 바꾸지 않았다. GUI 조작과 웹 실행은 확인하지 않았다.

2026-10-29에는 코어의 점검면 구도·거리·해상도·건물 가림 판정도 제거했다. 카메라 프레임 생성은 유지하며, 시나리오 임무 완료는 경유점 도착으로 결정한다. 카메라 영상의 실제 내용과 시설물 상태는 사람이 확인한다.

## 확인한 단순화

- `Mesh::LoadGlb()`는 선언·구현만 있고 호출처가 없어 삭제했다. 이에 붙어 있던 GLB 단일 메시 제한 검사와 파서 호출도 함께 제거했다.
- 앱이 `TrainingRangeScene::Obstacles()`를 통째로 복사해 들고 있던 `routeBuildings_`를 없앴다. 경로 계획, 시점 충돌 검사, 무선 장애물 생성은 장면의 건물 목록을 직접 참조한다. 카메라 가림막과 무선 장애물은 자료 형식이 달라 계산 결과를 계속 보관한다.
- 시험 코드도 장면의 기준 건물 목록을 직접 읽도록 바꿨다. 사용처 검색에서 `routeBuildings_`와 `Mesh::LoadGlb()`가 남지 않았다.
- Windows Release 전체 빌드 성공, CTest 31/31 통과. 헤더 변경 뒤 최초 증분 시험에서 앱 개체 파일 일부가 이전 클래스 배치를 유지해 접근 위반이 났다. 앱 소스와 시뮬레이터 시험을 다시 컴파일한 뒤 모두 통과했다.
