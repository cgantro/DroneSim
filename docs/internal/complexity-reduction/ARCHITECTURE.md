# DroneSim 구조와 데이터 위치

확인 기준은 2026년 10월 30일 작업 트리다. 이 문서는 현재 구조와 실제 변경·검증 결과를 기록한다. 계획과 현재 동작은 구분해 적는다.

## 구조 한눈에 보기

DroneSim은 여러 정적 라이브러리를 CMake로 묶은 한 프로그램이다. 시뮬레이션 상태와 비행 계산은 `simulation_core`, 편대 배치와 경로 계획은 `flight_planning`, 시험 입력과 실행은 `scenario`, 높이 격자와 좌표 변환은 `terrain`, 그래픽 자원은 `graphics`, HUD와 화면 패널·카메라는 `gui`, 통신은 `communication`, 실행 시작과 임무 연결은 `apps/simulator`가 맡는다.

```text
apps/headless ──▶ scenario ──▶ simulation_core ──▶ terrain
apps/simulator ──▶ graphics
      ├─────────▶ gui ──────────▶ graphics
      ├─────────▶ communication ──▶ simulation_core
      ├─────────▶ manual_control ─▶ simulation_core
      └─────────▶ flight_planning ─▶ terrain
      └─────────▶ simulation_core
지상통제 클라이언트 ──▶ communication
```

화살표는 직접 빌드 의존성을 나타낸다. `simulation_core`는 Flecs로 드론 상태를 관리하고 Jolt로 강체 적분과 접촉을 계산한다. 강체 적분은 Flecs 시스템 진행과 별도로 호출된다. 따라서 “모든 비행 계산이 ECS 안에서 처리된다”고 설명하면 맞지 않는다.

## 모듈별 책임

| 영역 | 현재 책임 | 검토 결과 |
|---|---|---|
| `simulation_core` | 드론 상태·제어·고정 Tick·Jolt 연동·배터리·카메라·충돌 | 비행 모의 핵심을 맡는다. 네이티브 Release 빌드는 확인했으며 웹 빌드 검증은 남아 있다. |
| `flight_planning` | 편대 위치 계산·편대 폭을 고려한 이동 경로 요청 | Simulation Core와 독립된 계산으로 분리했다. 지형 모듈에 의존하며 화면 앱과 시험에서 사용한다. |
| `scenario` | 시험 조건 읽기·검사·실행·결과 판정 | 임무 입력과 시험 조건이 한 정의에 섞여 있어 더 단순하게 나눌 후보지만, `simulation_core`와는 분리되어 있다. |
| `terrain` | 높이 격자 읽기·저장·고도 보간·훈련장 높이 생성 | OSM/GeoJSON 지도 읽기와 경로 계산은 제거했다. 격자 높이는 물리와 경로 계획에서 사용한다. 시뮬레이터 원점 기준의 지역 미터 좌표만 다룬다. |
| `graphics` | 창·카메라·셰이더·메시·GLB·화면 출력 | 화면 기반 모듈로 책임은 대체로 맞다. GLB 로더 진입점이 둘이고 내부 파서가 공개 헤더로 노출된 점은 정리 후보다. |
| `communication` | 명령 형식·UDP 소켓·직접 가상 통신 | 현재는 순환 의존이 없다. 메시지 형식이 시뮬레이션 자료형을 직접 사용해 Simulation Core와 강하게 묶여 있다. |
| `manual_control` | 게임패드 축을 비행 명령으로 바꾸는 계산 | GLFW 입력 수집은 앱에 있고 계산은 모듈에 있어 경계가 비교적 명확하다. |
| `media` | 삭제됨 | 사용자가 라이브 영상 전송도 제거하도록 요청했다. 화면 패널 표시는 그래픽스 안에서 직접 처리한다. |
| `gui` | HUD 입력·표시, 장면·EO 패널 카메라와 렌더 타깃 | 화면 표시와 패널 렌더 준비를 맡는다. 실제 장면의 드론·임무 표시 내용은 앱에서 전달한다. |
| 앱 | 창·시뮬레이션 초기화와 임무·환경 연결 | 실행 객체를 만들고 모듈을 연결한다. 화면 패널 카메라는 `gui::SimulatorView`가 맡는다. 임무 진행과 장면의 드론·경로 그리기는 아직 `DroneSimApp` 안에 남아 있어 후속 분리 범위다. |

주요 빌드 경계는 최상위 CMake 설정에 있다. `scenario`는 시험 조건을 읽고 검증한 뒤 Simulation Core를 실행한다. `flight_planning`은 편대 배치와 장애물을 고려한 경로 계산을 맡고, 지형 높이 조회가 필요할 때만 `terrain`을 참조한다. `terrain`은 경로를 찾거나 건물 모양을 만드는 책임을 맡지 않는다. JSON은 시나리오 입력과 통신 메시지에서 쓰며, `simulation_core`에는 들어가지 않는다.

## 임무와 시험 시나리오는 다르다

임무는 드론이 해야 할 일이다. 예를 들어 네 대가 모여 이동하고, 정찰 지점을 나눠 방문한 다음 출발 위치로 돌아오는 흐름이다. 시험 시나리오는 그 임무를 어떤 조건에서 실행하고 결과를 무엇으로 판정할지 정한다. 시작 위치와 기체 상태, 실행 Tick 수, 바람이나 통신 단절 같은 조건, 마지막 위치와 임무 완료 기준이 여기에 들어간다.

JSON은 시험 조건을 저장하고 실행기에 전달하는 파일 형식이다. JSON 자체가 임무는 아니다. 현재 실행기는 임무 입력, 물리 설정, 통신 장애, 궤적 기록, 기대 결과를 한 설정 자료형에서 함께 다룬다. 그래서 임무 설명보다 JSON 필드가 먼저 보여 전체 의미를 파악하기 어렵다. 대표 임무의 흐름은 코드에서 바로 읽히게 하고, JSON은 반복 시험에 필요한 조건만 담도록 줄이는 것이 맞다. 현재 JSON을 직접 편집해야 임무를 수행하는 구조라는 설명은 정확하지 않다.

지형 격자는 높이와 칸 간격만 가진다. 예전에는 중심 위도·경도도 저장해 WGS84 좌표를 지역 ENU로 바꾸려 했지만, 앱과 시뮬레이션에서 그 함수를 부르지 않았다. 저장 파일과 변환 도구가 좌표를 계속 요구하는 상태라 해당 필드와 변환 함수를 제거했다. 현재 ASCII 격자는 높이 모양만 읽으며, 원본의 지도상 위치는 보존하지 않는다. 따라서 실제 지형과 건물의 좌표를 맞추는 기능은 아직 없다.

## Flecs와 비행 상태

Flecs는 실제로 사용한다. 각 드론 엔티티에 비행 상태와 제어 목표가 들어가며, 카메라 상태도 컴포넌트로 관리한다. 네이티브 강체 모드에는 물리 객체 식별 정보도 붙는다. Flecs 시스템이 제어·운동학·카메라 갱신을 수행한다.

모든 드론별 자료가 ECS에 있는 것은 아니다. `SimulationCore::EcsStorage`는 드론 ID에서 Flecs 엔티티를 찾는 맵을 가진다. 배터리는 선택형 `BatteryModel` 컴포넌트로 드론 엔티티에 붙으며, Flecs가 저장 공간을 만들 수 있도록 기본 생성자를 제공한다. 배터리를 설정하지 않은 드론에는 컴포넌트가 없다. 드론을 지우면 엔티티와 함께 배터리도 사라진다. 지형, 충돌 장애물, 바람, 계측값은 월드 컴포넌트가 아니라 코어 소유 자료로 관리한다. 모든 상태를 억지로 ECS에 넣지 않고, 드론의 생애와 함께 움직이는 값만 컴포넌트로 둔다.

## 장면은 어디서 관리하나

화면용 장면 자료는 `scene::TrainingRangeScene`이 관리한다. 배치 목록에서 GLB 모델 인스턴스, SimulationCore 충돌 상자, 경로 계획용 건물 장애물, 정찰 지점을 만든다. 패널 크기와 관찰·EO 카메라 및 출력 프레임버퍼는 `gui::SimulatorView`가 맡는다. 앱은 장면을 준비하고 임무·시뮬레이션을 연결한다.

현재 데이터 흐름은 다음과 같다.

```text
TrainingRangeScene 배치 목록
  ├─ GLB 모델 인스턴스 → 화면에 그리기
  ├─ 충돌 상자 → SimulationCore에 등록
  ├─ BuildingObstacle 목록 → 경로 계획에 전달
  └─ 정찰 위치 → 앱의 임무 목표 목록
```

화면 모델, SimulationCore 충돌 상자, 경로 계획 장애물은 같은 배치값에서 각각 만들어진다. 필요한 모양은 다르지만 원본 배치가 하나라 위치를 맞출 수 있다. OSM 지도에서 건물·교량을 읽던 코드는 이번 정리에서 제거했다.

## 데이터마다 기준 위치와 사본이 다르다

| 자료 | 기준이 되는 저장 위치 | 다른 곳의 자료 | 사본이 필요한 이유 |
|---|---|---|---|
| 드론의 위치·자세·비행 모드 | Flecs의 `DroneState` | 네트워크 노드 위치, 관제 상태 | 링크 판정 시점의 위치 및 실제 전달된 과거 상태를 표현한다. |
| 드론 카메라 자세 | Flecs의 `CameraState` | GPU 프레임과 맞추는 마지막 생성 Tick | 코어는 카메라 상태·자세·프레임 진행을 관리한다. 임무 완료를 촬영 구도나 해상도로 판정하지 않는다. |
| 배터리 | 드론 엔티티의 선택형 `BatteryModel` 컴포넌트 | 앱 임무 표시·복귀 판단 | 배터리를 설정한 드론에만 붙고, 드론 제거 시 함께 사라진다. |
| 카메라 화면 | GPU 프레임버퍼의 색 텍스처 | 화면 패널이 텍스처 번호를 받아 표시 | 화면을 CPU 메모리로 복사하지 않는다. 로컬 표시만 하며 영상 분석·전송·파일 저장은 하지 않는다. |
| 임무 진행 | `mission` 모듈의 정찰·편대·전체 임무 상태 자료 | 앱의 임무 실행 조정 | 상태 자료와 판정 규칙은 임무 모듈이 소유한다. 실제 경로 생성과 Tick별 실행은 시뮬레이션·장면·통신 객체를 잇는 앱에 남아 있어 다음 분리 대상이다. |
| 건물·정찰 환경 | `TrainingRangeScene` 배치 | `obstacles_`, `formationRadioObstacles_`, 정찰 목표, SimulationCore 충돌 형상 | 장면 배치에서 화면·충돌·통신·정찰 자료를 만든다. 가림막과 자동 촬영 평가는 제거했으며, 남은 파생 자료의 생성 위치와 기준 목록은 정리 대상이다. |
| 네트워크 노드 위치 | Simulation Core의 현재 위치 | `VirtualMeshNetwork::nodes_` | 약 6 Tick마다 전달한 위치로 링크 거리·가림을 판정한다. 갱신 주기만큼 오래된 샘플일 수 있다. |
| 관제·리더 텔레메트리 | 실제 비행 상태는 Simulation Core | `telemetryAtGroundControl_`, `peerTelemetryAtLeader_` | 메시지가 끊긴 동안 마지막으로 받은 위치를 유지한다. 실제 현재 상태와 구분해야 하므로 의도된 사본이다. |

사본이 있다는 사실만으로 중복 구현은 아니다. 마지막 수신 텔레메트리, 비동기 프레임 Tick, 네트워크 위치는 지연이나 처리 시점을 나타내므로 별도 보관이 필요하다. 혼란을 줄이는 핵심은 **원본 상태인지, 시점이 고정된 사본인지, 계산해 만든 파생 자료인지** 이름과 갱신 위치에서 구분하는 것이다.

장면 배치와 임무 상태는 각각 `scene`, `mission` 모듈로 옮겼다. 편대 이동·드론별 정찰·전체 임무의 실제 실행은 여전히 앱에 있으므로, 작은 함수 단위로 임무 모듈에 옮길 수 있는지 의존 관계를 확인해야 한다. 건물은 `TrainingRangeScene`의 배치 목록에서 경로·통신·충돌 자료로 이어진다.

## 파일로 저장되는 자료

실행 중인 상태와 디스크에 남는 파일은 다른 종류다. 현재 파일 저장 지점은 아래처럼 쓰임새에 따라 나뉜다.

| 자료 | 위치 | 저장 주체와 기준 |
|---|---|---|
| 지도·모델 원본 | `assets/` | 프로그램이 읽는 입력 자료다. 실행 중 생성하지 않는다. |
| 임무와 시험 설정 | `scenarios/`, `tests/data/` | 사람이 관리하는 시나리오와 시험 입력이다. 실행 결과가 이 파일들을 덮어쓰지 않는다. |
| 화면 배치 | Windows의 `%LOCALAPPDATA%/DroneSim/imgui.ini` | ImGui가 패널 위치와 크기를 저장한다. 사용자 설정이므로 빌드 폴더와 분리되어 있다. |
| 성능 측정 결과 | 프로그램을 시작한 작업 폴더의 `benchmark-latest.json` | 벤치마크가 결과를 쓴다. 실행 파일 위치를 따로 찾지 않는다. |
| 변환한 지형 격자 | 변환 도구를 실행할 때 지정한 출력 경로 | `terrain_grid_converter`가 ASCII 격자를 `.aerotrn`으로 바꿔 저장한다. 앱은 준비된 지형 파일을 읽고, 변환 도구와 시험만 파일을 쓴다. |
| 수동 조종 명령 | 실행 중 입력 큐와 명령 패킷 | 통신 응답·드론 상태 | 입력은 적용 후 버린다. 앱 내 기록·재생 기능은 제거했다. 반복 시험은 JSON 시나리오가 맡는다. |

사용자가 직접 위치를 정하는 출력은 지형 변환 결과다. 화면 배치는 사용자 설정으로 따로 보관하고, 성능 결과는 실행 작업 폴더에 쓴다. 네이티브 실행 때는 CMake가 자산을 복사한 빌드 폴더에서 실행해야 모델과 셰이더를 찾을 수 있다. 서로 다른 파일을 한 폴더에 강제로 모으기보다 **입력 자산·시험 자료·실행 중 사용자 설정·생성 결과**를 구분하고 각 쓰기 위치를 한곳에서 찾을 수 있게 한다.

## 파일 배치와 이름

- 공개 모듈 헤더는 대부분 `modules/<모듈>/include/<모듈>/`에 있고 구현은 `src/` 아래에 있다.
- `modules/simulation_core/src/CollisionGeometry.h`와 `modules/terrain/src/MapGeometry.h`는 내부 구현끼리 공유하는 헤더다. 시나리오 정의 헤더는 2026-10-30에 사용자가 요청한 저장소 배치에 맞춰 `modules/scenario/include/scenario/`로 옮겼다. 내부 자료형은 `detail` 이름공간에 두어 공개 실행 기능과 구별한다. 별도 `detail` 폴더는 만들지 않는다.
- `Mesh::LoadGlb()`는 저장소 안에서 호출되지 않아 제거했다. `GlbModel::Load()`가 현재 GLB 모델을 불러오는 진입점이다.
- `GlbData.h`는 GLB 내부 파서인데 현재 `graphics/include`에 있다. 외부 공개용이 아니라면 `include`에 둔 것은 공개 범위가 넓다. 내부 파서 위치는 별도로 검토해야 한다.
- 그래픽스 시험의 include 경로에서 이전 `modules/graphics/src/graphics` 경로를 제거했다.
- JSON 시나리오 실행기와 점검 입력 파서는 `scenario` 모듈로 옮겼다. 전용 시험도 별도 실행 파일로 빌드한다. 앱 HUD에서 쓰지 않던 시나리오 헤더 포함도 제거했다.
- `simulation_core`에서 시나리오 실행과 JSON 파싱을 떼어 냈다. 통신 구현에 있던 사용하지 않는 시나리오 헤더 의존도 제거했다.
- 편대 위치·통과 경로 계산을 `flight_planning`으로 옮겼다. 구현과 헤더가 Simulation Core에 의존하지 않으므로 코어 타깃에서 빼고, 시뮬레이터와 편대 시험이 새 모듈을 직접 사용하게 했다. 알고리즘 동작은 이번 변경에서 바꾸지 않았다.

## 우선 정리 순서

1. **환경 자료의 파생 과정을 분명히 한다.** 건물 기준 목록은 장면에서 직접 읽도록 바꿨다. 촬영 가림막과 통신 장애물은 목적별 파생 자료로 남아 있으므로, 생성 위치와 갱신 시점을 확인하며 정리한다.
2. **임무 상태의 기준을 정한다.** 단일 정찰, 드론별 정찰, 편대 이동, 전체 임무의 실제 사용처를 확인하고 더 이상 활성 목표에 필요하지 않은 상태부터 정리한다.
3. **의도된 사본에 이름을 붙인다.** 관제와 리더의 마지막 수신 상태, 네트워크 위치 샘플, 카메라 Tick 스냅샷은 최신 실제 상태와 헷갈리지 않게 이름·주석을 정리한다.
4. **GLB 파서의 공개 범위를 검토한다.** 중복 로더를 제거했다. 내부 파서를 공개 `include`에서 감출 방법은 아직 남은 후보다.
5. **Simulation Core 내부 책임을 계속 살핀다.** 배터리는 드론 엔티티의 선택형 컴포넌트로 옮겼다. 다음은 `SimulationCore.cpp`를 새 헤더 계층 없이도 책임별로 이해하기 쉽게 나눌 수 있는지 확인한다.

시나리오 실행·JSON 파싱을 별도 모듈로 옮겨 코어에서 JSON 의존성을 제거했다. 배터리 저장은 드론 컴포넌트로 정리했지만, `SimulationCore` 클래스 자체의 책임 분리와 ID→엔티티 맵의 필요성 검토는 남아 있다. 이번 변경에서는 앱 임무 처리나 물리 동작을 바꾸지 않았다. GUI 조작과 웹 실행은 확인하지 않았다.

2026-10-29에는 코어의 점검면 구도·거리·해상도·건물 가림 판정도 제거했다. 카메라 프레임 생성은 유지하며, 시나리오 임무 완료는 경유점 도착으로 결정한다. 카메라 영상의 실제 내용과 시설물 상태는 사람이 확인한다.

## 확인한 단순화

- `Mesh::LoadGlb()`는 선언·구현만 있고 호출처가 없어 삭제했다. 이에 붙어 있던 GLB 단일 메시 제한 검사와 파서 호출도 함께 제거했다.
- 앱이 `TrainingRangeScene::Obstacles()`를 통째로 복사해 들고 있던 `routeBuildings_`를 없앴다. 경로 계획, 시점 충돌 검사, 무선 장애물 생성은 장면의 건물 목록을 직접 참조한다. 카메라 가림막과 무선 장애물은 자료 형식이 달라 계산 결과를 계속 보관한다.
- 시험 코드도 장면의 기준 건물 목록을 직접 읽도록 바꿨다. 사용처 검색에서 `routeBuildings_`와 `Mesh::LoadGlb()`가 남지 않았다.
- Windows Release 전체 빌드 성공, CTest 31/31 통과. 헤더 변경 뒤 최초 증분 시험에서 앱 개체 파일 일부가 이전 클래스 배치를 유지해 접근 위반이 났다. 앱 소스와 시뮬레이터 시험을 다시 컴파일한 뒤 모두 통과했다.
