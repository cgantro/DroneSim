# 문제 해결 기록 쓰기

문제 해결 기록은 측정값을 모아 둔 일지가 아니라, 문제가 어떻게 드러났고 무엇을 확인했는지 설명하는 글이다. 독자가 증상부터 현재 상태까지 따라갈 수 있게 쓴다.

## 작성 순서

1. **증상**: 사용자가 본 현상과 재현 조건을 먼저 쓴다. 체감 문제와 측정 결과를 구분한다.
2. **첫 가설**: 당시 의심한 원인을 설명한다. 실제 기록이 없으면 개발자의 감정이나 시행착오를 만들어 내지 않는다.
3. **확인 과정**: 가설을 뒷받침하거나 뒤집은 코드, 로그, 덤프, 시험, 측정 결과를 필요한 만큼 적는다. 독자가 문제를 검토하도록 재현 조건, 관찰 기준, 변경 전후의 핵심 근거를 남긴다.
4. **수정**: 바꾼 동작과 그 이유를 쉬운 말로 설명한다.
5. **결과와 남은 점**: 재현 여부와 검증 범위를 밝힌다. 원인이 확정되지 않았으면 그 경계를 분명히 쓴다.
6. **교훈 또는 다음 확인**: 재발 방지에 도움이 되는 기준을 한두 가지로 정리한다.

## 근거와 수치

- 저장소, 실행 기록, 사용자 제공 자료에서 확인한 사실만 쓴다. 서사를 위해 "삽질", "뒤통수", "범인" 같은 감정이나 사건을 지어내지 않는다.
- 동시 발생을 원인으로 단정하지 않는다. 같은 프레임·요청·호출에서 연결된 자료가 없으면 "함께 나타났다", "가능성이 있다"고 쓴다.
- p95·p99·최댓값을 이유 없이 한꺼번에 나열하지 않는다. 문제 크기와 변경 결과를 검토하는 데 필요한 수치, 반복 횟수, 실행 조건은 표나 문단에 남긴다. 모든 표본은 이미 있는 벤치마크 자료에 연결한다.
- 서로 다른 코드 리비전, 장면, 설정, 측정 방식의 결과를 직접 비교하지 않는다. 제한이 결론을 바꾸면 결과 옆에 설명한다.
- CPU 표본 시간은 함수 한 번의 실행 시간으로 표현하지 않는다. CPU 대기와 GPU 실행도 구분한다.
- 원본 기록에 개인정보나 큰 바이너리가 있으면 공개 문서에 경로나 내용을 노출하지 않는다.

## 문장과 구성

- 자연스러운 한국어를 쓰고 필요한 현업 용어는 처음 나올 때 쉽게 설명한다.
- 문서를 짧게 만드는 일을 목표로 삼지 않는다. 재현에 필요한 조건, 핵심 로그·덤프 관찰, 변경 이유와 검증 범위는 생략하지 않는다. 반복 설명과 문제 판단에 필요 없는 수치만 줄인다.
- "최적화했다", "해결했다"고 쓰기 전에 무엇이 달라졌는지 시험이나 측정으로 확인한다.
- 제목과 소제목은 독자가 겪는 문제를 바로 알 수 있게 짓는다. 실제 기록이 없는 절을 채우려고 내용을 만들지 않는다.
- 새 문서를 만들기 전에 비슷한 기존 문서에 합칠 수 있는지 확인한다. 빌드·설정의 단순 실수는 별도 문제 해결 문서로 늘리지 않는다.

## 확인

- 문서의 원인, 수정, 검증 상태를 현재 코드와 기존 기록에 대조한다.
- 내부 문서나 무시된 파일을 사용자 안내에서 필수 참조하게 하지 않는다.
- 내부·외부 링크와 한국어 표현을 확인한다.
