# 문제 해결 기록

독자가 **증상 → 원인 확인 → 수정 → 검증**을 따라갈 수 있게 쓴다. 단순 작업 일지나 성과 홍보문으로 만들지 않는다.

## 작성 전 조사

- 관련 코드, 커밋, 테스트, 로그, 벤치마크와 기존 문서를 확인한다. 과거 문제를 현재 코드만 보고 추측하지 않는다.
- 원인 규명, 설계 판단, 검증 결과가 드러나는 사례를 우선한다. 단순 설정 실수나 중복 사례는 별도 문서로 늘리지 않는다.
- 증상·원인·수정·검증 자료가 **같은 문제와 실행 조건**을 가리키는지 확인한다.

## 작성 순서

1. **증상**: 실제 현상, 기대 동작, 재현 조건을 설명한다. 체감과 측정 결과를 구분한다.
2. **가설**: 당시 기록된 의심 원인과 근거를 적는다. 기록이 없다면 당시 생각을 꾸며 내지 않는다.
3. **확인**: 코드 흐름, 로그, 실험으로 가설을 좁힌 과정을 설명한다. 실패한 가설도 판단에 중요했다면 남긴다.
4. **수정**: 바뀐 동작과 수정 이유를 설명한다.
5. **결과**: 재현 여부, 시험 범위, 남은 문제를 밝힌다. 검증하지 못한 결과는 미검증으로 표시한다.
6. **재발 방지**: 유효한 예방 기준이나 다음 확인 사항만 짧게 적는다.

자료가 없는 항목은 억지로 채우지 않는다. 제목은 문제를 구체적으로 드러내는 문장으로 짓는다.

## 근거와 수치

- **확인된 사실과 추정**을 구분한다. 동시 발생만으로 원인을 확정하지 않는다.
- 코드 변경은 수정 사실의 근거이지 해결의 증거가 아니다. 해결·성능 개선 주장은 테스트 또는 측정으로 뒷받침한다.
- 변경 전후 비교에는 코드 버전, 환경, 입력·부하, 설정, 측정 방법, 반복 횟수와 통계 기준을 확인한다. 조건이 다르면 직접 비교하거나 개선율을 단정하지 않는다.
- 핵심 수치와 단위만 본문에 싣고 원본 측정은 접근 가능한 자료에 연결한다. CPU 프로파일러 표본을 함수 실행 시간으로 오해하거나 CPU 대기·GPU 처리 시간을 혼동하지 않는다.
- 재현하지 못했거나 원인이 불명확하면 그 범위와 필요한 추가 검증을 명시한다.

## 문장과 마무리

- 자연스러운 한국어로 쓴다. 중복 설명은 줄이되 원인 판단에 필요한 코드·조건·수치·수정 이유는 남긴다.
- 극적인 감정이나 시행착오를 지어내지 않는다. 불필요한 표·링크·코드 덩어리를 추가하지 않는다.
- 공개 문서에 개인정보, 비밀 정보, 내부 절대경로를 노출하지 않는다. 링크가 실제로 열리는지 확인한다.
- 작성 후 **원인·수정·검증 결과가 현재 코드 및 당시 기록과 일치하는지** 대조한다.
